# appjail: a thin bwrap AppImage manager

## Context
AppMan-like convenience for AppImages in user mode: no sudo, each app sandboxed with bubblewrap, full GUI support.

Review of the AM repo (ivan-hc/AM, commit d739e48) showed:
- `AppMan/appman` is a 36-line stub that downloads `APP-MANAGER` from `main`.
- AM self-updates, and runs install and updater scripts from `main` outside any sandbox.
- Only 6 of 8,735 install scripts mention any checksum or signature.
- About 95% of apps come from GitHub releases (8,247 `SITE="owner/repo"` entries).
- Its sandbox generates a wrapper around `sas` or `aisap` (bwrap frontends); see `AM/modules/install.am:723-1011`.

Goal: a small tool with declarative manifests, no remote code execution, no self-update, and a clear evidence model for verifying downloads and updates. The MVP described below is implemented in `src/appjail/` (Python, stdlib only).

## Principles
1. Declarative manifests only (source, pinned hash, permissions). No shell from the network.
2. No self-update. The tool is updated by a reviewed `git pull` or signed tag.
3. The user provides the GitHub `owner/repo`. That repo is the only fetch source for the app. Update info embedded in an AppImage never decides the source.
4. Containment is the backstop: downloads in a network-only jail; apps in a minimal-permission jail.

## Platform
Linux on x86-64 only (decided 2026-10-20). Minimum supported systems (user decision, 2026-10-20): Debian 13 (the test guest) and Ubuntu 26.04 (the `ubuntu-26.04` CI runner: bubblewrap 0.11, Xwayland 24.1, xdg-desktop-portal 1.21, kernel 7.0; the whole suite passes there except tests that need hardware the runner lacks, which skip, and the real-X11-app window test, which skips on that Xwayland's crash). Older systems are not supported or tested: on Ubuntu 24.04 the real-portal tests fail because xdg-desktop-portal 1.18 does not export `FileChooser` with the tests' fake backend (cause not investigated), and its `reuse` cannot read `REUSE.toml`. The seccomp filter is built for x86-64 and `run` refuses to start on any other architecture rather than run unfiltered; the AM index is read from its `x86_64` entries only. Other architectures are not planned.

## Commands
- `search <kw>`: text-only lookup in the local AM index (candidates only, never installs).
- `add owner/repo`: resolve, review, download, pin, write manifest.
- `run <app>`, `update [app]`, `list`, `remove <app>`, `perms <app>` (edit permissions), `history [app]` (recorded manifest changes), `tools status|install NAME` (pinned helper binaries).
- `index update`, `index rollback`: refresh or roll back the AM search snapshot.

## Resolver (GitHub first)
1. `GET /repos/{o}/{r}/releases/latest` (or `/releases` if prereleases are allowed). Optional token for rate limits (60 requests/hour unauthenticated).
2. Filter assets for `*.AppImage` matching the architecture; ask the user on multiple candidates or none.
3. Show owner, account age, stars, fork and archived status before download (typosquat check).
4. Collect evidence: `published_at`, GitHub per-asset sha256 `digest` (verify it exists), attestation (`gh attestation verify` or the attestations API; verify), embedded GPG signature.
5. Download in a throwaway network-only jail, hash, write manifest.

Implemented in `src/appjail/github.py` (client with injectable transport) and `src/appjail/textsafe.py` (escape-sequence and control-character stripping for every untrusted string shown to the user):
- Per `add`: `/repos/{o}/{r}`, `/users/{o}` (owner age), `/releases/latest` (or the first non-draft of `/releases` with prereleases), then one attestation lookup per chosen asset: 4 requests of the 60/hour budget.
- `GITHUB_TOKEN` is optional and sent only to api.github.com. Redirects are followed by hand within that host (a moved repo yields `RepoInfo.renamed`); a redirect elsewhere is refused.
- Assets whose download URL is not under `https://github.com/{owner}/{repo}/releases/download/`, or whose name has odd characters, are dropped. Digest `sha256:<hex>` is parsed; null or other algorithms mean "no digest".
- AppImage selection: `.AppImage` suffix (case-insensitive), other architectures excluded by name token; explicitly x86_64/amd64 names win over untagged ones; several candidates means the caller asks the user. `.zsync` files never match.
- `asset_pattern` is suggested by replacing the release version in the chosen name with `*`, and matched with `fnmatch`.
- Owner pinning: `add` records the owner's GitHub account id (`owner_id`, optional in the schema) and `update` blocks when the id changes, so a repository deleted and re-registered under the same `owner/repo` string is caught. A manifest from before pinning has no id: `update` warns that the account cannot be checked and pins the current id once the user approves.

Other forges (GitLab, Codeberg, SourceForge, vendor sites) are later resolvers. **Known gap (decided 2026-10-20, not planned for now):** only GitHub is supported. The AM index lists about 224 apps whose `SITE=` points elsewhere (and a few repackagers via `SITE2=`); `search` shows them but `add` cannot install them. A second resolver would sit behind the same interface as `src/appjail/github.py` (`repo_info`, `latest_release`, assets with size and optional digest); GitLab and Codeberg expose release assets with sizes, but not GitHub's `digest` or attestations, so apps from them would be tier 4 at best until the forge offers equivalent evidence.

## `add` (implemented in `src/appjail/cmd_add.py`, `src/appjail/jail.py`, `src/appjail/fetcher.py`)
`appjail add owner/repo [--name N] [--prerelease] [--tag TAG] [--dir PATH[:ro|:rw]] [--dbus NAME] [--dbus-own NAME] [--allow network|network_host|portals|userns] [--portal NAME] [--no-audio] [--no-gpu] [--display wayland|xwayland]`. `--tag` pins a specific release (looked up with `/releases/tags/<tag>`) instead of the latest; the manifest records the version and the channel `pinned`, so `update` leaves the app alone until `update APP --channel` changes that (see "Update flow").
1. Refuse early if the name exists. Fetch repo data and show the review (owner, id, account age, stars, fork/archived/renamed warnings).
2. Resolve the release, select the AppImage (ask on several, abort on none), show GitHub's digest and whether an attestation exists.
3. Ask before downloading. The download runs `src/appjail/fetcher.py` inside the network-only jail: `--unshare-all --share-net --cap-drop ALL --clearenv --new-session --die-with-parent`, system dirs and `/etc/ssl` read-only, only the staging dir writable, root remounted read-only. The fetcher follows only https redirects within github.com / *.githubusercontent.com and stops at the size GitHub announced.
4. On the host: size must equal the announced size, sha256 is computed, a GitHub digest must match, the file must be a type-2 AppImage (ELF + `AI\x02`). Any failure deletes the staging directory and writes nothing.
5. Tier 3 if GitHub gave a digest, else tier 4 (with a warning). An attestation that merely exists is shown but not counted: tier 1 needs real verification (deferred).
6. Move the file to `~/.local/share/appjail/apps/<name>/app.AppImage`, extract it to `apps/<name>/root/` (see Extraction), record the source hash in `apps/<name>/root.sha256`, and write the manifest (with `owner_id`) last. If extraction fails, nothing is kept. Defaults: audio and gpu on, network and portals off, Wayland.
- Verified in the qemu guest on 2026-10-17 (real downloads, user-approved): `AppImage/appimagetool` (14.4 MiB, digest, tier 3), `AppImage/AppImageKit` obsolete-appimagetool (2.1 MiB, no digest, tier 4 with warning), `hluk/CopyQ` (43.9 MiB, digest, tier 3). Stored sha256 equals an independent `sha256sum`; the staging directory is empty afterwards. A 2 KB cli/cli text asset also confirmed that a wrong announced size and a non-GitHub URL are refused inside the jail. None of the three had a GitHub attestation.
- Observations: appimagetool's release tag is the rolling `continuous`, so `update` must compare `sha256`/`published_at`, never the tag alone. Assets of a renamed repo live under the new canonical name, so release lookup must use `RepoInfo.full_name` (as `add` does). No "hello world" AppImage release exists on GitHub; appimagetool is the small test fixture.
- Network of the download, attestation and index-git jails (`jail.net_wrap`, run by `jail.run`): the bwrap command runs inside a private network namespace made by `pasta` (package `passt`), started with `--config-net --no-map-gw`, no port forwarding in either direction, and `--dns-forward 169.254.1.53`. The jail's `--share-net` then shares that namespace, not the host's: outbound TCP/UDP works through ordinary host sockets, but the host's loopback and the host's own addresses are unreachable (verified in the guest, with a control that the same probe reaches a host listener without pasta). The jail gets a `resolv.conf` naming only the forwarder (`resolv.conf.pasta` in the data directory, bound read-only) because the host's stub resolver on 127.0.0.53 is invisible there. Not covered: other hosts on the LAN stay reachable (pasta has no filtering). pasta is an optional host dependency: without it the jails fall back to the host network with a one-time warning on stderr. Verified with the real e2e suites (jailed download, Sigstore verification with `gh`, index fetch with `git`). Extraction jails use `--unshare-net`. The app jail's `network` permission uses the same mechanism (next bullet).
- App jail `network` (implemented, user decision 2026-10-20): an app with `network` runs in the pasta namespace like the download jails (`runner.launch` wraps the bwrap command with `jail.net_wrap(required=True)`; DNS through the forwarder `resolv.conf`), so it reaches the internet but not the host's loopback services or the host's own addresses. Without pasta the app is refused (RunError naming `passt`), never silently put on the host network. The same refusal is raised earlier, when the permission is granted (`add --allow network`, `perms --allow network`: `permargs.require_pasta`), so the user hears about it before any download or save. Apps that need host localhost services get the separate `network_host` permission (requires `network`; `--allow network_host` implies `network`; `--deny network` clears it), which keeps the host network namespace and the host `resolv.conf`; `add`/`perms` warn when it is granted. pasta closes every inherited descriptor, so bwrap's descriptors are opened inside the namespace instead: the seccomp filter is written to a private 0600 temp file, the portal handshake uses two FIFOs in a private temp directory (the parent holds both read-write, so nothing blocks and closing the block FIFO starts the app), and `/bin/sh -c 'exec "$@" 9<filter 8>status 7<block'` opens them for bwrap (`jail.net_wrap(fd_files=...)`, `runner.Pipes(fifo_dir)`; one digit only, dash redirects accept no more). pasta also runs the command as uid 0 of a user namespace mapped to the host user, so the app jail passes `--uid`/`--gid` to get its real ids back (passwd, D-Bus authentication and file ownership depend on it). Verified in the guest with a real jailed probe (host listener on loopback and on the host address unreachable, real DNS and TLS to api.github.com reachable, uid and gid unchanged; `network_host` reaches the listener) and with the real portal frontend behind pasta (`network` + `portals`). Not covered: other LAN hosts stay reachable (pasta has no filtering). Decision (user, 2026-10-20): attacks from an app against LAN hosts are outside the threat model; the goal is to keep apps off the user's own host services. An allowlisting proxy would be the way to change that, and is not planned.

## Runtime jail: implemented (`src/appjail/jail.py` `runtime_args`, `src/appjail/runner.py`)
`appjail run <name> [-- app args]`.
- Before every launch: the stored AppImage must hash to the pinned `sha256` (otherwise "refusing to run"); the extracted tree is reused only if `root.sha256` matches and the tree itself still hashes to `root.tree.sha256` (taken right after extraction: paths, modes, contents, link targets), else it is re-extracted from the verified image with a warning. Installs made before this check are re-extracted once.
- Jail: `--unshare-all` (no network unless `network`, then in a pasta namespace unless `network_host`), `--die-with-parent --new-session --cap-drop ALL --clearenv --hostname appjail`, host system dirs read-only, root remounted read-only, tmpfs `/tmp` and `/run`, `/proc`, minimal `/dev`. The extracted tree is `/app` (read-only); a persistent private home `apps/<name>/home` is `/home/app`. Generated `/etc/passwd` and `/etc/group` hide host users; only fonts, ld.so, localtime and alternatives are taken from the host `/etc` (plus hosts/nsswitch/resolv/ssl when `network`).
- Wayland: when the compositor offers `wp_security_context_v1` (sway, labwc, Mutter 46+, KWin 6.x; not weston 14), `run` makes a private listening socket, hands it to the compositor with sandbox engine `appjail` and the app name (`src/appjail/wayland.py`, hand-written minimal wire protocol with fd passing), and binds that socket instead of the host one. The compositor then hides its privileged protocols from the app; verified with sway 1.10 in the guest: `zwlr_screencopy_manager_v1` and `zwp_virtual_keyboard_manager_v1` are hidden and a real client still connects. Without the protocol `run` prints a warning and falls back to the host socket. In both cases the socket is bound read-only as `$XDG_RUNTIME_DIR/wayland-0`; nothing else from the runtime dir is visible. No X11 socket. Audio: PipeWire and Pulse sockets only when `audio`. This grants microphone capture too: neither server can restrict a client by device without a portal-style filter, so a separate `mic` permission would be a promise appjail cannot keep and is not offered. GPU: `/dev/dri`, `/dev/nvidia*` and the read-only `/sys` and Vulkan/GLVND data only when `gpu`. `dirs`: bound read-only or read-write (`~/` maps into `/home/app/`); missing directories are errors; directories that are, contain or sit inside appjail's own data/config are refused.
- Environment: a fixed whitelist (HOME, PATH, LANG, TZ, XDG_RUNTIME_DIR, WAYLAND_DISPLAY, toolkit hints, `APPDIR=/app`); no host variables leak.
- Every permission the schema accepts is enforced; anything appjail could not enforce would be refused, never ignored. `display = "xwayland"`, `dbus_filter` and `portals` are enforced (see "Xwayland", "D-Bus filtering" and "Portals").
- Seccomp (`src/appjail/seccomp.py`): a hand-assembled classic BPF filter, loaded by bwrap through `--seccomp` from a memfd. Default allow; EPERM for the Flatpak-style deny list (kernel modules, kexec, `bpf`, `perf_event_open`, keyrings, `userfaultfd`, `ptrace`, `process_vm_*`, handle-based opens, NUMA policy, the `TIOCSTI`/`TIOCLINUX` ioctls, x32 ABI). The syscall table is checked in the guest against the kernel's `unistd_64.h` (`linux-libc-dev`). x86_64 only: on any other architecture `run` refuses instead of running unfiltered.
- Nested user namespaces: denied by default (`--unshare-user --disable-userns` at the kernel level, plus the filter: `unshare`, `setns`, `clone` with any CLONE_NEW* flag, the mount API and `pivot_root`/`chroot` fail, `clone3` answers ENOSYS so libc falls back to `clone`). The `userns` permission (`--allow userns`, `perms --allow userns`) lifts exactly that, for Electron/Chromium sandboxes and nested bwrap; the always-denied list still applies. `perms` warns when it is granted.
- GPU: the Debian *cloud* kernel has no DRM drivers, so the first guest had no `/dev/dri`. Fixed by `tests/vm/provision.sh`: it installs the regular `linux-image-amd64`, removes the cloud kernel, and `start.sh` adds a `virtio-gpu-pci` device, giving `/dev/dri/card0`, `card1` and `renderD128`. The test `test_gpu_nodes_only_when_granted` opens the render node inside the jail with `gpu = true` and shows that `/dev/dri` is absent with `gpu = false`. Supplementary groups (`render`, `video`) survive in the jail, so group-owned nodes stay usable. This proves the device plumbing only; the guest renders with Mesa software drivers, not real hardware.
- Verified in the guest: all isolation properties by test (private home, host files invisible, no capabilities, own PID namespace, loopback-only network, only the granted sockets and directories, environment whitelist, tamper refusal) and a real Wayland client (`weston-simple-shm`) connecting to a headless weston from inside the jail. appimagetool and AppImageKit run end to end through `appjail run`. CopyQ cannot run in the Debian 13 guest, with or without the jail: it needs glibc 2.43 and Debian 13 has 2.41 (the previous release v16 is as new). AppImages use the host libc, so this is a limit of the guest, not of appjail. The GUI test app is therefore `skyjake/lagrange` (SDL, 11 MB): `tests/test_e2e.py` adds it for real, runs it inside the jail against a headless weston, and checks that its settings land in the private home and nothing reaches the real home.

## Directory access and file isolation
Files are isolated by default. The app sees: the host system directories (`/usr`, `/lib*`, `/bin`, `/sbin`) read-only, its own extracted tree (`/app`, read-only), a private writable home (`/home/app`, stored under `~/.local/share/appjail/apps/<name>/home`), and empty tmpfs `/tmp` and `/run`. It does not see the real home, Documents, Downloads, other apps, appjail's own data or manifests, or any host file that was not granted.

An app can be given specific directories, never the whole home:
- In the manifest: `permissions.dirs = ["~/Documents/notes", "~/Pictures:rw"]`. `~/x` appears as `/home/app/x`; absolute paths outside the home appear at the same path. Read-only unless `:rw`.
- `appjail add owner/repo --dir PATH[:ro|:rw]` (repeatable) writes the grant into the manifest. The path must exist, is normalised (relative paths against the current directory, home becomes `~/`), and is checked before any network access.
- `appjail run NAME --dir PATH[:ro|:rw]` grants a directory for that run only; the manifest is unchanged and the run prints "Temporary access for this run: ...".
- `appjail perms NAME --add-dir PATH[:rw]` and `--rm-dir PATH` edit the grants later.
- Sensitive paths are refused in every mode, at parse time and again at launch on the symlink-resolved path (`manifest.sensitive_reason`): credential stores (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.kube`, keyrings, `.git-credentials`, `.pki`, shell and tool history files, browser profiles, mail, `~/.var`, and files named like password databases or private keys: `*.kdbx`, `*.key`, `*.pem`, ...), the broad `~/.config`, `~/.local`, `~/.local/share`, `~/.cache`, and system trees (`/etc`, `/dev`, `/proc`, `/sys`, `/run`, `/usr`, `/boot`, `/root`, ...). Read-write access is also refused where it could plant code that runs outside the jail (`~/.local/bin`, `~/.config/autostart`, `~/.config/systemd`, `~/.local/share/applications`, shell and editor startup dirs). There is no override: use a subdirectory the app needs.
- Refused at parse time or launch: `/`, the home directory itself or any parent of it, `..` components, appjail's own data and config trees (and parents/children of them), and missing paths. Symlinks are resolved when the jail starts, so a link cannot point a granted path elsewhere afterwards.
- `appjail run NAME --file PATH[:rw]` (repeatable) binds just that file for that run (`jail.file_binds`): read-only unless `:rw`, nothing else from its directory is visible, and the in-jail path is appended to the app's arguments (a file under the real home appears under the app's home). Only regular files are accepted; the path is resolved first (a link cannot dodge the policy) and the `dirs` sensitive-path policy applies, plus `PERSIST_HOME_FILES` (`.bashrc`, `.profile`, `.gitconfig`, ... never read-write). Not persisted in the manifest. A bind-mounted file cannot be replaced by rename, so apps that save by write-and-rename fail on `:rw`; the portal file chooser exists too (see "Portals").

## Xwayland (implemented in `src/appjail/jail.py`: `xwayland_command`)
`display = "xwayland"` is for apps that only speak X11. The host X11 socket is never bound (it would let the app read every other X client's keystrokes and screen). Instead the app command is wrapped by a short `sh` script that starts a rootless `Xwayland` inside the jail, as a client of the restricted Wayland socket, with `-nolisten tcp` and `-displayfd`; then it sets `DISPLAY` and execs the app.
- The X socket lives in the jail's private `/tmp` and abstract namespace (the network namespace is unshared), so no other app and no host X server is reachable. The app environment has no `WAYLAND_DISPLAY` and selects X11 toolkits (`GDK_BACKEND=x11`, `QT_QPA_PLATFORM=xcb`, `SDL_VIDEODRIVER=x11`, ...). Xwayland dies with the jail.
- The wrapper script waits up to 20 s for Xwayland to report its display, and gives up at once, with a message, if Xwayland exits (a fixed 5 s wait made the test flaky on a slow CI runner).
- Needs `/usr/bin/Xwayland` on the host (package `xwayland`); `run` stops with a clear message when it is missing. With no window manager, windows map as plain toplevels.
- Verified in the guest: `xdpyinfo` inside the real jail reaches the private Xwayland over headless weston. Also verified with a real X11-only AppImage (ImageMagick 7.1.2-34 `display`, opt-in `tests/test_xwayland_e2e.py`): a window appears with `display = "xwayland"` and the app fails with `display = "wayland"`. Not verified: GPU acceleration through Xwayland (glamor). On the GitHub runner (Xwayland 24.1.10) a bare Xwayland without appjail segfaults on that client, so the test skips there.

## D-Bus filtering (implemented in `src/appjail/dbusproxy.py`)
`permissions.dbus_filter` is a list of session-bus names the app may talk to, for example `org.freedesktop.Notifications` or `org.mpris.MediaPlayer2.*`.
- With an empty list the jail has no bus at all (no `DBUS_SESSION_BUS_ADDRESS`, no socket), as before.
- Otherwise `run` starts `xdg-dbus-proxy` on the host side, inside a bwrap jail of its own: no network, read-only system, and only two things from the host, the real bus socket (read-only) and a private directory `$XDG_RUNTIME_DIR/appjail-XXXX` for the new socket. The proxy runs `--filter` with one `--talk=NAME` per entry: every other name is invisible and every other call is answered with an error by the proxy itself. The app jail binds only the proxy's socket, as `$XDG_RUNTIME_DIR/bus`, and gets `DBUS_SESSION_BUS_ADDRESS` pointing at it. The real bus socket is never visible to the app.
- Lifetime: `run` waits (5 s) for the proxy's ready byte on a sync pipe, and stops the proxy and removes its directory when the app exits or `run` fails. The proxy also dies with appjail (`--die-with-parent`).
- The host bus address must be `unix:path=...` (from `DBUS_SESSION_BUS_ADDRESS`, else `$XDG_RUNTIME_DIR/bus`); abstract and TCP addresses are refused. Needs the `xdg-dbus-proxy` package, reported if missing.
- Names that would hand over the host or the desktop are refused when the manifest is loaded and when entered on the command line: `org.freedesktop.DBus`, `org.freedesktop.systemd1` (starting arbitrary units), `org.freedesktop.Flatpak`, `org.freedesktop.portal*` and `org.freedesktop.impl*`, `org.gnome.Shell`, `org.gnome.SessionManager`, `org.kde.KWin`, `org.kde.klauncher*`, plus any wildcard that covers them, and wildcards with fewer than three name parts before `.*`. Names that expose stored secrets (`org.freedesktop.secrets`, keyring, kwallet) are allowed with a warning.
- Owning a name (an app that exports MPRIS or a single-instance name) is a second list, `permissions.dbus_own`, passed to the proxy as `--own=NAME` (which also allows talking to it). Names in the desktop namespaces (`org.freedesktop.`, `org.gnome.`, `org.kde.`, `org.a11y.`, `com.canonical.`, `org.ayatana.`) cannot be owned, so an app cannot impersonate the notification daemon, the secret service or polkit; the exception is the status-notifier item names. The proxy only matches a trailing `.*`, so a `-<pid>` suffix as in `org.kde.StatusNotifierItem-1234-1` is not expressible (a tray icon needs `org.kde.StatusNotifierItem.*` and a client that uses that form; not verified). `--dbus-own NAME` on `add`; `--add-dbus-own` / `--rm-dbus-own` on `perms`; `add` and `perms` warn for each owned name.
- Commands: `appjail add ... --dbus NAME` (repeatable, talk only) and `appjail perms APP --add-dbus NAME / --rm-dbus NAME`.
- Verified in the guest with a real `dbus-daemon`, the real proxy and `dbus-send` inside the real jail: a call to the bus control interface is denied; a call to a granted name reaches the bus (which answers that it has no such service); a call to any other name is answered by the proxy and never reaches the bus; the proxy and its socket directory are gone afterwards. Not verified: real desktop services (notification daemon, MPRIS players), which the headless guest does not run.

## Portals (implemented in `src/appjail/portal.py`, `src/appjail/dbusproxy.py`, `src/appjail/runner.py`)
`portals = true` gives the app the desktop portals (file chooser, notifications, settings, ...) through the same filtering proxy as `dbus_filter`; the app never sees the real bus.
- **Identity.** xdg-desktop-portal decides who is calling by reading `/proc/<pid>/root/.flatpak-info` of the D-Bus peer and `$XDG_RUNTIME_DIR/.flatpak/<instance>/bwrapinfo.json` (read from its source, `shared/xdp-app-info-flatpak.c`). That file format is the only sandbox identity it understands besides Snap and Linyaps, so appjail writes it: a compatibility shim, nothing depends on or installs Flatpak. The app id is `app.appjail.<name>` (`portal.app_id`). The identity file is bound into the proxy's jail (the proxy connection is the peer the portal sees), never into the app's, so the app can neither read nor forge it, and cannot pick its own id (the alternative, `org.freedesktop.host.portal.Registry`, lets an app claim any id that has a `.desktop` file). `bwrapinfo.json` carries the app jail's init pid, taken from bwrap's `--json-status-fd`; bwrap's `--block-fd` holds the app back until the file exists.
- **Side effects of the shim:** the portal's permission store and Background portal treat the app as a Flatpak app (an autostart entry would say `flatpak run`, inert without Flatpak). Document-portal paths are `<XDG_RUNTIME_DIR>/doc/<id>/<name>`; the per-app view `doc/by-app/<app id>` is bound at `/run/user/<uid>/doc` and, if the host runtime dir differs, at its path too.
- **Which interfaces.** `portals = true` allows only the safe set (`manifest.PORTAL_SAFE`: FileChooser, Notification, Settings, Trash, Print, Inhibit, NetworkMonitor, ProxyResolver, Secret, Realtime, MemoryMonitor, PowerProfileMonitor) plus the document portal. The privileged interfaces must be named in `portal_interfaces` (`PORTAL_OPT_IN`: OpenURI, Email, Screenshot, ScreenCast, RemoteDesktop, GlobalShortcuts, InputCapture, Camera, Location, Account, Wallpaper, Background, Usb); `add`/`perms` warn for each. `Flatpak` (spawn on the host) and `DynamicLauncher` (installs launchers) are refused in the manifest. Everything else on the portal's name is invisible to the app (`--call` rules per interface; unknown calls are answered with AccessDenied by the proxy).
- **Revoking grants:** see `appjail portals` under Commands.
- **The document portal** is D-Bus activated; if `doc/by-app/<id>` is missing, `run` asks the bus to start it (`dbus-send`, GetMountPoint) and otherwise stops with a clear message. It needs FUSE.
- **Verified in the guest** with the real xdg-desktop-portal 1.20.3 and document portal on a private bus, and a fake FileChooser backend (`tests/portal/`): the backend received exactly `app.appjail.app` as the caller, the response URI pointed into the document portal, the app read the chosen file through the FUSE mount inside the jail, `/.flatpak-info` is absent in the app jail, OpenURI is refused unless opted in (and reaches the portal when it is), the host's `org.freedesktop.portal.Flatpak` name is invisible, bus control calls are denied, and the instance directory and proxy sockets are gone afterwards.
- **Also verified with the real GTK backend** (`xdg-desktop-portal-gtk` under headless weston, `tests/portal/client_real.py`): Settings reads and the start of a FileChooser request go through the filtered bus; the dialog itself is not driven.
- **Not verified:** the GNOME, KDE and wlr backends, and any interactive dialog. Desktops differ in which interfaces they implement and how dialogs look; behaviour of each privileged interface depends on its backend asking the user.

### Lifetime of the jail (implemented in `src/appjail/runner.py` `_wait_group`)
- The app runs in its own session. SIGINT, SIGTERM and SIGHUP sent to appjail are forwarded to the whole process group, and the group is killed when the app ends. Reason (found 2026-10-21): killing `pasta` leaves the bwrap it started running, because `--die-with-parent` does not follow pasta's namespace helper, so an app with `network` would outlive its launcher. Test: `test_terminating_the_launcher_stops_the_whole_jail`.
- SIGKILL of appjail cannot be caught. Without pasta the jail dies with its parent (`--die-with-parent`). Behind pasta it did not (verified: the bwrap pid 1 of pasta's pid namespace survives the death of pasta and of appjail), so `jail.Lifeline` gives the launcher a FIFO that it holds open read-write; `net_wrap(lifeline=...)` starts a watcher in the namespace that reads it, and at end-of-file (the kernel closed the launcher's descriptor) runs `kill -KILL -1`, but only when it is pid 1 of a private pid namespace, since `kill -1` anywhere else would hit all of the user's processes. The launcher's host pid cannot be polled instead: pasta's namespace has its own `/proc`. Residue after a SIGKILL: an empty `appjail-life-*` directory in `XDG_RUNTIME_DIR`. Not applied to the short-lived download, attestation and index jails (bounded by their own limits). Test: `test_terminating_the_launcher_stops_the_whole_jail[SIGKILL-pasta]`, which fails without the lifeline.

## Extraction (implemented in `src/appjail/appimage.py`, `src/appjail/jail.py`)
- The AppImage is extracted and `AppRun` executed; it is never mounted (FUSE mounts do not work well in user namespaces). The AppImage runtime itself never runs outside a jail.
- Offset: end of the ELF runtime = `e_shoff + e_shentsize * e_shnum` (64-bit little-endian ELF only). `hsqs` there means SquashFS; `DWARFS` means a DwarFS image (extracted with the pinned helper, see "DwarFS AppImages"); anything else is unsupported.
- Preferred path: `/usr/bin/unsquashfs -no-progress -no-xattrs -p 2 -o <offset> -d /out/root /app.AppImage` in a jail with `--unshare-all` (no network), read-only root, the AppImage bound read-only and only the work directory writable. The AppImage runtime never runs.
- Fallback (only with the user's consent, asked before the download when `unsquashfs` is missing): a private copy runs `--appimage-extract` in the same jail. Verified in the guest on appimagetool.
- Limits: the work directory is polled every 0.25 s; the jail is killed beyond 4 GiB of disk use or 500,000 entries, or after 15 minutes. After extraction the apparent size is checked as well, so sparse files cannot hide a huge tree.
- Host-side validation never follows symlinks: only regular files, directories and symlinks are allowed (fifos, sockets and devices reject the image); set-id and sticky bits are cleared; directories get owner access so the tree can always be deleted.
- Entry point: `AppRun` must resolve, through relative symlinks only, to an executable regular file inside the tree. Absolute symlinks, `..` above the root, loops and missing or non-executable targets reject the image.
- Extraction goes to `<root>.tmp` and is renamed on success. A hostile image therefore can fill only the work directory and cannot leave a partial `root`.
- Verified in the guest on the three approved AppImages: appimagetool 20 entries/36.9 MB, AppImageKit 48/15.4 MB, CopyQ 439/132.5 MB, each in under a second, `AppRun` a regular file in all three.

## Manifest (TOML, stored in the user's own git repo)
`source` (github owner/repo), `channel`, `asset_pattern`, `version`, `sha256`, `evidence_tier`, `published_at`, `permissions` (network, audio, gpu, display = wayland|xwayland, dbus_filter, portals, dirs[]).

Implemented in `src/appjail/manifest.py` (schema 1), one file per app at `~/.config/appjail/apps/<name>.toml`:
- Top level: `schema = 1`, `name` (`[a-z0-9][a-z0-9._-]{0,63}`), `source`, `asset_pattern` (fnmatch, no `/`), `version`, `sha256` (64 lowercase hex), `evidence_tier` (1-5), `published_at` (UTC `YYYY-MM-DDTHH:MM:SSZ`).
- `[permissions]` is optional and everything defaults to denied: `network`, `network_host` (needs `network`), `audio`, `gpu`, `portals`, `userns` (bool; `add` writes `audio` and `gpu` as true unless `--no-audio` or `--no-gpu`); `dbus_own` (list of session-bus names the app may own), `portal_interfaces` (list of opt-in portal interface names, only with `portals = true`); `display` (`wayland` default, or `xwayland`); `dbus_filter` (list of D-Bus names, optional `.*` suffix); `dirs` (list of absolute or `~/` paths, optional `:ro`/`:rw`, default read-only; `/`, `~/` and `..` rejected).
- Strict: unknown keys, wrong types, control characters and bad formats are errors. The writer is deterministic and atomic, and refuses invalid manifests.

## Trust tiers (never silently downgraded)
1. Build attestation (Sigstore / GitHub artifact attestations): implemented, see "Attestation verification".
2. Pinned-key GPG signature. **Deferred (decided 2026-10-20).** A signature proves a key, not its owner, so `add` would still be trust on first use for the key fingerprint; it needs a per-app fingerprint pin, a jailed `gpgv`, `update` rules (key change blocks, lost signature is a downgrade) and a source for the signature file. Tier 1 plus the quarantine hash already cover attested and unattested apps. Revisit when a wanted app signs with GPG and has no GitHub attestation.
3. Publisher-pinned hash / GitHub digest.
4. Trust on first use.
5. Cross-check against another source (weak).

Most AppImages will only reach tiers 3-4. That proves "unchanged, same account", not "safe".

## Attestation verification (implemented in `src/appjail/attest.py`, `src/appjail/snappy.py`, `src/appjail/tools.py`)
Tier 1 means: a Sigstore build attestation covers the exact downloaded bytes and its certificate names this repository and GitHub Actions.
- Opt-in helper: `appjail tools install gh` fetches the pinned GitHub CLI v2.102.0 tarball (size and sha256 in source; the executable inside is pinned too and re-hashed before every use). Without it an existing attestation is shown as "present, cannot be verified" and the tier stays 3 or 4.
- Bundles are fetched by appjail (`github.Client.attestation_bundles`): the listing from api.github.com, then each bundle from the short-lived `*.blob.core.windows.net` URL (https only, 1 MiB cap, no credentials), Snappy-decoded by a bounded stdlib decoder. Nothing from them is trusted until verified.
- `gh attestation verify --bundle` runs in a jail with network (it fetches the Sigstore trusted root over TUF) that sees only the subject, the bundles and a scratch directory. No GitHub token is passed (`gh` insists on one being set; a dummy is given and never used with `--bundle`). gh checks signatures, the transparency-log entry, the subject digest and that the signing identity belongs to `owner/repo`.
- appjail then re-reads the certificate: issuer must be GitHub Actions, `sourceRepositoryURI` must equal the repository, and `sourceRepositoryOwnerIdentifier` must equal the pinned owner account id.
- `add`/`update` verify after the download, on the real bytes, so tier 1 is possible even without GitHub's digest. A failed verification never aborts an `add` (tier 3/4 with the reason shown); for an app already at tier 1 it blocks the update: no attestation on GitHub blocks before downloading, a bundle that does not verify aborts after it, and nothing is installed.
- Verified live in the guest on a cli/cli release: the signing workflow `deployment.yml` was reported; another repository's name, a wrong owner id and a one-byte change to the file are all refused (`tests/test_attest.py`, opt-in with `APPJAIL_E2E=1`).
- Limits: identity is the repository and owner account, not a specific workflow or branch, so any workflow of that repository can attest. A compromised repository or workflow still gets tier 1; that is what the quarantine is for. Verification needs network access to the Sigstore TUF repository.

## Update flow
1. Resolve the new release.
2. Download in a throwaway jail and verify the evidence.
3. Show a diff: hashes, tier, permissions, release link.
4. Enforce a quarantine delay (default 7 days, overridable).
5. User approves; the manifest is committed to the user's git repo.

A tier downgrade or an owner change blocks the update.

### As implemented: `appjail update [app] [--prerelease] [--channel C] [--quarantine DAYS]`, `list`, `remove`, `perms`
- Without `app`, every installed app is checked in name order (two API requests each); one failure does not stop the others, and the exit status is 1 if any app was blocked or failed. A GitHub rate limit stops the whole run at once: the remaining apps are listed as "not checked (rate limited)" (exit status 1) instead of each repeating a doomed request; `GITHUB_TOKEN` raises the limit.
- **Resolve:** `repo_info` on the pinned `source`, then the latest release (stable only unless `--prerelease`). The asset is the one `asset_pattern` selects (the user chooses if several match). The manifest records an update `channel` (top-level key, omitted when `stable`): `add` writes `pinned` for `--tag` and `prerelease` for `--prerelease`; `update` never touches a pinned app (it says so and makes no request), asks for pre-releases on a `prerelease` app, and `appjail update APP --channel stable|prerelease|pinned` changes the policy and saves it. `--prerelease` on `update` stays a one-run override. A release published before the installed one is never installed (it is reported instead), so a pre-release install is not "downgraded" to an older stable one.
- **Up to date** means the GitHub digest equals the pinned sha256 (tier 3), or, without a digest (tier 4), the same tag and `published_at`. Rolling tags such as `continuous` are therefore detected by hash or publication time, never by tag alone. Limitation: a tier 4 asset swapped in place without a new publication time is not seen by the check itself; the quarantine hash below narrows this.
- **Blocks** (no override, no download, no pending state): the repository's owner account id differs from the pinned `owner_id`; the evidence tier would get weaker (digest gone: 3 -> 4). To go on anyway, `remove` the app and `add` it again after checking the repository. **Cautions** (shown, not blocking): no `owner_id` pinned yet (it is filled in by the update), repository renamed or transferred (the new canonical name is recorded), repository archived.
- **Quarantine:** a candidate is identified by its GitHub digest, or by tag, publication time and size when there is none. The first time it is seen is stored in `apps/<name>/pending.json` (`key`, `tag`, `first_seen`). It can be installed once `first_seen` plus the delay (7 days, `--quarantine DAYS`, 0 disables with a warning) has passed. A different candidate (including a swapped asset in the same release, when GitHub gives a digest) starts a new clock. **Tier 4 hash check:** without a GitHub digest nothing identifies the content, so the first waiting run asks to download the candidate in the network-only jail once, only to hash it, and stores the sha256 in `pending.json` (`sha256`, optional; declining prints a warning and the check is skipped). When the quarantine ends, the download that would be installed must hash the same; if it does not, nothing is installed (`CHANGED DURING QUARANTINE`, status blocked), the clock restarts and the new hash is recorded. Tier 3 candidates need none of this: the digest is part of the candidate key.
- **Install:** confirm, jailed download (as in `add`), size and digest checks, AppImage check, and for tier 4 the new sha256 is shown and confirmed again. The new image is extracted into the staging directory first; only then are tree, image, marker and manifest replaced. A failure at any point restores the previous tree and image. Permissions are never changed by an update. The manifest in `~/.config/appjail` is rewritten but not committed: committing is left to the user's own git.
- `appjail list`: name, version, source, tier, granted permissions, directories and any update seen.
- `appjail remove APP [--yes]`: deletes the manifest and the app directory, including the private home (its settings and data); asks first.
- `appjail portals APP [--revoke DOC_ID]... [--revoke-all] [--yes]`: lists the documents the document portal granted to the app id `app.appjail.<name>` (host permission store, table `documents`, read with `dbus-send`) and revokes them through `org.freedesktop.portal.Documents.RevokePermissions` (host side, nothing new reaches the jail). Revoking only in the permission store is not enough: verified against the real portal that it keeps serving the file; the portal call removes the per-app view at once. The app's own recent-files list in its private home is untouched (it lists paths it can no longer open). `remove` revokes the grants too, and notes it when the app had portals and the bus is unreachable.
- `appjail perms APP [--allow|--deny network|network_host|audio|gpu|portals|userns] [--add-portal NAME] [--rm-portal NAME] [--display wayland|xwayland] [--add-dir PATH[:ro|:rw]] [--rm-dir PATH] [--add-dbus NAME] [--rm-dbus NAME] [--add-dbus-own NAME] [--rm-dbus-own NAME] [--yes]`: shows the permissions, or shows before/after and asks before saving. `--add-dir` uses the same validation as `add --dir`. The pinned release is untouched. `--display xwayland` is enforced by the runner (see "Xwayland").

## Manifest history (implemented in `src/appjail/history.py`)
Every change `add`, `update` (install and `--channel`), `perms` and `remove` make to `~/.config/appjail` is committed to a local git repository there (author `appjail`). The manifests hold the pins and sit where any process of the user can write, so this is the tamper evidence: `appjail run` warns when a manifest differs from the last commit, and `appjail history [APP] [--limit N]` lists the changes.
- git runs inside a jail with no network that sees only the config directory (`jail.local_git_args`), with user and system git configuration ignored and hooks, fsmonitor and signing disabled. A hostile `.git/config` (filters, fsmonitor) can therefore run code only inside that jail.
- Best effort by design: no git, or a config directory that already lies inside another repository (a dotfiles repo), means no history and no error; `history` then says so. Nothing is ever pushed anywhere.
- It detects edits made outside appjail, not an attacker who also rewrites `.git`; it is not a substitute for protecting the account.

## AM as lookup-only index
- Local snapshot of ivan-hc/AM pinned by commit; read as text only (never sourced or executed); terminal escape sequences stripped.
- `search` reads `programs/x86_64-appimages` (name, description) and `SITE=` from `programs/x86_64/<app>` to suggest a repo.
  - Non-`owner/repo` entries are flagged "resolve manually" (about 224 of them).
  - Repackager repos (e.g. `ivan-hc/Firefox-appimage`, via `SITE2=`) are flagged.
- The user must still type or paste `owner/repo` to `add`. A search hit never installs anything.
- `index update`:
  - shallow sparse fetch of only `programs/x86_64-appimages` and `programs/x86_64/`, in the network-only jail;
  - git run without hooks, submodules, LFS or filters;
  - prints a diff summary: apps added and removed, and changed `SITE=` owner/repo (changed owner gets a loud warning);
  - the user accepts, the tool pins the new commit and keeps the previous one for `index rollback`;
  - AM commit signatures (checked on the last 200 commits up to d739e48): 139 carry a PGP signature (GitHub web-flow key), 2 SSH, 59 unsigned. The pinned commit d739e48 and the maintainer's own commits are unsigned. Signatures therefore cannot prove maintainer authenticity. The controls are pinning by commit hash and the diff review above; verifying the web-flow signature is at most a weak "came through GitHub" signal.
- The index only affects `search`. Installed apps never depend on it.

### `index` commands (implemented in `src/appjail/indexsync.py`, `src/appjail/jail.py` `git_args`)
- `appjail index update [--commit SHA]`: one script runs in the network-only git jail (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_ALLOW_PROTOCOL=https`, terminal prompts off; `core.hooksPath=/dev/null`, no attributes file, no submodule recursion, https only). It creates a partial clone (`--depth 1 --filter=blob:none`), sparse-checks-out only `/programs/x86_64-appimages` and `/programs/x86_64/`, and reports the commit and whether a signature header is present (not verified). `--commit` accepts only 40 lowercase hex digits (or the default `HEAD`), so no ref or option text from the user or the network reaches git.
- The host never runs git on the result. `collect` copies the list and the install scripts as plain files into a staging snapshot; a symlink, special file, unexpected directory or oversize file refuses the whole snapshot, odd file names are skipped and counted, and the list must contain apps.
- The review: commit, number of scripts, signature note, then apps added and removed, and every app whose suggested source changed. A change of owner (compared case-insensitively) is a loud warning; the same owner with another repository, or a source that appears or disappears, is listed as a source change. Nothing is pinned until the user confirms (default no). Declining or failing removes all temporary directories.
- State under `~/.local/share/appjail/index/`: `snapshots/<commit>/programs/...`, `tree` (a symlink to the current snapshot, swapped atomically), `PINNED`, `PREVIOUS`. Only the current and the previous snapshot are kept. `appjail index rollback` swaps them (so it can be undone), and `appjail index status` prints both commits.
- Measured in the guest: the fetch takes about 3 s and 42 MB of work space; a snapshot is 39 MB. Moving from the analysed commit d739e48 to the remote HEAD (220f506 at the time) showed 128 apps added, 13 removed and no owner or source changes; the remote HEAD was unsigned like the analysed commit.

## Search (implemented in `src/appjail/index.py`)
`appjail search KEYWORD... [--limit N] [--all]` reads the local snapshot at `~/.local/share/appjail/index/tree/` (filled by `index update`, step 5; the pinned commit is in `index/PINNED`) and prints suggestions only.
- Matching: every keyword must occur (case-insensitive) in the name or the description. Ranking: exact name, name prefix, all keywords in the name, any keyword in the name, description only; alphabetical within a rank.
- For each shown hit the install script `programs/x86_64/<name>` is read as text (256 KiB cap, regular files only, symlinks refused, `O_NOFOLLOW`) and the first `SITE=` / `SITE2=` assignments are extracted with a regex, comment lines ignored. Nothing is sourced, expanded or executed (a test plants `$(touch ...)` in a script and checks it never runs).
- A `SITE` that is `owner/repo` (or a github.com URL) becomes "source owner/repo -> appjail add owner/repo". Anything else (vendor site, shell variable, other forge) is flagged "resolve manually: ...". A `SITE2` is flagged "repackager ...".
- List lines must look like `<bullet> name : description` with a plain name, so `../x` style entries are dropped before any file name is built. All text is cleaned of escape sequences and control characters.
- Measured on AM at d739e48 in the guest: 8,140 list entries, 7,855 with a GitHub source, 284 flagged "resolve manually", 1 without any source, 63 flagged as repackager; parsing takes 0.05 s, resolving every entry 1 s, a search 0.05 s.

## DwarFS AppImages (implemented in `src/appjail/tools.py`, `src/appjail/appimage.py`)
- DwarFS-based AppImages: supported through a pinned helper (`src/appjail/tools.py`). Evaluation (2026-10-18): Debian 13, trixie-backports and sid have no `dwarfs` package (`apt-cache` in the guest and packages.debian.org), so there is no distribution-trusted source. Upstream `mhx/dwarfs` v0.15.8 publishes a static multi-call binary, `dwarfs-universal-small-0.15.8-Linux-x86_64` (2,195,148 bytes), whose `--tool=dwarfsextract` takes `--image-offset`; GitHub's digest for the asset equals the downloaded file's sha256 (`d29734ed...e69`).   - Trust model: the tool's URL, size and sha256 are constants in appjail's reviewed source. `appjail tools install dwarfs` (explicit, asks first) downloads it in the network-only jail and keeps it only if size and hash match; it lives in `~/.local/share/appjail/tools/`, is re-hashed before every use, and runs only inside the extraction jail (no network, read-only root, `--skip-devices --skip-specials`), followed by the same host-side tree validation as SquashFS. The only noise was htop's harmless "Cannot find CA Certificates" warning (no host `/etc/ssl` in a no-network jail). Both repositories are small (0 and 5 stars), which appjail flags.
  - Verified in the guest: the real tool builds and extracts an image in the jail, symlinks are preserved (the validator rejects the escaping ones), and the opt-in `tests/test_tools.py` end-to-end test passes with the real download.
  - `squashfs-tools` 4.6.1 is in trixie/main; appjail needs it (`apt install squashfs-tools`) and reports its absence clearly.

## Findings: GitHub API (docs, plus live check on cli/cli v2.102.0, 2026-10-17)
- Release assets have a `digest` field ("string or null"). Live: all 22 assets of cli/cli v2.102.0 carry `sha256:<64 hex>`. Treat null as "no digest" and fall back to TOFU (older releases may lack it).
- Attestations: the documented `GET /users/{username}/attestations/{subject_digest}` and the `orgs/` variant return 401 without a token. The repo-scoped `GET /repos/{owner}/{repo}/attestations/{subject_digest}` works unauthenticated (200) and returns `attestations[]` with `repository_id`, `bundle_url` (short-lived signed blob URL); other fields were not inspected. cli/cli publishes attestations for its release assets.
- Use the repo-scoped endpoint, with the digest taken from the release asset. Verifying the Sigstore bundle is deferred, so the MVP only records whether an attestation exists (this alone is not proof: the check must later confirm the signing workflow and repo identity). Existence suggests tier 1 is reachable for some repos.
- Unauthenticated rate limit is 60 requests/hour; a release plus attestation lookup costs 2.

X11 is dropped only when a Wayland socket exists.
- Good parts to copy: `--unshare-user/pid/uts/ipc/cgroup`, `--die-with-parent`, `--new-session`, GPU binds including nvidia nodes.
- Decision: do not build on `sas`. Write bwrap flags directly in Python. Reasons: shell (violates the language rule), permissive defaults opposite to our model, FUSE mount instead of extraction, and it is a moving external dependency. Use its GPU and runtime-dir handling as reference only.
- AM also supports `aisap` (mgord9518/aisap), not evaluated.

## Findings: Flatpak comparison
- Flatpak already offers a mature sandbox, portals, signed OSTree remotes and permission overrides. It covers the need where the app exists on Flathub.
- It does not cover: AppImages released only on GitHub, user-pinned per-release hashes with a quarantine delay, and declarative manifests in the user's own git repo. appjail targets that gap and does not replace Flatpak. Prefer Flatpak when the same app is available there.

## Findings: Firejail comparison (netblue30/firejail, read 2026-10-18: README and `etc/inc/disable-common.inc`)
- Firejail is a setuid-root C program (namespaces, seccomp-bpf, capabilities, optional Landlock) under GPL-2.0, with 900+ maintainer-written per-application profiles. Its README does not mention AppImage.
- Decision: not a base and not a dependency. It needs setuid root (appjail runs unprivileged bubblewrap), its profiles are implicitly trusted text rather than pinned declarative manifests, and the GPL-2.0 licence rules out copying code or profile text into this MPL-2.0 project. Only ideas were taken, written from scratch.
- Useful as a checklist for the `dirs` policy: its denylist covers credentials and keys, keyrings and certificates, cloud configs, shell and editor startup files, autostart and session scripts, shell and application history, mail, encrypted-volume tools, other sandboxes' data (Flatpak, Snap) and sockets of container runtimes. appjail's `SECRET_HOME_DIRS`, `BROAD_HOME_DIRS` and `PERSIST_HOME_DIRS` cover the credential, keyring, cloud, startup and autostart groups; not yet covered: shell history files (`.*_history`, `.viminfo`), `.git-credentials`, `*.kdbx` password databases, `.pki`, browser profiles, mail directories, `.var`, and `$XDG_RUNTIME_DIR` sockets of other tools. Open point, see CLAUDE.md.
- It also strips token variables (`GH_TOKEN`, `GITHUB_TOKEN`, `CARGO_REGISTRY_TOKEN`) from the sandbox environment; appjail clears the whole environment and passes a fixed whitelist, so nothing leaks by construction.
- X11: Firejail's `--x11` defaults to Xephyr and it removed Xpra, which supports appjail's plan for `display = "xwayland"` (a separate X server inside the jail, never the host X11 socket). It adds no new technique.
- Landlock (unprivileged kernel filesystem filter, kernel 5.13 or newer): Firejail offers it as an experimental extra. A possible later hardening layer for appjail on top of bubblewrap; Python's stdlib has no wrapper, so it would be raw `syscall` use like the seccomp filter. Not evaluated beyond this note.

## Findings: Landlock and a private network namespace for the network jails (evaluated 2026-10-19, not implemented)
- Which jails have the host network: only the download jail (runs `fetcher.py`), the attestation jail (the pinned `gh`) and the index git jail. The jail that extracts an AppImage, the only one that touches untrusted bytes with a program from the image, has no network (`jail.extract_args`), and neither has the app jail unless `network` is granted. So the shared network namespace is reachable only by code appjail ships or pins (stdlib `urllib`, `gh`, `git`) talking to GitHub.
- (Superseded 2026-10-20: the user approved pasta as an optional dependency and the network jails now use it, see the network bullets under "`add`".) A private netns would have needed a way out; without `pasta`/`slirp4netns` it would be a host-side CONNECT proxy with a host allowlist on a unix socket, plus an in-jail TCP relay for `git` and `gh` (neither speaks HTTP proxies over unix sockets). That is new code on the path of every download, for a defence against a bug in `urllib`/`git`/`gh` while they talk to GitHub. Judged not worth it now.
- Landlock (kernel ABI 6 is present in the guest, `landlock` is in the active LSM list): bwrap cannot apply it, so each jail's program would have to be wrapped by a launcher that calls `landlock_restrict_self` first. The filesystem rules duplicate what the mount namespace already enforces. The network rules (ABI 4+) only cover TCP bind/connect by port; they do not cover UDP or DNS and cannot name hosts, so "connect only to 443" adds nothing for the download jails and would break apps that need other ports. Abstract-socket and signal scoping (ABI 6) is already given by the unshared network and PID namespaces. Judged not worth it now.
- Revisit if: a network jail starts running third-party code, or a bwrap release gains Landlock support, or an allowlisting proxy is wanted for the app jail's own `network` permission (the one place where host filtering would be a real feature).
- seccomp for non-x86_64 is out of scope (see Platform: x86-64 only).

## Verification
Layers: the ordinary suite (`APPJAIL_INTEGRATION=1`, no downloads) runs in the guest and in GitHub Actions on every push; the opt-in suites (`APPJAIL_E2E=1` real downloads of approved repos, `APPJAIL_LIVE=1` live API metadata) run in the guest on demand and in the manual/weekly `e2e.yml` workflow. What is verified against real software, and what is not, is stated in each feature's section above.

Integration tests run inside a dedicated qemu-kvm guest (rebuilt from `tests/vm/create.sh`; see CLAUDE.md "Testing environment") (snapshot or throwaway disk) so downloads, extraction and jailed apps cannot affect the host. All tests, unit and integration, run in the guest. It needs bubblewrap, `unsquashfs`, user namespaces and a compositor (Wayland, or headless for non-GUI checks).

Test with 2-3 real GitHub AppImage repos:
- `add`, then `run`: confirm home is private and Documents are invisible.
- Tamper test: modify the pinned hash or the stored AppImage; `run` must refuse (`update` treats the changed digest as a new candidate and applies the quarantine).
- `index update` diff output with a changed `SITE=`.
