# appjail: design

appjail installs and runs AppImages in user mode: no sudo, one bubblewrap jail per app, full GUI support, pinned and verified downloads. This document specifies how it behaves. Why alternatives were rejected, and what is deferred, is in [DECISIONS.md](DECISIONS.md). Day-to-day project rules are in [CLAUDE.md](CLAUDE.md).

## Principles
1. Declarative manifests only (source, pinned hash, permissions). No shell, script or code from the network is ever sourced, evaluated or executed.
2. No self-update. The tool is updated by a reviewed `git pull` or a signed tag, and never fetches code to run.
3. The user names the one source of an app (a GitHub `owner/repo`, a URL, or a file). Update information embedded in an AppImage never decides the source.
4. Containment is the backstop: downloads run in a network-only jail, extraction in a jail without network, apps in a minimal-permission jail. Every permission the schema accepts is enforced; what cannot be enforced is refused, never ignored.
5. Evidence is explicit and never silently downgraded (trust tiers). An update is a reviewed diff, delayed by a quarantine.

Motivation: AM (ivan-hc/AM) self-updates and runs install scripts from `main` outside any sandbox, and almost none of its 8,700 scripts check a checksum or signature. About 95% of its apps are GitHub releases, which is what appjail targets.

Python 3, stdlib only (`tomllib`, `urllib`, `hashlib`, `subprocess`); the helpers it uses (bubblewrap, `unsquashfs`, `xdg-dbus-proxy`, `pasta`, `Xwayland`, `git`) are system packages.

## Platform
Linux on x86-64 only. Minimum supported systems: Debian 13 and Ubuntu 26.04. Older systems are not supported and get no workarounds. The seccomp filter is built for x86-64 and `run` refuses to start on another architecture rather than run unfiltered; the built-in catalog lists `x86_64` entries only. `network_host` needs Linux 6.12 or later with Landlock (ABI 6), which both minimum systems have; without it those apps are refused (see Runtime jail).

## Commands
| Command | Purpose |
|---|---|
| `search KW... [--limit N] [--all]` | Lookup in the local catalogs; suggestions only, never installs. |
| `add owner/repo` / `add --file PATH` / `add --url URL` | Resolve (or take), review, download, verify, pin, write the manifest. |
| `run APP [--dir PATH[:ro\|:rw]] [--file PATH[:rw]] [-- args]` | Start an app; the grants are for that run only. |
| `update [APP] [--prerelease] [--channel C] [--quarantine DAYS] [--file PATH] [--sha256 HEX] [--verify]` | Re-resolve, verify, show the diff, quarantine, install. |
| `list`, `remove APP`, `perms APP`, `history [APP]` | Inspect, delete, edit permissions, list recorded manifest changes. |
| `portals APP` | List and revoke document-portal grants. |
| `desktop APP`, `open APP -- FILE...` | Menu entry; open files in the jail. |
| `tools status\|install NAME` | Pinned helper binaries (`gh`, `dwarfs`). |
| `index add\|remove\|update\|rollback\|status` | Manage the catalogs `search` reads. |

## Trust tiers
Never silently downgraded; an update that would weaken the tier is blocked.
1. Build attestation (Sigstore / GitHub artifact attestations), verified against the exact bytes.
2. Pinned-key GPG signature. Not implemented (see DECISIONS.md).
3. Publisher hash: the GitHub per-asset `digest` matched the download.
4. Trust on first use.
5. Reserved for `add --file/--url` bytes with no external confirmation.

For `github:` apps the tiers are 1, 3 or 4: tier 4 is trust on first use of an asset with no digest, anchored by the pinned owner account id. For `add --file/--url` tiers 1-3 do not exist: tier 4 means `--sha256` was given and matched, tier 5 means trust on first use of the bytes alone. Most apps reach 3-4, which proves "unchanged, same account", not "safe".

### Attestation verification (`attest.py`, `snappy.py`, `tools.py`)
Tier 1 means a Sigstore build attestation covers the exact downloaded bytes and its certificate names this repository and GitHub Actions.
- Needs the opt-in helper `appjail tools install gh` (pinned GitHub CLI; size, sha256 and the executable's hash are in source; re-hashed before every use). Without it an existing attestation is shown as "present, cannot be verified" and the tier stays 3 or 4.
- appjail fetches the bundles (`github.Client.attestation_bundles`): the listing from api.github.com, then each bundle from the short-lived `*.blob.core.windows.net` URL (https only, 1 MiB cap, no credentials), decoded by a bounded stdlib Snappy decoder. Nothing from them is trusted until verified.
- `gh attestation verify --bundle` runs in a jail with network (it fetches the Sigstore trusted root) that sees only the subject, the bundles and a scratch directory. No token is passed. gh checks signatures, the transparency-log entry, the subject digest and that the identity belongs to `owner/repo`.
- appjail then re-reads the certificate: the issuer must be GitHub Actions, `sourceRepositoryURI` must equal the repository, and `sourceRepositoryOwnerIdentifier` must equal the pinned owner account id.
- Verification runs after the download, on the real bytes, so tier 1 is possible even without a GitHub digest. A failed verification never aborts an `add` (tier 3/4 with the reason shown). For an app already at tier 1 it blocks the update: no attestation on GitHub blocks before downloading; a bundle that does not verify aborts after it; nothing is installed.
- Limit: the identity is the repository and owner account, not a workflow or branch, so a compromised repository still gets tier 1. That is what the quarantine is for.

## Installing
### Resolver (`github.py`, `textsafe.py`)
- A client with an injectable transport. Per `add`: `/repos/{o}/{r}`, `/users/{o}` (owner age), `/releases/latest` (or the first non-draft of `/releases` with prereleases, or `/releases/tags/<tag>`), then one attestation lookup per chosen asset: 4 of the 60 unauthenticated requests per hour.
- `GITHUB_TOKEN` is optional and sent only to api.github.com. Redirects are followed by hand within that host (a moved repo sets `RepoInfo.renamed`); a redirect elsewhere is refused.
- Assets whose download URL is not under `https://github.com/{owner}/{repo}/releases/download/`, or whose name has odd characters, are dropped. The digest `sha256:<hex>` is parsed; null or another algorithm means "no digest".
- Selection: `.AppImage` suffix (case-insensitive); other architectures excluded by name token; explicit x86_64/amd64 names win over untagged ones; several candidates means the user is asked, none means abort. `.zsync` never matches. `asset_pattern` is suggested by replacing the release version in the chosen name with `*` and matched with `fnmatch`.
- Every untrusted string shown to the user passes `textsafe` (escape sequences and control characters stripped).
- Owner pinning: `add` records the owner's account id (`owner_id`); `update` blocks when it changes, which catches a repository deleted and re-registered under the same name. A manifest without an id gets a warning and the id is pinned once the user approves.
- Only GitHub is supported. A second forge would sit behind the same interface (`repo_info`, `latest_release`, assets with size and optional digest) and could reach tier 4 at best.

### `add owner/repo` (`cmd_add.py`, `jail.py`, `fetcher.py`)
`add owner/repo [--name N] [--prerelease] [--tag TAG] [--dir PATH[:ro|:rw]] [--dbus NAME] [--dbus-own NAME] [--allow network|network_host|portals|userns] [--portal NAME] [--no-audio] [--no-gpu] [--display wayland|xwayland] [--desktop [--mime TYPE] [--rw]]`. `--tag` pins a release: the manifest records the version and the channel `pinned`, so `update` leaves it alone.
1. Refuse early if the name exists. Show the review: owner, id, account age, stars, fork/archived/renamed warnings.
2. Resolve the release and select the AppImage. Show the digest and whether an attestation exists.
3. Ask before downloading. `fetcher.py` runs in the network-only jail (below). It follows only https redirects within github.com / *.githubusercontent.com and stops at the announced size.
4. On the host: the size must equal the announced size, the sha256 is computed, a GitHub digest must match, the file must be a type-2 AppImage (ELF + `AI\x02`). Any failure deletes the staging directory and writes nothing.
5. Verify the attestation when possible. Tier 1 if verified, 3 if there was a digest, else 4 with a warning.
6. Move the file to `~/.local/share/appjail/apps/<name>/app.AppImage`, extract it to `root/` (see Extraction), record `root.sha256` and `root.tree.sha256`, and write the manifest last. If extraction fails, nothing is kept. Defaults: audio and gpu on; network, portals and the rest off; Wayland.

Rolling tags (such as `continuous`) exist, so `update` compares hashes and publication times, never tags alone. Assets of a renamed repo live under the new canonical name, so release lookup uses `RepoInfo.full_name`.

### The network-only jail and pasta
The download and attestation jails (`jail.net_wrap`, run by `jail.run`) are bwrap jails with `--unshare-all --share-net --cap-drop ALL --clearenv --new-session --die-with-parent`, system directories and `/etc/ssl` read-only, the root remounted read-only and only a staging directory writable.
- The command runs inside a private network namespace made by `pasta` (package `passt`): `--config-net --no-map-gw`, no port forwarding either way, `--dns-forward 169.254.1.53`. `--share-net` then shares that namespace: outbound TCP/UDP works, the host's loopback and own addresses are unreachable. The jail gets a `resolv.conf` naming only the forwarder (the host's stub resolver is invisible there). Without pasta these jails fall back to the host network with a one-time warning.
- Not covered: other hosts on the LAN stay reachable. Attacks from an app against LAN hosts are outside the threat model; the goal is to keep apps off the user's own host services.
- The app jail's `network` permission uses the same mechanism (see Permissions).
- Extraction jails use `--unshare-net`.
- Every helper jail (these, extraction, icon conversion, the manifest-history git and the D-Bus proxy; `jail.common_args`) also gets `--unshare-user --disable-userns` and the app jail's seccomp filter without the `userns` grant (see Runtime jail). None of these programs needs a nested user namespace, and the `--appimage-extract` fallback runs the image's own code there. `jail.run` passes the filter as a memfd, or behind pasta, which closes inherited descriptors, as a private temp file opened inside its namespace.

### `add --file` / `add --url` (`cmd_addimage.py`, `cmd_updateimage.py`, `imagesrc.py`)
Installs an AppImage that is not a GitHub release. Principle 3 holds: the user names the one source; nothing embedded in the AppImage chooses it.
- `add --file PATH [--name N] [--sha256 HEX] [permission options]` and `add --url URL [--name N] [--sha256 HEX] [--max-size MIB] [permission options]`, exclusive with `owner/repo`. Permissions, `--dir`, defaults and jailed extraction are those of `add owner/repo`. `--name` defaults to the file name minus `.AppImage`, cleaned to the name pattern, and is shown for confirmation. Nothing is fetched or copied before the user confirms.
- Manifest `source` carries a kind prefix: `github:owner/repo`, `url:https://...`, `file:BASENAME` (base name only, never a path). `asset_pattern` and `owner_id` apply to `github:` only. `version` is `sha256:` plus 12 hex digits, `published_at` is the install time. A `url:` app has a `fingerprint` table (`size`, `etag`, `last_modified`, `chunks`). The parser rejects a `url:` that is not https, credentials in the URL, and keys that do not belong to the kind.
```toml
source = "url:https://example.org/dl/MyApp-x86_64.AppImage"
version = "sha256:1ccdd4decb46"
sha256 = "1ccdd4decb469fb4…"
evidence_tier = 5
fingerprint = { size = 48211968, etag = "\"abc123\"", last_modified = "Tue, 20 Oct 2026 08:00:00 GMT", chunks = "3f9a…" }
```
- Review before anything is fetched: for a URL the full URL (the final host after redirects is shown and recorded), for a file its real path, size and modification time; always the warning "no origin evidence". A `--sha256` mismatch aborts and deletes the staging directory.
- Local file: must be a regular file (a symlink is resolved and the target must be regular). It is copied into the staging directory, size and sha256 are computed on the copy, then the type-2 check and the install steps of `add`. The original is untouched.
- URL: downloaded by `fetcher.py` in the network-only jail; https start, no credentials. Redirects may go to any host and also to plain http; any http hop without a matching `--sha256` prints a warning and needs an extra confirmation. There is no announced size, so a hard cap applies (default 1 GiB, `--max-size`) and a `Content-Length`, when present, must equal the bytes received. The fetcher's redirect policy comes from the caller (GitHub hosts for `add owner/repo`, anything for `--url`), never from the server.

## Updating
`update [APP]` flow: resolve the new release; download in a throwaway jail and verify the evidence; show a diff (hashes, tier, permissions, release link); enforce the quarantine; ask the user; install. The manifest is rewritten and recorded in the history. Permissions are never changed by an update. A tier downgrade or an owner change blocks it.

- Without an app, every installed app is checked in name order (three API requests each, one more for a tier 1 app); one failure does not stop the others; the exit status is 1 if any was blocked or failed. A GitHub rate limit stops the whole run, and the rest are listed as "not checked (rate limited)".
- **Resolve:** `repo_info` on the pinned `source`, then the latest release (stable only unless `--prerelease`). The asset is the one `asset_pattern` selects (the user chooses if several match). A release published before the installed one is never installed, only reported.
- **Channel:** the top-level manifest key `channel` (omitted when `stable`). `add` writes `pinned` for `--tag` and `prerelease` for `--prerelease`. `update` never touches a pinned app, asks for pre-releases on a `prerelease` app, and `update APP --channel stable|prerelease|pinned` changes and saves the policy. `--prerelease` on `update` is a one-run override.
- **Up to date** means the GitHub digest equals the pinned sha256 (tier 3), or, with no digest (tier 4), the same tag and `published_at`.
- **Blocks** (no override, no download, no pending state): the owner account id differs from the pinned one; the tier would weaken (digest gone, attestation gone for a tier 1 app). To go on, `remove` and `add` again after checking the repository. **Cautions** (shown, not blocking): no `owner_id` pinned yet, repository renamed or transferred (the canonical name is recorded), repository archived.
- **Quarantine:** a candidate is identified by its GitHub digest, or by tag, publication time and size when there is none. The first time it is seen is stored in `apps/<name>/pending.json` (`key`, `tag`, `first_seen`). It can be installed once `first_seen` plus the delay (default 7 days; `--quarantine DAYS`; 0 disables with a warning) has passed. A different candidate, including a swapped asset in the same release when GitHub gives a digest, starts a new clock.
- **Tier 4 hash check:** with no GitHub digest nothing identifies the content, so the first waiting run asks to download the candidate in the network-only jail once, only to hash it, and stores the sha256 in `pending.json` (declining skips the check with a warning). When the quarantine ends, the download that would be installed must hash the same; otherwise nothing is installed (`CHANGED DURING QUARANTINE`, status blocked), the clock restarts and the new hash is recorded. Known limit: without that download, a tier 4 asset swapped in place without a new publication time is not seen.
- **Install:** confirm, jailed download (as in `add`), size and digest checks, AppImage check; for tier 4 the new sha256 is shown and confirmed again. The new image is extracted into staging first; only then are tree, image, marker and manifest replaced. A failure at any point restores the previous tree and image.
- **`url:` apps**, cheapest test first; each step ends the check or forces the full download: (1) conditional request with the stored `ETag` / `Last-Modified` (`304` = unchanged); (2) `Content-Length` from a `HEAD` (different size = changed); (3) ranged requests (`206`) for fixed windows: the SquashFS superblock, the middle 64 KiB and the last 64 KiB, hashed together and compared with `fingerprint.chunks` (about 200 KB; the first chunk alone is useless since every AppImage with the same runtime starts alike). All equal means unchanged; anything different, or no `206`, means one full jailed download after asking. The fingerprint detects a new version; it is not an integrity check, and a change confined to unsampled bytes is missed. A changed hash is a candidate keyed by its sha256 and goes through the quarantine; the candidate stays in `apps/<name>/pending.AppImage` and, at the end, a conditional request with its validators installs the stored copy on `304` without a second download. `--verify` forces a full re-download and comparison.
- **Tier rules for url/file:** a tier 4 app stays tier 4 only with `update APP --sha256 HEX` matching the new bytes; a plain `update` of a tier 4 app is refused with that hint. A tier 5 app given a matching `--sha256` becomes tier 4; without it, it stays tier 5.
- **`file:` apps:** a plain `update` says there is no source. `update APP --file PATH [--sha256 HEX]` replaces the image: hash diff, confirmation, jailed extraction, rollback on failure, no quarantine (the user holds the bytes). It exists because `remove` plus `add` would delete the private home.
- `list` shows name, version, source, tier, granted permissions, directories, dangling menu entries and any update seen. `remove APP [--yes]` deletes the manifest and the app directory including the private home, the menu entry, the document-portal grants and the portal decisions remembered for the app (see Portals); it asks first.

### Manifest history (`history.py`)
Every change `add`, `update` (install and `--channel`), `perms` and `remove` make to `~/.config/appjail` is committed to a local git repository there (author `appjail`). Manifests hold the pins and sit where any process of the user can write, so this is tamper evidence: `run` warns when a manifest differs from the last commit, and `history [APP] [--limit N]` lists the changes.
- git runs inside a no-network jail that sees only the config directory (`jail.local_git_args`), with user and system git configuration ignored and hooks, fsmonitor and signing disabled.
- Best effort: no git, or a config directory already inside another repository (a dotfiles repo), means no history and no error. Nothing is ever pushed. It detects edits made outside appjail, not an attacker who also rewrites `.git`.

## Manifest (`manifest.py`, `grants.py`, `valid.py`)
TOML, schema 1, one file per app at `~/.config/appjail/apps/<name>.toml`. Strict: unknown keys, wrong types, control characters and bad formats are errors. The writer is deterministic and atomic and refuses invalid manifests.
- Top level: `schema = 1`, `name` (`[a-z0-9][a-z0-9._-]{0,63}`), `source` (kind-prefixed), `channel`, `asset_pattern` (`github:` only; fnmatch, no `/`), `fingerprint` (`url:` only), `owner_id` (`github:` only), `version`, `sha256` (64 lowercase hex), `evidence_tier` (1-5), `published_at` (UTC `YYYY-MM-DDTHH:MM:SSZ`).
- `[permissions]` is optional and everything defaults to denied:
  - booleans: `network`, `network_host` (needs `network`), `audio`, `gpu`, `portals`, `userns` (`add` writes `audio` and `gpu` as true unless `--no-audio` / `--no-gpu`);
  - `display`: `wayland` (default) or `xwayland`;
  - `dbus_filter`: session-bus names the app may talk to (optional `.*` suffix); `dbus_own`: names it may own;
  - `portal_interfaces`: opt-in portal interfaces, only with `portals = true`;
  - `dirs`: absolute or `~/` paths, optional `:ro` / `:rw` (default read-only).
- `perms APP [--allow|--deny network|network_host|audio|gpu|portals|userns] [--add-portal N] [--rm-portal N] [--display D] [--add-dir PATH[:ro|:rw]] [--rm-dir PATH] [--add-dbus N] [--rm-dbus N] [--add-dbus-own N] [--rm-dbus-own N] [--yes]` shows the permissions, or shows before/after and asks before saving. `--add-dir` validates like `add --dir`.

## Extraction (`appimage.py`, `jail.py`)
- The AppImage is extracted and `AppRun` executed; it is never mounted (FUSE mounts do not work well in user namespaces). The AppImage runtime itself never runs outside a jail.
- Offset: end of the ELF runtime = `e_shoff + e_shentsize * e_shnum` (64-bit little-endian ELF only). `hsqs` there means SquashFS; `DWARFS` means DwarFS; anything else is unsupported.
- SquashFS: `/usr/bin/unsquashfs -no-progress -no-xattrs -p 2 -o <offset> -d /out/root /app.AppImage` in a jail with `--unshare-all`, a read-only root, the AppImage read-only and only the work directory writable. Needs the `squashfs-tools` package. Fallback, only with the user's consent asked before the download: a private copy runs `--appimage-extract` in the same jail. Like every helper jail it also gets `--disable-userns` and the seccomp filter (see The network-only jail and pasta).
- DwarFS: through the pinned helper `appjail tools install dwarfs` (explicit, asks first). The tool's URL, size and sha256 are constants in appjail's source; it is downloaded in the network-only jail, kept only if both match, stored in `~/.local/share/appjail/tools/`, re-hashed before every use, and run only in the extraction jail (no network, read-only root, `--skip-devices --skip-specials`), followed by the same tree validation. Moving to a newer dwarfs means editing the pin in a commit; appjail never fetches a helper on its own.
- Limits: the work directory is polled every 0.25 s; the jail is killed beyond 4 GiB of disk use or 500,000 entries, or after 15 minutes. The apparent size is checked afterwards, so sparse files cannot hide a huge tree.
- Host-side validation never follows symlinks: only regular files, directories and symlinks are allowed (fifos, sockets and devices reject the image); set-id and sticky bits are cleared; directories get owner access so the tree can always be deleted.
- `AppRun` must resolve, through relative symlinks only, to an executable regular file inside the tree; absolute symlinks, `..` above the root, loops and missing or non-executable targets reject the image.
- Extraction goes to `<root>.tmp` and is renamed on success, so a hostile image can fill only the work directory and cannot leave a partial `root`.

## Runtime jail (`runtimejail.py`, `runner.py`)
`run APP [-- app args]`.
- **Before every launch:** the stored AppImage must hash to the pinned `sha256` (otherwise "refusing to run"); the extracted tree is reused only if `root.sha256` matches and the tree still hashes to `root.tree.sha256` (paths, modes, contents, link targets), else it is re-extracted from the verified image with a warning.
- **Jail:** `--unshare-all` (no network unless `network`), `--die-with-parent --new-session --cap-drop ALL --clearenv --hostname appjail`, host system directories read-only, root remounted read-only, tmpfs `/tmp` and `/run`, `/proc`, a minimal `/dev`. The extracted tree is `/app` (read-only); a persistent private home `apps/<name>/home` is `/home/app`. Generated `/etc/passwd` and `/etc/group` hide host users; only fonts, ld.so, localtime and alternatives come from the host `/etc` (plus hosts, nsswitch, resolv and ssl when `network`).
- **Environment:** a fixed whitelist (HOME, PATH, LANG, TZ, XDG_RUNTIME_DIR, WAYLAND_DISPLAY, toolkit hints, `APPDIR=/app`); no host variable leaks, tokens included.
- **Wayland:** when the compositor offers `wp_security_context_v1` (sway, labwc, Mutter 46+, KWin 6.x; not weston 14), `run` creates a private listening socket and hands it to the compositor with engine `appjail` and the app name (`wayland.py`, a minimal hand-written wire protocol with fd passing); the compositor then hides its privileged protocols. Without the protocol `run` warns and binds the host socket. Either way the socket appears read-only as `$XDG_RUNTIME_DIR/wayland-0` and nothing else from the runtime directory is visible except what a permission binds (the Pulse socket, the filtered bus, the document portal). No X11 socket.
- **Audio:** the Pulse socket (`$XDG_RUNTIME_DIR/pulse/native`, served by `pipewire-pulse` on PipeWire systems) only when `audio`; PipeWire's own socket is never bound. PipeWire restricts only clients it recognises as sandboxed (a `.flatpak-info` in the client's root, which the app jail does not have, see Portals), so a jailed client on `pipewire-0` would be unrestricted: every node, cameras and other apps' screen casts included. The Pulse protocol carries audio only. Apps that speak only native PipeWire get no audio. Audio includes microphone capture: the server cannot restrict a client by device, so a separate `mic` permission would be a promise appjail cannot keep. Verified against a real PipeWire with a test video source (`tests/test_audio.py`).
- **GPU:** `/dev/dri`, `/dev/nvidia*` and the read-only `/sys` and Vulkan/GLVND data only when `gpu`. Supplementary groups survive in the jail, so group-owned render nodes stay usable.
- **Landlock (`landlock.py`):** every app jail that is not behind pasta runs in a Landlock domain scoped with `LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET` (ABI 6, Linux 6.12): no connection to an abstract unix socket created outside the jail. Sockets made inside it, such as the private Xwayland's, keep working. bwrap cannot apply Landlock, so a small wrapper (`python3 -I landlock.py bwrap ...`, a separate process rather than a `preexec_fn`, which is unsafe with threads) sets `no_new_privs`, enters the domain and execs bwrap. Only the scope is set, no filesystem or network rules. It matters for `network_host`, which shares the host's network namespace and so its abstract sockets: on a kernel without ABI 6 those apps are refused. Without `network` the jail's own network namespace already isolates them, and the scope is defence in depth. Behind pasta it is not applied: pasta's private namespace isolates abstract sockets, and pasta refuses to start its command under `no_new_privs`.
- **Seccomp (`seccomp.py`):** a hand-assembled classic BPF filter loaded by bwrap through `--seccomp` from a memfd (a private temp file behind pasta). Default allow; EPERM for the Flatpak-style deny list (kernel modules, kexec, `bpf`, `perf_event_open`, keyrings, `userfaultfd`, `ptrace`, `process_vm_*`, handle-based opens, NUMA policy, the `TIOCSTI`/`TIOCLINUX` ioctls, x32 ABI). Also as Flatpak: `socket` and `socketpair` only for `AF_UNSPEC`, `AF_UNIX`, `AF_INET`, `AF_INET6` and `AF_NETLINK` (others such as `AF_VSOCK`, `AF_TIPC`, `AF_ALG`, `AF_PACKET`, `AF_BLUETOOTH` get EAFNOSUPPORT), and `personality` only for `PER_LINUX` and the query value (no turning off ASLR or making data executable for child programs). The `io_uring` calls answer ENOSYS, so libraries fall back to ordinary I/O: a large kernel attack surface few desktop apps need. The syscall table is checked against the kernel's `unistd_64.h`. The helper jails get the same filter.
- **Nested user namespaces:** denied by default (`--unshare-user --disable-userns`, plus the filter: `unshare`, `setns`, `clone` with any CLONE_NEW* flag, the mount API and `pivot_root`/`chroot` fail; `clone3` answers ENOSYS so libc falls back to `clone`). The `userns` permission lifts exactly that for Electron/Chromium sandboxes and nested bwrap; the always-denied list still applies. `perms` warns when it is granted.
- **Lifetime (`runner._wait_group`):** the app runs in its own session. SIGINT, SIGTERM and SIGHUP sent to appjail are forwarded to the whole process group, which is killed when the app ends (killing `pasta` alone would leave the jail running, since `--die-with-parent` does not follow pasta's namespace helper). SIGKILL of appjail cannot be caught: without pasta the jail dies with its parent; behind pasta, `jail.Lifeline` gives the launcher a FIFO it holds open, and a watcher in the namespace reads it and, at end-of-file, runs `kill -KILL -1` only when it is pid 1 of a private pid namespace. The launcher's pid cannot be polled instead (pasta's namespace has its own `/proc`). Residue after a SIGKILL: an empty `appjail-life-*` directory in `XDG_RUNTIME_DIR`. Not applied to the short-lived download, attestation and index jails.

## Permissions
### Directories and files
Files are isolated by default. The app sees the host system directories read-only, its own tree, a private writable home, and empty tmpfs `/tmp` and `/run`. It does not see the real home, Documents, other apps, appjail's data or manifests, or any host file not granted. An app can be given specific directories, never the whole home.
- Manifest `dirs = ["~/Documents/notes", "~/Pictures:rw"]`: `~/x` appears as `/home/app/x`; absolute paths outside the home appear at the same path; read-only unless `:rw`.
- `add --dir PATH[:ro|:rw]` (repeatable): the path must exist, is normalised (home becomes `~/`) and is checked before any network access. `run APP --dir PATH[:ro|:rw]`: for that run only, announced as "Temporary access for this run". `perms APP --add-dir / --rm-dir` edit the grants later.
- **Sensitive paths** are refused in every mode, at parse time and again at launch on the symlink-resolved path (`grants.sensitive_reason`): credential stores (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.kube`, keyrings, `.git-credentials`, `.pki`), shell and tool history files, browser profiles, mail, `~/.var`, files named like password databases or private keys (`*.kdbx`, `*.key`, `*.pem`, ...), the broad `~/.config`, `~/.local`, `~/.local/share`, `~/.cache`, and system trees (`/etc`, `/dev`, `/proc`, `/sys`, `/run`, `/usr`, `/boot`, `/root`, ...). Read-write is also refused where it could plant code that runs outside the jail (`~/.local/bin`, `~/.config/autostart`, `~/.config/systemd`, `~/.local/share/applications`, shell and editor startup directories). There is no override: grant a subdirectory.
- Also refused: `/`, the home directory or any parent of it, `..` components, appjail's own data and config trees (and parents/children), and missing paths. Symlinks are resolved when the jail starts, so a link cannot redirect a grant afterwards.
- **Shared temporary directories** (`/tmp`, `/var/tmp` and everything below them) are refused as directory grants, at parse time and at launch on the resolved path (`grants.directory_reason`). Every program keeps its unix sockets there (the X server's `/tmp/.X11-unix`, tmux's server socket, agents), and a bind mount does not stop `connect()`, even read-only: the app could drive those programs from inside the jail. A single regular file there can still be opened (`run --file`, `open`): it carries no socket.
- `run APP --file PATH[:rw]` (repeatable) binds just that file for that run (`runtimejail.file_binds`): read-only unless `:rw`, nothing else from its directory is visible, and the in-jail path is appended to the app's arguments. Only regular files; the path is resolved first; the sensitive-path policy applies, plus `PERSIST_HOME_FILES` (`.bashrc`, `.profile`, `.gitconfig`, ... never read-write). Not persisted. Apps that save by write-and-rename fail on `:rw` (a bind-mounted file cannot be replaced); the portal file chooser exists too.

### Network
- No network by default. `network` runs the app in the pasta namespace like the download jails (`runner.launch` wraps the command with `jail.net_wrap(required=True)`, DNS through the forwarder): the internet is reachable, the host's loopback services and own addresses are not. Without pasta the app is refused, never silently put on the host network; the same refusal happens earlier when the permission is granted (`permargs.require_network_isolation`).
- `network_host` (needs `network`; `--allow network_host` implies `network`; `--deny network` clears it) keeps the host network namespace and `resolv.conf` for apps that need host services; `add` and `perms` warn when it is granted. The shared namespace would also carry the host's abstract unix sockets (the X server's `@/tmp/.X11-unix/X0` among them); Landlock keeps the app off them (see Runtime jail), and without Landlock ABI 6 `network_host` is refused when it is granted and when the app starts.
- pasta closes every inherited descriptor, so bwrap's are opened inside the namespace: the seccomp filter in a private 0600 temp file, the portal handshake over two FIFOs in a private temp directory, opened by `/bin/sh -c 'exec "$@" 9<filter 8>status 7<block'` (`jail.net_wrap(fd_files=...)`, `runner.Pipes`; one digit only, dash accepts no more). pasta runs the command as uid 0 of a user namespace mapped to the host user, so the jail passes `--uid`/`--gid` to restore the real ids (passwd, D-Bus authentication and file ownership depend on them). IPv6 is forwarded by pasta when the host has a route.
- An allowlisting proxy for the LAN is not planned.

### Xwayland (`runtimejail.xwayland_command`)
`display = "xwayland"` is for X11-only apps. The host X11 socket is never bound (it would expose every other X client's keystrokes and screen). The app command is wrapped by a short `sh` script that starts a rootless `Xwayland` inside the jail as a client of the restricted Wayland socket, with `-nolisten tcp` and `-displayfd`, then sets `DISPLAY` and execs the app.
- The X socket lives in the jail's private `/tmp` and abstract namespace, so no other app and no host X server is reachable. With `network_host` the abstract namespace is the host's: Landlock then refuses connections to sockets created outside the jail, including the host X server's, while the private Xwayland, started inside the jail, stays reachable. The environment has no `WAYLAND_DISPLAY` and selects X11 toolkits (`GDK_BACKEND=x11`, `QT_QPA_PLATFORM=xcb`, `SDL_VIDEODRIVER=x11`, ...). Xwayland dies with the jail.
- The script waits up to 20 s for Xwayland to report its display and gives up at once, with a message, if Xwayland exits. Needs `/usr/bin/Xwayland` (package `xwayland`); `run` stops with a clear message when it is missing. With no window manager, windows map as plain toplevels.
- Not verified: GPU acceleration through Xwayland (glamor).

### D-Bus (`dbusproxy.py`)
`dbus_filter` lists the session-bus names the app may talk to, such as `org.freedesktop.Notifications` or `org.mpris.MediaPlayer2.*`. `add --dbus NAME` (repeatable), `perms --add-dbus / --rm-dbus`.
- Empty list: the jail has no bus at all (no `DBUS_SESSION_BUS_ADDRESS`, no socket).
- Otherwise `run` starts `xdg-dbus-proxy` on the host side inside a bwrap jail of its own: no network, read-only system, and only the real bus socket (read-only) and a private directory `$XDG_RUNTIME_DIR/appjail-XXXX` for the new socket. The proxy runs `--filter` with one `--talk=NAME` per entry; every other name is invisible and every other call is answered with an error by the proxy. The app jail binds only the proxy socket as `$XDG_RUNTIME_DIR/bus`. The real bus is never visible.
- `run` waits 5 s for the proxy's ready byte, and stops the proxy and removes its directory when the app exits or `run` fails; the proxy also dies with appjail. The host address must be `unix:path=...` (from `DBUS_SESSION_BUS_ADDRESS`, else `$XDG_RUNTIME_DIR/bus`); abstract and TCP are refused. Needs `xdg-dbus-proxy`.
- Refused when the manifest is loaded and when typed: `org.freedesktop.DBus`, `org.freedesktop.systemd1`, `org.freedesktop.Flatpak`, `org.freedesktop.portal*`, `org.freedesktop.impl*`, `org.gnome.Shell`, `org.gnome.SessionManager`, `org.kde.KWin`, `org.kde.klauncher*`, any wildcard covering them, and wildcards with fewer than three name parts before `.*`. Names exposing stored secrets (`org.freedesktop.secrets`, keyring, kwallet) are allowed with a warning.
- Owning a name (MPRIS, single-instance) is `dbus_own`, passed as `--own=NAME` (`add --dbus-own`, `perms --add-dbus-own / --rm-dbus-own`; each owned name is warned about). Names in the desktop namespaces (`org.freedesktop.`, `org.gnome.`, `org.kde.`, `org.a11y.`, `com.canonical.`, `org.ayatana.`) cannot be owned, so an app cannot impersonate the notification daemon, secret service or polkit; the exception is status-notifier item names. The proxy matches only a trailing `.*`, so a `-<pid>` suffix as in `org.kde.StatusNotifierItem-1234-1` is not expressible.
- Not verified: real desktop services (notification daemon, MPRIS players).

### Portals (`portal.py`, `dbusproxy.py`, `runner.py`, `cmd_portals.py`)
`portals = true` gives the app the desktop portals (file chooser, notifications, settings, ...) through the same filtering proxy; the app never sees the real bus.
- **Identity:** xdg-desktop-portal identifies the caller by reading `/proc/<pid>/root/.flatpak-info` of the D-Bus peer and `$XDG_RUNTIME_DIR/.flatpak/<instance>/bwrapinfo.json`. That is the only sandbox identity it understands besides Snap and Linyaps, so appjail writes it: a compatibility shim; nothing depends on or installs Flatpak. The app id is `app.appjail.<name>`, one per name (`portal.app_id`): it is the portal's whole notion of who the app is, so two apps must never share it. Each dot-separated part of the name is escaped: `_` becomes `_u`, `-` becomes `_h`, an empty part becomes `_e`, and a part starting with a digit gets a leading `_` (`my-app` is `app.appjail.my_happ`, `7zip` is `app.appjail._7zip`; plain names keep their spelling). The identity file is bound into the proxy's jail (the proxy connection is the peer the portal sees), never into the app's, so the app cannot read or forge it, and cannot pick its own id (the alternative, `org.freedesktop.host.portal.Registry`, lets an app claim any id that has a `.desktop` file). `bwrapinfo.json` carries the app jail's init pid from bwrap's `--json-status-fd`; `--block-fd` holds the app back until the file exists.
- **Side effects:** the permission store and the Background portal treat the app as a Flatpak app (an autostart entry would say `flatpak run`, inert without Flatpak). Document-portal paths are `<XDG_RUNTIME_DIR>/doc/<id>/<name>`; the per-app view `doc/by-app/<app id>` is bound at `/run/user/<uid>/doc` (and at the host runtime path too if it differs).
- **Interfaces:** `portals = true` allows only the safe set (`grants.PORTAL_SAFE`: FileChooser, Notification, Settings, Trash, Print, Inhibit, NetworkMonitor, ProxyResolver, Secret, Realtime, MemoryMonitor, PowerProfileMonitor) plus the document portal. Privileged interfaces must be named in `portal_interfaces` (`grants.PORTAL_OPT_IN`: OpenURI, Email, Screenshot, ScreenCast, RemoteDesktop, GlobalShortcuts, InputCapture, Camera, Location, Account, Wallpaper, Background, Usb); `add` and `perms` warn for each (`--portal NAME`, `--add-portal`, `--rm-portal`). `Flatpak` (spawn on the host) and `DynamicLauncher` (installs launchers) are refused. Everything else on the portal's name is invisible (`--call` rules per interface; unknown calls get AccessDenied from the proxy).
- **Document portal:** D-Bus activated; if `doc/by-app/<id>` is missing, `run` asks the bus to start it (`dbus-send`, GetMountPoint) and otherwise stops with a clear message. It needs FUSE.
- **Revoking:** `portals APP [--revoke DOC_ID]... [--revoke-all] [--yes]` lists the documents granted to `app.appjail.<name>` (host permission store, read with `dbus-send`) and revokes them through `org.freedesktop.portal.Documents.RevokePermissions` on the host side. Revoking only in the store is not enough: the portal keeps serving the file until the call removes the per-app view. The app's own recent-files list is untouched. `remove` revokes the grants too, and also deletes the app id's entries from the portal's other permission-store tables (`portal.STORE_TABLES`: device access such as the camera, location, screenshot, background, screen-cast restore tokens, chosen URI handlers, ...), so a later app with the same name starts with no remembered decision. The store cannot list its tables, so the list follows xdg-desktop-portal 1.20; a table a system does not use is empty.
- Not verified: the GNOME, KDE and wlr backends, and interactive dialogs. Desktops differ in which interfaces they implement; each privileged interface depends on its backend asking the user.

## Menu entry and opening files (`desktop.py`, `cmd_desktop.py`, `cmd_open.py`)
`desktop NAME [--mime TYPE]... [--mime-all] [--rw] [--yes]`, `--remove`, `--prune`; `add ... --desktop [--mime ...]`; `open NAME [--rw] -- FILE...`. The AppImage's own `.desktop` is untrusted (its `Exec`, `Actions`, `TryExec` and `MimeType` would act outside the jail), so appjail generates the entry and never copies that file. It is written by the host-side CLI to `${XDG_DATA_HOME:-~/.local/share}/applications/appjail-<name>.desktop`; only files carrying the `X-Appjail-App=<name>` marker are ever replaced or deleted.
- **Fields:** from the top-level `*.desktop` of the tree (regular file, no symlink following, 64 KiB cap) only `Name`, `Comment`, `GenericName`, `Categories`, `Keywords` (unlocalised, through `textsafe.clean`, one line, length caps, charset check for `Categories`) are kept. `Name` gets the suffix ` (appjail)` so an app cannot pose as a host app. `Exec=<absolute appjail> run <name>` (quoted per the spec, `%` doubled, no field codes), `Terminal=false`.
- **Icon:** `Icon=` or `.DirIcon` resolved with `appimage.resolve_entry(..., executable=False)` (no escape from the tree). PNG: signature, IHDR, square 16..1024 px, 1 MiB cap, installed as `icons/hicolor/<WxH>/apps/appjail-<name>.png`. SVG: rendered to 256 px by `rsvg-convert` inside a no-network jail (the host never decodes an SVG), then validated like any PNG. No converter: no icon, a one-line note.
- **File types** (`MimeType`) are opt-in and advertise-only: nothing is registered unless the user picks types (`--mime`, `--mime-all`, or the interactive list); only types the app declares and that pass the filter can be picked. The filter drops anything not `type/subtype` in lowercase, `x-scheme-handler/*`, `inode/*`, executables, shell and script-language types, AppImage and installer types, duplicates, and everything beyond 32. appjail never writes `mimeapps.list`. With types, the entry runs `appjail open <name> [--rw] -- %F`.
- **`open`:** each file is bound alone into the jail like `run --file`: read-only unless `--rw` (baked into the Exec by `desktop --rw`; the manifest is unchanged), sensitive-path policy applies, URLs and non-regular files are refused. The mode is always spelled out (`:ro`/`:rw`) so a file named `x:rw` cannot raise its own mode. No file after `--` is a plain start. Errors also go to `notify-send` when present. Choosing the file is the consent.
- **Lifecycle:** `remove` deletes the entry and icons and refreshes the cache (`update-desktop-database`; a missing tool is a note); a default left in the user's `mimeapps.list` is only reported. `update` regenerates an existing entry, keeps the types the app still declares, drops the others and only lists newly declared types. Dangling entries (app directory removed by hand): `list` flags them, `desktop --prune` deletes them, and `open` of a removed app deletes its own entry.
- Out of scope: default applications, URL handlers, `%u`, per-type actions, drag and drop of unrelated types.

## Index and search (`catalog.py`, `indexstore.py`, `index.py`, `cmd_index.py`)
The index is a derived catalog, not a copy of the AM repository, and further sources can provide catalogs in the same format. The built-in catalog is built elsewhere (the sister project appjail-db, from the AM index and the AppImageHub feed, merged without duplicates); appjail reads neither itself. It only affects `search`; installed apps never depend on it.
- **Format** (`catalog.py`; user documentation in README "Search"): one JSON document `{"format": "appjail-catalog", "version": 1, "origin"?, "revision"?, "apps": [{"name", "description"?, "source"?, "note"?}]}`. Strict: unknown keys, a wrong version, duplicate names, a bad `source`, names outside `[A-Za-z0-9][A-Za-z0-9._+-]{0,80}`, more than 50,000 apps or 16 MiB refuse the whole catalog. Texts are cleaned of terminal escapes and cut (description 300, note 200, origin and revision 300). What is stored is `catalog.dumps(catalog.parse(text))` (deterministic, apps sorted), never the downloaded bytes. The format stays version 1 until 0.3.0; a bare `owner/repo` source is refused.
- **Source grammar:** `source` is the manifest's `kind:target` string. Kinds: `github:owner/repo`, `gitlab:HOST/group[/sub...]/project` (host always explicit), `forgejo:HOST/owner/repo`, `codeberg:owner/repo` (normalized to `forgejo:codeberg.org/owner/repo`), `url:https://...`. `file:` is refused. Hosts are lowercased DNS names without port or credentials; syntax only, nothing is contacted. Only `github:` and `url:` can be installed; the others are information (`search` prints the matching `appjail add` command only for those). The update review compares `catalog.identity` (kind, host, owner, case-folded): another kind, host or owner is an owner change (loud warning), the same owner with another repository an ordinary source change. There is no forge alias table: a catalog cannot redefine what a host name means.
- **Sources** (`indexstore.py`): the built-in `appjail-db` plus any added with `index add NAME --url https://... | --file PATH`. Layout under `~/.local/share/appjail/index/`: `sources.json`, and per source `current.json`, `previous.json`, `state.json` (sha256, revision, update time of both). A `file` source stores the path and re-reads it at `index update`. Every file is replaced atomically and `current.json` is never moved, so a crash leaves a readable catalog; `index update` first removes the temp files an interrupted update left behind. Source names match `[a-z0-9][a-z0-9._-]{0,31}`; `appjail-db` is reserved and cannot be removed. The state of a snapshot may also hold `commit`, the appjail-db commit it was fetched at.
- **Built-in source (appjail-db):** the kind `repo`, `github:alberto743/appjail-db`. `index update` asks the GitHub API for the commit the default branch points to (`github.Client.head_commit`; one unauthenticated request, a rate limit or API error fails the update without falling back to an unpinned URL), then downloads `https://raw.githubusercontent.com/alberto743/appjail-db/<commit>/catalog.json` exactly as a URL source is downloaded (network-only jail, 16 MiB cap) and runs it through `catalog.parse`. `--commit` takes only 40 lowercase hex digits and skips the API request; it applies to the built-in source only. The commit is shown in the review and recorded in the snapshot's state (and in `index status`), so the catalog in use can be traced to an exact state of appjail-db and an older one fetched again. The catalog itself is made by appjail-db, weekly, from the AM index and the AppImageHub feed (descriptions cut to 100 characters, size and shrink checks); appjail reads neither. An app whose name is the same in both but whose repositories differ has no `source` and a `note` naming both (`resolve manually: ...`). The catalog's own `revision` names the AM commit and the AppImageHub feed hash it was built from and is informational. A commit is not a signature: the catalog is unsigned, and the controls are HTTPS, who can write to appjail-db, the strict parser and the diff review.
- **URL and file sources:** a URL is downloaded by `jail.download_url` (https start, 16 MiB cap, redirects as for `add --url`; a plain-http hop is warned about); a file must be a regular file within the cap. Both go through `catalog.parse`. There is no hash pin: the safeguards are the strict parser, the diff review at every update and the previous catalog kept for rollback.
- **Review** (`cmd_index.review_and_install`): app count, size, revision, the appjail-db commit (built-in source) and a sha256 prefix; for an update the apps added and removed and every app whose `source` changed, an owner change as a loud warning, and nothing replaces the current catalog before the user agrees (default no). An identical catalog is reported without a prompt. A new source is registered only after the user accepted its first catalog. `index update` without a name does every source; one failure does not stop the others and makes the status 1. `rollback` swaps current and previous (so it can be undone).
- **Search:** `search KEYWORD... [--limit N] [--all]` reads the current catalog of every source; with several sources each hit shows its source in brackets. Every keyword must occur (case-insensitive) in the name or description. Ranking: exact name, name prefix, all keywords in the name, any keyword in the name, description only; then alphabetical, then source name. A `note` is shown in brackets.

## Graphical front end (`gui/`)
`appjail-gui` (or `python -m appjail.gui`) opens a tkinter window; it needs the system package `python3-tk` and a display, and prints a one-line message without them. Tabs: Apps (the installed apps from their manifests; run, run with extra access for one run, open file, update with its options, permissions, portals, history, menu entry, remove), Add (GitHub, URL or file, with every grant and menu-entry option of `add`; options the CLI refuses for the chosen source are greyed out), Search (`search` and `index`), Tools (helpers, version, list, prune). One output pane shows what the commands print. Options of a command that has many (`update`, `run`, `desktop`, `portals`) are set in a small form that only builds the argv.
- **One implementation:** every action builds an argv (`gui/argv.py`) and runs `cli.main` on a worker thread with `GuiConsole` (`gui/console.py`), a `Console` whose output goes through `textsafe` into a queue and whose prompts are answered by modal dialogs on the Tk thread. Closing a dialog cancels the command.
- **File types at add time:** the types an app declares are known only after the install. With "Create menu entry" on and no types (or "all") given, the window adds without `--desktop` and then runs `desktop NAME` for the new app, which lists the declared types and asks. The "Files writable" box adds `--rw` to the add or to that follow-up; the default stays read-only.
- **Consent:** every prompt (confirmation, free text, list choice) shows the lines the command printed just before it (the review: before/after permissions, release details, the file types on offer); confirmations default to No and take the keyboard focus on No. The GUI never adds `--yes`; the permissions editor only computes the `perms` options and the command asks.
- **Running apps:** `run` and `open` start `python -m appjail` in its own session, so closing the window does not end the app. A file chosen in the dialog is bound read-only, like the menu entry.
- **Text:** everything shown passed `textsafe.clean`; network text is never put into a widget directly.
- **Menu entry of appjail-gui:** `appjail-gui --desktop` writes `${XDG_DATA_HOME:-~/.local/share}/applications/appjail.desktop` (the name cannot collide with an app entry, which is `appjail-<name>.desktop`) and copies the SVG shipped in the package (`gui/appjail.svg`, trusted, so not converted) to `icons/hicolor/scalable/apps/appjail.svg`. The entry carries `X-Appjail-GUI=true`; only a regular file with that marker is replaced or deleted by `--desktop` and `--remove-desktop`, a symlink or foreign file never. `Exec` is the installed `appjail-gui`, or the running interpreter with `-m appjail.gui`. Neither flag needs a display or tkinter (a missing tkinter is a note).

## Verification strategy
- The ordinary suite (`APPJAIL_INTEGRATION=1`, no downloads) runs in a dedicated qemu-kvm guest and in GitHub Actions on every push. Opt-in suites run on demand and in the manual/weekly `e2e.yml` workflow: `APPJAIL_E2E=1` (real downloads of user-approved repositories), `APPJAIL_LIVE=1` (live API metadata). All execution happens in the guest or on CI runners, never on the developer's host (see CLAUDE.md).
- Verified against real software: `add` and `run` of real AppImages (SquashFS and DwarFS), tier 3 and tier 4 downloads and the quarantine hash, Sigstore verification with the real `gh`, the private Xwayland with an X11-only app, a GUI app with `network` behind pasta, the real xdg-desktop-portal frontend with a fake backend and with the GTK backend (non-interactive calls), the real `xdg-dbus-proxy`, the menu entry through `gio`, the real appjail-db catalog, a real PipeWire and pipewire-pulse (`tests/test_audio.py`: Pulse reachable, the camera not), the real permission store (an app's entries forgotten on `remove`), and Landlock ABI 6 on Linux 6.12 (an outside abstract socket refused, the private Xwayland still reachable).
- Tamper tests: modifying the pinned hash, the stored AppImage or the extracted tree makes `run` refuse; a changed digest on `update` is a new candidate under the quarantine.
- Not verified: the GNOME, KDE and wlr portal backends, IPv6 on a real internet route (covered only by a fake network), GPU acceleration through Xwayland, tray icons with `-<pid>` bus names, real desktop D-Bus services.
