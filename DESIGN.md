# appjail: design

appjail installs and runs AppImages in user mode: no sudo, one bubblewrap jail per app, full GUI support, pinned and verified downloads. This document specifies how it behaves. Why alternatives were rejected, and what is deferred, is in [DECISIONS.md](DECISIONS.md). Day-to-day project rules are in [CLAUDE.md](CLAUDE.md).

## Principles
1. Declarative manifests only (source, pinned hash, permissions). No shell, script or code from the network is ever sourced, evaluated or executed.
2. No self-update. The tool is updated by a reviewed `git pull` or a release, and never fetches code to run.
3. The user names the one source of an app (a GitHub `owner/repo`, a URL, or a file). Update information embedded in an AppImage never decides the source.
4. Containment is the backstop: downloads run in a network-only jail, extraction in a jail without network, apps in a minimal-permission jail. Every permission the schema accepts is enforced; what cannot be enforced is refused, never ignored.
5. Evidence is explicit and never silently downgraded (trust tiers). An update is a reviewed diff, delayed by a quarantine.

Motivation: AM (ivan-hc/AM) self-updates and runs install scripts from `main` outside any sandbox, and almost none of its install scripts check a checksum or signature (see DECISIONS.md). About 95% of its apps are GitHub releases, which is what appjail targets.

Python 3, stdlib only (`tomllib`, `urllib`, `hashlib`, `subprocess`); the helpers it uses (bubblewrap, `unsquashfs`, `xdg-dbus-proxy`, `pasta`, `Xwayland`, `openbox`, `git`, `rsvg-convert`, `gtk-update-icon-cache`, `update-desktop-database`, `dbus-send`, `notify-send`, and for the private audio graph `pipewire`, `wireplumber`, `pipewire-pulse` and `pw-dump`) are system packages; `/usr/bin/python3` also runs the `linger` supervisor inside the jail.

## Platform
Linux on x86-64 only. Minimum supported systems: Debian 13 and Ubuntu 26.04. Older systems are not supported and get no workarounds. bubblewrap 0.10 or later is required (`--bind-fd`, see Directories and files); both minimum systems have it. The seccomp filter is built for x86-64 and `run` refuses to start on another architecture rather than run unfiltered; the built-in catalog lists `x86_64` entries only. `network_host` needs Linux 6.12 or later with Landlock (ABI 6), which both minimum systems have; without it those apps are refused (see Runtime jail).

## Manifest (`manifest.py`, `grants.py`, `valid.py`)
TOML, schema 1, one file per app at `~/.config/appjail/apps/<name>.toml`. Strict: unknown keys, wrong types, control characters and bad formats are errors. The writer is deterministic and atomic and refuses invalid manifests. `name` must match the file name.
- App names match `[a-z0-9][a-z0-9._-]{0,63}` and are used as path components, so every command that takes an app name (`run` and `update` included) checks it with `manifest.check_name` before using it.
- Top level: `schema = 1`, `name` (`[a-z0-9][a-z0-9._-]{0,63}`), `source` (kind-prefixed), `channel` (`github:` only), `asset_pattern` (`github:` only; fnmatch, no `/`), `fingerprint` (`url:` only), `owner_id` (`github:` only), `version`, `sha256` (64 lowercase hex), `evidence_tier` (1-5), `published_at` (UTC `YYYY-MM-DDTHH:MM:SSZ`).
- `[permissions]` is optional and everything defaults to denied:
  - booleans: `network`, `network_host` (needs `network`), `audio`, `mic` (needs `audio`), `gpu`, `camera`, `portals`, `userns`, `linger`, `full_wayland` (see Runtime jail, Wayland) (the writer always writes `network`, `audio`, `gpu`, `portals` and `userns`, and the others only when true; a key missing from a hand-written manifest means denied);
  - `audio_mode`: `pipewire` (default) or `pulse`, written only when `pulse`: how `audio` and `mic` are provided (see Audio);
  - `display`: `wayland` (default), `xwayland`, `xwayland-rootful` or `none` (a headless app: no Wayland socket, no X server, none of the display variables; `desktop` refuses it, since an entry would start it invisibly); `display_size` (`WxH`, 320 to 8192 each, default `1280x800`, written only when it differs) is the window of the latter;
  - `dbus_filter`: session-bus names the app may talk to (optional `.*` suffix); `dbus_own`: names it may own;
  - `portal_interfaces`: opt-in portal interfaces, only with `portals = true`;
  - `dirs`: absolute or `~/` paths, optional `:ro` / `:rw` (default read-only).
- `perms APP [--allow|--deny network|network_host|audio|mic|gpu|camera|portals|userns|linger|full_wayland] [--audio-mode pipewire|pulse] [--add-portal N] [--rm-portal N] [--display D] [--display-size WxH] [--add-dir PATH[:ro|:rw]] [--rm-dir PATH] [--add-dbus N] [--rm-dbus N] [--add-dbus-own N] [--rm-dbus-own N] [--yes]` shows the permissions, or shows before/after and asks before saving. `--add-dir` validates like `add --dir`.

## Trust tiers
Never silently downgraded; an update that would weaken the tier is blocked.
1. Build attestation (Sigstore / GitHub artifact attestations), verified against the exact bytes.
2. Pinned-key GPG signature. Not implemented (see DECISIONS.md).
3. Publisher hash: the GitHub per-asset `digest` matched the download.
4. Trust on first use.
5. Reserved for `add --file/--url` bytes with no external confirmation.

For `github:` apps the tiers are 1, 3 or 4: tier 4 is trust on first use of an asset with no digest, anchored by the pinned owner account id. For `add --file/--url` tiers 1-3 do not exist: tier 4 means `--sha256` was given and matched, tier 5 means trust on first use of the bytes alone. Most apps reach 3-4, which proves "unchanged, same account", not "safe".

### Attestation verification (`attest.py`, `snappy.py`, `tools.py`)
Tier 1 means a Sigstore build attestation covers the exact downloaded bytes and its certificate names this repository and GitHub Actions.
- Needs the opt-in helper `appjail tools install gh` (pinned GitHub CLI; size, sha256 and the executable's hash are in source; re-hashed before every use). Without it an existing attestation is shown as "present, cannot be verified" and the tier stays 3 or 4.
- appjail fetches the bundles (`github.Client.attestation_bundles`): the listing from api.github.com, then each bundle from the short-lived `*.blob.core.windows.net` URL (https only, 1 MiB cap, no credentials), decoded by a bounded stdlib Snappy decoder. Nothing from them is trusted until verified.
- `gh attestation verify --bundle` runs in a jail with network (it fetches the Sigstore trusted root) that sees only the subject, the bundles and a scratch directory. No token is passed. gh checks signatures, the transparency-log entry, the subject digest and that the identity belongs to `owner/repo`.
- appjail then re-reads the certificate: the issuer must be GitHub Actions, `sourceRepositoryURI` must equal the repository, and `sourceRepositoryOwnerIdentifier` must equal the pinned owner account id.
- Verification runs after the download, on the real bytes, so tier 1 is possible even without a GitHub digest. A failed verification never aborts an `add` (tier 3/4 with the reason shown). For an app already at tier 1 it blocks the update: no attestation on GitHub blocks before downloading; a bundle that does not verify aborts after it; nothing is installed.
- Limit: the identity is the repository and owner account, not a workflow or branch, so a compromised repository still gets tier 1. That is what the quarantine is for.

## Output conventions (`console.py`)
- Results go to stdout. Warnings are `! warning: …` on stdout, so they stay beside the step that caused them. Errors are `error: …` on stderr (a plain `cancelled` has no prefix); the exit status is 1 (130 after Ctrl-C, 2 for a usage error).
- Detail blocks are label/value lines aligned by `Console.kv`, tables are `Console.table` (columns with no content are dropped, cells are cleaned and cut), bullets are `Console.item`. An `update` prints a `== app ==` header per app and, for several apps, ends with an APP/RESULT table.
- `--json` on `list`, `search` and `index status` prints one JSON document (ASCII only) on stdout and nothing else; `list --json` always includes the permissions, and an unreadable manifest gives an object with `error`. Only these three commands have `--json`.
- Every line goes through `textsafe` first. Colour is added only to the fixed `warning:`/`error:` prefixes, only on a terminal, and not when `NO_COLOR` is set or `TERM=dumb`. Bullets (`•`) and arrows (`→`) are always Unicode. On a terminal, long warnings, notes and values wrap at the terminal width (at least 60) with a hanging indent, never inside a word; a pipe or a log keeps one line per message.

## Installing
### Resolver (`github.py`, `textsafe.py`)
- A client with an injectable transport. Per `add`: `/repos/{o}/{r}`, `/users/{o}` (owner age), `/releases/latest` (or the first non-draft of `/releases` with prereleases, or `/releases/tags/<tag>`), then an attestation lookup for an asset with a digest (before the download) and the attestation listing for the downloaded bytes: 4 or 5 of the 60 unauthenticated requests per hour.
- `GITHUB_TOKEN` is optional and sent only to api.github.com. Redirects are followed by hand within that host (a moved repo sets `RepoInfo.renamed`); a redirect elsewhere is refused.
- Assets whose download URL is not under `https://github.com/{owner}/{repo}/releases/download/`, or whose name has odd characters, are dropped. The digest `sha256:<hex>` is parsed; null or another algorithm means "no digest".
- Selection: `.AppImage` suffix (case-insensitive); other architectures excluded by name token; explicit x86_64/amd64 names win over untagged ones; several candidates means the user is asked, none means abort. `.zsync` never matches. `asset_pattern` is suggested by replacing the release version in the chosen name with `*` and matched with `fnmatch`.
- Every untrusted string shown to the user passes `textsafe` (escape sequences and control characters stripped).
- Owner pinning: `add` records the owner's account id (`owner_id`); `update` blocks when it changes, which catches a repository deleted and re-registered under the same name. A manifest without an id gets a warning and the id is pinned once the user approves.
- Only GitHub is supported. A second forge would sit behind the same interface (`repo_info`, `latest_release`, assets with size and optional digest) and could reach tier 4 at best.

### `add owner/repo` (`cmd_add.py`, `install.py`, `jail.py`, `fetcher.py`)
`add owner/repo [--name N] [--prerelease] [--tag TAG] [--dir PATH[:ro|:rw]] [--dbus NAME] [--dbus-own NAME] [--allow network|network_host|audio|mic|gpu|camera|portals|userns|linger|full_wayland] [--audio-mode pipewire|pulse] [--portal NAME] [--display wayland|xwayland|xwayland-rootful|none [--display-size WxH]] [--desktop [--mime TYPE]... [--mime-all] [--rw]]`. The review warns about every risky grant, as `perms` does. `--tag` pins a release: the manifest records the version and the channel `pinned`, so `update` leaves it alone. An option that does not apply to the chosen source (`--tag` with `--file`, `--max-size` without `--url`, `--mime` without `--desktop`, ...) is refused, never ignored.
1. Refuse early if the name exists. Show the review: owner, id, account age, stars, fork/archived/renamed warnings.
2. Resolve the release and select the AppImage. Show the digest and whether an attestation exists.
3. Ask before downloading. `fetcher.py` runs in the network-only jail (below). It follows only https redirects within github.com / *.githubusercontent.com and stops at the announced size.
4. On the host: the size must equal the announced size, the sha256 is computed, a GitHub digest must match, the file must be a type-2 AppImage (ELF + `AI\x02`). Any failure deletes the staging directory and writes nothing.
5. Verify the attestation when possible. Tier 1 if verified, 3 if there was a digest, else 4 with a warning.
6. Move the file to `~/.local/share/appjail/apps/<name>/app.AppImage`, extract it to `root/` (see Extraction), record `root.sha256` and `root.tree.sha256`, and write the manifest last. If extraction fails, nothing is kept. Defaults: nothing is granted but the window (Wayland); audio, gpu, network, portals and the rest are off.

Rolling tags (such as `continuous`) exist, so `update` compares hashes and publication times, never tags alone. Assets of a renamed repo live under the new canonical name, so release lookup uses `RepoInfo.full_name`.

### The network-only jail and pasta
The download and attestation jails (`jail.net_wrap`, run by `jail.run`) are bwrap jails with `--unshare-all --share-net --cap-drop ALL --clearenv --new-session --die-with-parent`, system directories and `/etc/ssl` read-only, the root remounted read-only and only a staging directory writable.
- The command runs inside a private network namespace made by `pasta` (package `passt`): `--config-net --no-map-gw`, no port forwarding either way, `--dns-forward 169.254.1.53`. `--share-net` then shares that namespace: outbound TCP/UDP works, the host's loopback and own addresses are unreachable. The jail gets a `resolv.conf` naming only the forwarder (the host's stub resolver is invisible there). Without pasta these jails fall back to the host network, with one warning per command through its console (`jail.warn_with`).
- Not covered: other hosts on the LAN stay reachable. Attacks from an app against LAN hosts are outside the threat model; the goal is to keep apps off the user's own host services.
- The app jail's `network` permission uses the same mechanism (see Permissions).
- Extraction jails use `--unshare-net`.
- Every helper jail (these, extraction, icon conversion, the manifest-history git and the D-Bus proxy; `jail.common_args`) also gets `--unshare-user --disable-userns` and the app jail's seccomp filter without the `userns` grant (see Runtime jail). None of these programs needs a nested user namespace, and the `--appimage-extract` fallback runs the image's own code there. `jail.run` passes the filter as a memfd, or behind pasta, which closes inherited descriptors, as a private temp file opened inside its namespace.

### `add --file` / `add --url` (`cmd_addimage.py`, `cmd_updateimage.py`, `imagesrc.py`)
Installs an AppImage that is not a GitHub release. Principle 3 holds: the user names the one source; nothing embedded in the AppImage chooses it.
- `add --file PATH [--name N] [--sha256 HEX] [permission options]` and `add --url URL [--name N] [--sha256 HEX] [--max-size MIB] [permission options]`, exclusive with `owner/repo`. Permissions, `--dir`, defaults and jailed extraction are those of `add owner/repo`. `--name` defaults to the file name minus `.AppImage`, cleaned to the name pattern; for `--file` the confirmation names it, for `--url` the name appears once the app is installed. Nothing is fetched or copied before the user confirms.
- Manifest `source` carries a kind prefix: `github:owner/repo`, `url:https://...`, `file:BASENAME` (base name only, never a path). `asset_pattern`, `owner_id` and a `channel` other than `stable` apply to `github:` only. `version` is `sha256:` plus 12 hex digits, `published_at` is the install time. A `url:` app has a `fingerprint` table (`size`, `etag`, `last_modified`, `chunks`). The parser rejects a `url:` that is not https, credentials in the URL, and keys that do not belong to the kind.
```toml
source = "url:https://example.org/dl/MyApp-x86_64.AppImage"
version = "sha256:1ccdd4decb46"
sha256 = "1ccdd4decb469fb4…"
evidence_tier = 5
fingerprint = { size = 48211968, etag = "\"abc123\"", last_modified = "Tue, 20 Oct 2026 08:00:00 GMT", chunks = "3f9a…" }
```
- Review before anything is fetched: for a URL the full URL (a different final host after redirects is shown once the download is done), for a file its real path, size and modification time; always the warning "no origin evidence". A `--sha256` mismatch aborts and deletes the staging directory.
- Local file: must be a regular file (a symlink is resolved and the target must be regular). It is copied into the staging directory, size and sha256 are computed on the copy, then the type-2 check and the install steps of `add`. The original is untouched.
- URL: downloaded by `fetcher.py` in the network-only jail; https start, no credentials. Redirects may go to any host and also to plain http; any http hop without a matching `--sha256` prints a warning and needs an extra confirmation. There is no announced size, so a hard cap applies (default 1 GiB, `--max-size`) and a `Content-Length`, when present, must equal the bytes received. The fetcher's redirect policy comes from the caller (GitHub hosts for `add owner/repo`, anything for `--url`), never from the server.

## Updating (`cmd_update.py`, `install.py`, `updater.py`, `services.py`)
`update [APP]` flow: resolve the new release; download in a throwaway jail and verify the evidence; show a diff (hashes, tier, permissions, release link); enforce the quarantine; ask the user; install. The manifest is rewritten and recorded in the history. Permissions are never changed by an update. A tier downgrade or an owner change blocks it.

- Without an app, every installed app is checked in name order (three API requests each, two for a pinned app, one more for a tier 1 app and one more for each release installed); one failure does not stop the others; the exit status is 1 if any was blocked or failed. A GitHub rate limit stops the whole run, and the rest are listed as "not checked (rate limited)".
- **Resolve:** `repo_info` on the pinned `source`, then the latest release (stable only unless `--prerelease`). The asset is the one `asset_pattern` selects (the user chooses if several match). A release published before the installed one is never installed, only reported.
- **Channel:** the top-level manifest key `channel` (omitted when `stable`). `add` writes `pinned` for `--tag` and `prerelease` for `--prerelease`. `update` never touches a pinned app, asks for pre-releases on a `prerelease` app, and `update APP --channel stable|prerelease|pinned` changes and saves the policy; a `url:` or `file:` app has no releases, so the option is refused there and the manifest accepts no other channel than `stable` for them. `--prerelease` on `update` is a one-run override. `--file`, `--sha256` and `--channel` need an app name.
- **Up to date** means the GitHub digest equals the pinned sha256 (tier 3), or, with no digest (tier 4), the same tag and `published_at`.
- **Blocks** (no override, no download, no pending state): the owner account id differs from the pinned one; the tier would weaken (digest gone, attestation gone for a tier 1 app). To go on, `remove` and `add` again after checking the repository. **Cautions** (shown, not blocking): no `owner_id` pinned yet, repository renamed or transferred (the canonical name is recorded), repository archived.
- **Quarantine:** a candidate is identified by its GitHub digest, or by tag, publication time and size when there is none. The first time it is seen is stored in `apps/<name>/pending.json` (`key`, `tag`, `first_seen`). It can be installed once `first_seen` plus the delay (default 7 days; `--quarantine DAYS`, with a warning below 7; 0 disables it) has passed. A different candidate, including a swapped asset in the same release when GitHub gives a digest, starts a new clock.
- **Tier 4 hash check:** with no GitHub digest nothing identifies the content, so the first waiting run asks to download the candidate in the network-only jail once, only to hash it, and stores the sha256 in `pending.json` (declining skips the check with a warning). When the quarantine ends, the download that would be installed must hash the same; otherwise nothing is installed (`CHANGED DURING QUARANTINE`, status blocked), the clock restarts and the new hash is recorded. Known limit: without that download, a tier 4 asset swapped in place without a new publication time is not seen.
- **Install:** confirm, jailed download (as in `add`), size and digest checks, AppImage check; for tier 4 the new sha256 is shown and confirmed again. The new image is extracted into staging first; only then are tree, image, marker and manifest replaced. A failure at any point restores the previous tree and image.
- **`url:` apps**, cheapest test first; each step ends the check or forces the full download: (1) a conditional ranged request for the first 64 bytes with the stored `ETag` / `Last-Modified` (`304` = unchanged), which also gives the size through `Content-Range`; (2) ranged requests (`206`) for fixed windows: the SquashFS superblock, the middle 64 KiB and the last 64 KiB, hashed together and compared, with the size, to `fingerprint.chunks` (about 130 KB; the first chunk alone is useless since every AppImage with the same runtime starts alike). All equal means unchanged; anything different, or no `206`, means one full jailed download after asking. The fingerprint detects a new version; it is not an integrity check, and a change confined to unsampled bytes is missed. A changed hash is a candidate keyed by its sha256 and goes through the quarantine; the candidate stays in `apps/<name>/pending.AppImage` and, at the end, a conditional request with its validators installs the stored copy on `304` without a second download. `--verify` forces a full re-download and comparison.
- **Tier rules for url/file:** a tier 4 app stays tier 4 only with `update APP --sha256 HEX` matching the new bytes; a plain `update` of a tier 4 app whose file changed is blocked with that hint. A tier 5 app given a matching `--sha256` becomes tier 4; without it, it stays tier 5.
- **`file:` apps:** a plain `update` says there is no source. `update APP --file PATH [--sha256 HEX]` replaces the image: hash diff, confirmation, jailed extraction, rollback on failure, no quarantine (the user holds the bytes). It exists because `remove` plus `add` would delete the private home.
- `list`, `remove`, `perms`, `history` and `tools` are in `cmd_apps.py`. `list` prints a table of name, version, source, tier, update channel (when not stable) and update seen; `list -l` adds, under each app, what it is granted (flags, display, directories, D-Bus names, portals). Dangling menu entries follow as notes. `remove APP [--yes]` deletes the manifest and the app directory including the private home, the menu entry, the document-portal grants and the portal decisions remembered for the app (see Portals); it asks first.

### Manifest history (`history.py`)
Every change `add`, `update` (install, `--channel`, a tier earned with `--sha256`, new validators of a URL app), `perms` and `remove` make to `~/.config/appjail` is committed to a local git repository there (author `appjail`). Manifests hold the pins and sit where any process of the user can write, so this is tamper evidence: `run` warns when a manifest differs from the last commit, and `history [APP] [--limit N]` lists the changes.
- git runs inside a no-network jail that sees only the config directory (`jail.local_git_args`), with user and system git configuration ignored and hooks, fsmonitor and signing disabled.
- Best effort: no git, or a config directory already inside another repository (a dotfiles repo), means no history and no error. Nothing is ever pushed. It detects edits made outside appjail, not an attacker who also rewrites `.git`.

## Extraction (`appimage.py`, `jail.py`)
- The AppImage is extracted and `AppRun` executed; it is never mounted (FUSE mounts do not work well in user namespaces). The AppImage runtime itself never runs outside a jail.
- Offset: end of the ELF runtime = `e_shoff + e_shentsize * e_shnum` (64-bit little-endian ELF only). `hsqs` there means SquashFS; `DWARFS` means DwarFS; anything else is unsupported.
- SquashFS: `/usr/bin/unsquashfs -no-progress -no-xattrs -p 2 -o <offset> -d /out/root /app.AppImage` in a jail with `--unshare-all`, a read-only root, the AppImage read-only and only the work directory writable. Needs the `squashfs-tools` package. Fallback, only with the user's consent asked before the download: a private copy runs `--appimage-extract` in the same jail. Like every helper jail it also gets `--disable-userns` and the seccomp filter (see The network-only jail and pasta).
- DwarFS: through the pinned helper `appjail tools install dwarfs` (explicit, asks first). The tool's URL, size and sha256 are constants in appjail's source; it is downloaded in the network-only jail, kept only if both match, stored in `~/.local/share/appjail/tools/`, re-hashed before every use, and run only in the extraction jail (no network, read-only root, `--skip-devices --skip-specials`), followed by the same tree validation. Moving to a newer dwarfs means editing the pin in a commit; appjail never fetches a helper on its own.
- Limits: the work directory is polled every 0.25 s; the jail is killed beyond 4 GiB of disk use or 500,000 entries, or after 15 minutes. Standard output and error of every jailed helper are drained as they arrive: only the first and last 16 KiB of each are kept, decoded with replacement characters, and a stream beyond 64 MiB kills the jail. The apparent size is checked afterwards, so sparse files cannot hide a huge tree.
- Host-side validation never follows symlinks: the tree root must be a real directory (the `--appimage-extract` fallback lets the image's runtime name it), and only regular files, directories and symlinks are allowed (fifos, sockets and devices reject the image); set-id and sticky bits are cleared; directories get owner access so the tree can always be deleted.
- `AppRun` must resolve, through relative symlinks only, to an executable regular file inside the tree; absolute symlinks, `..` above the root, loops and missing or non-executable targets reject the image.
- Extraction goes to `<root>.tmp` and is renamed on success, so a hostile image can fill only the work directory and cannot leave a partial `root`.

## Runtime jail (`runtimejail.py`, `runner.py`)
`run APP [-- app args]`.
- **Before every launch:** the stored AppImage must hash to the pinned `sha256` (otherwise "refusing to run"); the extracted tree is reused only if `root.sha256` matches and the tree still hashes to `root.tree.sha256` (paths, modes, contents, link targets), else it is re-extracted from the verified image (with a warning when the record or the tree hash does not match).
- **Jail:** `--unshare-all` (no network unless `network`), `--die-with-parent --new-session --cap-drop ALL --clearenv --hostname appjail`, host system directories read-only, root remounted read-only, tmpfs `/tmp` and `/run`, `/proc`, a minimal `/dev`. The extracted tree is `/app` (read-only); a persistent private home `apps/<name>/home` is `/home/app`. Generated `/etc/passwd` and `/etc/group` hide host users; only fonts, ld.so, localtime and alternatives come from the host `/etc` (plus hosts, nsswitch, host.conf, gai.conf, resolv, ssl and ca-certificates when `network`, and vulkan and glvnd when `gpu`).
- **Environment:** a fixed whitelist (HOME, PATH, LANG, TZ, USER, LOGNAME, SHELL, TMPDIR, XDG_RUNTIME_DIR, XDG_SESSION_TYPE, WAYLAND_DISPLAY, toolkit hints, `APPDIR=/app`, `APPIMAGE_EXTRACT_AND_RUN=1`, and per grant `DBUS_SESSION_BUS_ADDRESS`, `PULSE_SERVER`, `GTK_USE_PORTAL`); no host variable leaks, tokens included.
- **Wayland:** not with `display = none`: `run` then never asks the compositor for a socket, binds none and sets no display variable, so it also works without a Wayland session, over ssh for instance.
  - **Socket:** when the compositor offers `wp_security_context_v1`, `run` creates a private listening socket and hands it to the compositor with engine `appjail` and the app name (`wayland.py`, a minimal hand-written wire protocol with fd passing); the app gets that socket, otherwise the compositor's own. The socket appears read-only as `$XDG_RUNTIME_DIR/wayland-0` and nothing else from the runtime directory is visible except what a permission binds (the audio sockets, the filtered bus, the document portal). No X11 socket.
  - **Rule:** either way `run` reads the registry of the socket the app will get (before starting anything; a restricted socket is waited for a few seconds) and refuses the app when it lists a privileged interface (`wayland.PRIVILEGED`: screen capture, virtual input and input methods, data-control, foreign-toplevel, layer shell, session lock, output management, gamma, and KWin's desktop controls) or one in neither that list nor `wayland.ALLOWED` (unknown), naming them and what they would allow, unless the manifest grants `full_wayland`: then it warns and runs. A socket that lists none runs without the permission, whether or not the compositor has the protocol (GNOME has none and lists none; KWin has it and its restricted socket still lists data-control).
  - **Xwayland:** `display = xwayland` and `xwayland-rootful` are windowed too: Xwayland is a client of the same socket.
- **Audio (`audiomode.py`, `audiojail.py`):** `audio` is playback, `mic` the microphone (it needs `audio`; `--allow mic` implies `audio` and `--deny audio` takes `mic` with it). `audio_mode` says how they are provided; `audiomode.resolve` picks the path at every start.
  - `pulse`: the host's Pulse socket (`$XDG_RUNTIME_DIR/pulse/native`, served by `pipewire-pulse` on PipeWire systems) when `audio`. The server cannot restrict a client by device, so capture is always included: `mic` has no effect, and `add` and `perms` warn that the microphone cannot be denied. A client can also load modules into that server (on PipeWire's: null sinks, loopbacks, a TCP listener, FIFOs at paths of its choosing in the user's name), so it can rewire the user's audio and create such files and listeners outside the jail; it cannot make PipeWire's server load a library (`module-ladspa-*` with a path is not implemented in PipeWire 1.4.2 and 1.6.2). PulseAudio itself does load it: a client makes the server `dlopen` a library of the client's choosing, which runs the client's code in the server, outside the jail (reproduced on PulseAudio 17.0). So the socket of a PulseAudio server is never bound: `audio_mode = pulse` is refused with a message and the app gets no audio, and the fallback of an app with `mic` gives no audio either. `audiomode.host_server` tells the servers apart by the process that holds the socket (found through the inode of the listening socket in `/proc/net/unix`; a socket-activated server is started by a connection first, since its peer credentials are systemd's). A server that cannot be told is treated as PipeWire's and its socket is given (the weak point of this check, see DECISIONS.md). The private graph is unaffected: it tunnels to PulseAudio like to any Pulse server, and its own `pipewire-pulse` refuses modules. The host's PipeWire socket is never bound: PipeWire restricts only clients it recognises as sandboxed (a `.flatpak-info` in the client's root, which the app jail does not have, see Portals), so a jailed client on `pipewire-0` would be unrestricted, every node, cameras and other apps' screen casts included.
  - `pipewire` (the default): a private PipeWire graph per app (`audiojail.PrivateAudio`), started before the app and stopped with it.
    - **Daemons:** `pipewire`, `wireplumber` and `pipewire-pulse` run in a helper jail built on `jail.common_args` (no network; only its runtime directory under `$XDG_RUNTIME_DIR`, a read-only configuration, a generated `/etc/passwd` and the host's Pulse socket). The jail gets the seccomp filter of the other helper jails. There are no `/dev/video*`, `/dev/snd` or `/sys` device tree in it, so WirePlumber has no hardware to find; its profile disables the audio, video-capture and Bluetooth monitors as well. The jail's hostname is the app's name, which is what the host's desktop shows ("Tunnel for app@name": the tunnel module names its stream that way and calls itself "PipeWire").
    - **Graph:** `libpipewire-module-pulse-tunnel` nodes that connect to the host's Pulse server: a sink `app-speaker` always, a source `app-mic` only with `mic`, on the host's default devices at the moment of connection. The app jail gets this graph's `pipewire-0` and `pulse/native` and nothing of the host's, so native PipeWire clients and Pulse clients both work and neither sees a host device, a camera or another app's stream. Without `mic` the app has no source: a recorder that falls back to the default source gets the silent monitor of its own sink.
    - **Modules:** the app is a client of the graph's `pipewire-pulse` and could ask it to load modules (`pactl load-module module-tunnel-source` with the host socket's path, which the jail knows, would add the host microphone to an app without `mic`). The daemon's configuration sets `pulse.allow-module-loading = false`, so the request is refused; the graph's own tunnels are loaded by `pipewire` from its configuration.
    - **Start:** the graph is ready when both sockets exist, WirePlumber is connected and the expected nodes are there (15 s at most). The daemons start in order: PipeWire, then (once `pw-dump` is answered) WirePlumber and `pipewire-pulse`. After a short settle `pw-dump`, run in a helper jail, must show nothing but those nodes and the two driver nodes; anything else (or a daemon that exits, or a timeout) makes the graph unusable.
    - **Fallback** (`audiomode.fallback`), always with a warning that names the reason: an app with `mic` gets the host's Pulse socket (the warning says the microphone cannot be denied there); an app without `mic` gets no audio, since that socket would open a microphone it was not granted. Without a host Pulse socket no app gets audio. The reasons are a missing tool (all four must resolve under the system directories the helper jail sees), a missing tunnel module, no host Pulse socket or an unusable graph. `audio_mode = pulse` is unaffected.
    - **Limits:** the tunnel does not follow the host's devices. A default change adds links instead of moving them (playback on both sinks, the microphone mixed from both sources); an unplugged device's links disappear and nothing re-attaches, so a tunnel that was on that device alone stays silent until the app restarts; the tunnel does not reconnect after the host's `pipewire-pulse` restarts. Naming the devices in the configuration does not change this (the host's WirePlumber policy acts on the tunnel's streams).
    - **Cost:** about 36 MiB resident per app and under a second to start. The daemons die with the launcher (`--die-with-parent`; killing the jail's init removes them all).
- **GPU:** `/dev/dri` (card and render nodes), `/dev/nvidia*`, and read-only `/sys/dev/char`, `/sys/devices` and the Vulkan/GLVND data only when `gpu`. Supplementary groups survive in the jail, so group-owned render nodes stay usable.
- **Camera:** only when `camera`, the V4L2 capture nodes of the host and nothing else (`runtimejail._camera_args`).
  - A node is bound when the driver reports video capture for it (`VIDIOC_QUERYCAP`, which opens the node briefly but starts no stream): video output, metadata and codec nodes, and `/dev/media*`, stay out. The nodes are bound writable, since capture needs `O_RDWR`; supplementary groups survive in the jail, so group-owned nodes stay usable.
  - For each bound node only its own sysfs directory is bound read-only, with the `/sys/dev/char/MAJOR:MINOR` symlink recreated, which is what tools such as `v4l2-ctl` and GStreamer follow to identify the device. The rest of `/sys` is absent, unless `gpu` is granted too: that binds `/sys/dev/char` and `/sys/devices` whole, and the camera adds no `/sys` entry of its own.
  - Every capture node is bound: the app cannot choose among several cameras. Nodes that appear after the launch are not bound. With no camera present nothing is bound and the app starts normally.
  - The seccomp filter lets the V4L2 ioctls through; the grant gives no audio device (a webcam's microphone is an audio card, see Audio).
  - Apps that reach the camera through PipeWire (browsers, for instance) need the portal instead: `portals` with `--portal Camera` (see Portals).
- **Landlock (`landlock.py`):** on a kernel with Landlock ABI 6, every app jail that is not behind pasta runs in a Landlock domain scoped with `LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET` (ABI 6, Linux 6.12): no connection to an abstract unix socket created outside the jail. Sockets made inside it, such as the private Xwayland's, keep working.
  - bwrap cannot apply Landlock, so a small wrapper (`python3 -I landlock.py bwrap ...`, a separate process rather than a `preexec_fn`, which is unsafe with threads) sets `no_new_privs`, enters the domain and execs bwrap. Only the scope is set, no filesystem or network rules.
  - It matters for `network_host`, which shares the host's network namespace and so its abstract sockets: on a kernel without ABI 6 those apps are refused. Without `network` the jail's own network namespace already isolates them, and the scope is defence in depth.
  - Behind pasta it is not applied: pasta's private namespace isolates abstract sockets, and pasta refuses to start its command under `no_new_privs`.
- **Seccomp (`seccomp.py`):** a hand-assembled classic BPF filter loaded by bwrap through `--seccomp` from a memfd (a private temp file behind pasta). Default allow.
  - EPERM for the Flatpak-style deny list (`seccomp.ALWAYS`, among them kernel modules, kexec, `reboot`, swap, quotas, `syslog`, port I/O, `fanotify_init`, `bpf`, `perf_event_open`, keyrings, `userfaultfd`, `ptrace`, `process_vm_*`, handle-based opens, NUMA policy, the `TIOCSTI`/`TIOCLINUX` ioctls, x32 ABI).
  - Also as Flatpak: `socket` and `socketpair` only for `AF_UNSPEC`, `AF_UNIX`, `AF_INET`, `AF_INET6` and `AF_NETLINK` (others such as `AF_VSOCK`, `AF_TIPC`, `AF_ALG`, `AF_PACKET`, `AF_BLUETOOTH` get EAFNOSUPPORT), and `personality` only for `PER_LINUX` and the query value (no turning off ASLR or making data executable for child programs).
  - The `io_uring` calls answer ENOSYS, so libraries fall back to ordinary I/O: a large kernel attack surface few desktop apps need.
  - The syscall table is checked against the kernel's `unistd_64.h`. The helper jails get the same filter.
- **Nested user namespaces:** denied by default (`--unshare-user --disable-userns`, plus the filter: `unshare`, `setns`, `clone` with any CLONE_NEW* flag, the mount API and `pivot_root`/`chroot` fail; `clone3` answers ENOSYS so libc falls back to `clone`). The `userns` permission lifts exactly that for Electron/Chromium sandboxes and nested bwrap; the always-denied list still applies. `perms` warns when it is granted.
- **Lifetime (`runner._wait_group`):** the app runs in its own session. SIGINT, SIGTERM and SIGHUP sent to appjail are forwarded to the whole process group, which is killed when the app ends (killing `pasta` alone would leave the jail running, since `--die-with-parent` does not follow pasta's namespace helper).
  - SIGKILL of appjail cannot be caught: without pasta the jail dies with its parent; behind pasta, `jail.Lifeline` gives the launcher a FIFO it holds open, and a watcher in the namespace reads it and, at end-of-file, runs `kill -KILL -1` only when it is pid 1 of a private pid namespace. The launcher's pid cannot be polled instead (pasta's namespace has its own `/proc`).
  - Residue after a SIGKILL, in `XDG_RUNTIME_DIR` (emptied at logout): the `appjail-life-*` directory with its FIFO, and, depending on the grants, the `appjail-wl-*` (restricted Wayland socket), `appjail-audio-*` (private graph), `appjail-*` (D-Bus proxy) and, behind pasta, `appjail-pipes-*` directories and the `appjail-seccomp-*` file, plus the app's `.flatpak/<id>` portal identity. The lifeline is not applied to the short-lived download (catalogs included) and attestation jails.
- **Linger (`linger.py`):** by default the jail ends with its main command, so an app whose launcher starts the real app detached and exits (VS Code's CLI does) dies at once. With `linger = true` (`add`/`perms --allow linger`) the command runs under a small Python supervisor, run inside the jail by `/usr/bin/python3` (`-I -c`, no file bound).
  - It becomes the jail's subreaper (`PR_SET_CHILD_SUBREAPER`), runs the command, and exits with the command's status only when no process is left except pid 1, itself and the processes that were its children when it started (the private Xwayland) with their descendants. It sits inside the Xwayland wrapper.
  - An app that leaves a process behind keeps `run` from returning until that process exits; SIGINT/SIGTERM to appjail still end everything. It grants nothing and has no warning.

## Permissions
### Directories and files
Files are isolated by default. The app sees the host system directories read-only, its own tree, a private writable home, and empty tmpfs `/tmp` and `/run`. It does not see the real home, Documents, other apps, appjail's data or manifests, or any host file not granted. An app can be given specific directories, never the whole home.
- Manifest `dirs = ["~/Documents/notes", "~/Pictures:rw"]`: `~/x` appears as `/home/app/x`; absolute paths outside the home appear at the same path; read-only unless `:rw`.
- `add --dir PATH[:ro|:rw]` (repeatable): the path must exist, is normalised (home becomes `~/`) and is checked before any network access. `run APP --dir PATH[:ro|:rw]`: for that run only, announced as "Temporary access for this run". A `:` inside a directory path is refused (it separates the mode). `run APP --file PATH[:ro|:rw]` binds one file the same way; `files_from_args` always writes the mode out, so a file named `x:rw` (given as `x:rw:ro`) stays that file, read-only. `perms APP --add-dir / --rm-dir` edit the grants later.
- **Sensitive paths** are refused in every mode, at parse time and again at launch on the path of the file really opened (`grants.sensitive_reason`): credential stores (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.kube`, `~/.azure`, `~/.docker`, `~/.password-store`, `~/.netrc`, the gcloud and gh configuration, keyrings, `.git-credentials`, `.pki`), package-registry and cloud tokens (`~/.npmrc`, `~/.pypirc`, `~/.cargo/credentials*`, `~/.gem/credentials`, `~/.m2/settings.xml`, `~/.gradle/gradle.properties`, rclone, OCI, doctl, Terraform), password vaults and messaging sessions (KeePassXC, 1Password, Signal), a directory that contains one of these (grant a subdirectory), shell and tool history files, browser profiles, mail, `~/.var`, files named like password databases or private keys (`*.kdbx`, `*.key`, `*.pem`, ...), the broad `~/.config`, `~/.local`, `~/.local/share`, `~/.local/state`, `~/.cache`, and system trees (`/etc`, `/dev`, `/proc`, `/sys`, `/run`, `/usr`, `/boot`, `/root`, ...). Read-write is also refused where it could plant code that runs outside the jail (`~/.local/bin`, `~/.config/autostart`, `~/.config/systemd`, `~/.local/share/applications`, `~/.local/lib` (the Python user site every host Python imports, appjail included), thumbnailers, file-manager scripts and service menus, the icon themes (`~/.local/share/icons`, `~/.icons`: the desktop decodes their images outside any jail), shell and editor startup directories), and where it could change how the desktop's own apps look or plant files the desktop decodes outside the jail (`grants.APPEARANCE_HOME_DIRS`: GTK and Qt/KDE style settings such as `~/.config/gtk-3.0`, `~/.config/gtk-4.0`, `~/.gtkrc-2.0` and `~/.config/kdeglobals`, themes, fonts and the fontconfig configuration; read-only stays possible). There is no override: grant a subdirectory.
- Also refused: `/`, the home directory or any parent of it, `..` components, appjail's own data and config trees (and parents/children), and missing paths. Each grant is opened once when the jail starts and checked through that descriptor (`runtimejail.Grants`): the checks judge the file really opened, and bwrap binds the descriptor (`--bind-fd`, `--ro-bind-fd`, bubblewrap 0.10), so swapping a path or one of its components for a symlink afterwards changes nothing. A file unlinked during the check is refused.
- **Shared temporary directories** (`/tmp`, `/var/tmp` and everything below them) are refused as directory grants, at parse time and at launch on the path of the directory really opened (`grants.directory_reason`). Every program keeps its unix sockets there (the X server's `/tmp/.X11-unix`, tmux's server socket, agents), and a bind mount does not stop `connect()`, even read-only: the app could drive those programs from inside the jail. A single regular file there can still be opened (`run --file`, `open`): it carries no socket.
- `run APP --file PATH[:ro|:rw]` (repeatable) binds just that file for that run (`runtimejail.Grants`): read-only unless `:rw`, nothing else from its directory is visible, and the in-jail path is appended to the app's arguments. Only regular files; the policy looks at the file really opened; the sensitive-path policy applies, plus `PERSIST_HOME_FILES` (`.bashrc`, `.profile`, `.gitconfig`, ... never read-write). Not persisted. Apps that save by write-and-rename fail on `:rw` (a bind-mounted file cannot be replaced); the portal file chooser exists too.

### Network
- No network by default. `network` runs the app in the pasta namespace like the download jails (`runner.launch` wraps the command with `jail.net_wrap(required=True)`, DNS through the forwarder): the internet is reachable, the host's loopback services and own addresses are not. Without pasta the app is refused, never silently put on the host network; the same refusal happens earlier when the permission is granted (`permargs.require_network_isolation`).
- `network_host` (needs `network`; `--allow network_host` implies `network`; `--deny network` clears it) keeps the host network namespace and `resolv.conf` for apps that need host services; `add` and `perms` warn when it is granted. The shared namespace would also carry the host's abstract unix sockets (the X server's `@/tmp/.X11-unix/X0` among them); Landlock keeps the app off them (see Runtime jail), and without Landlock ABI 6 `network_host` is refused when it is granted and when the app starts.
- pasta closes every inherited descriptor, so bwrap's are opened inside the namespace: the seccomp filter in a private 0600 temp file, the portal handshake over two FIFOs in a private temp directory, opened by `/bin/sh -c 'exec "$@" 9<filter 8>status 7<block'` (`jail.net_wrap(fd_files=...)`, `runner.Pipes`; one digit only, dash accepts no more). Granted directories and files cannot be carried either: a small wrapper between pasta and bwrap (`reopen.py`) opens each path again inside the namespace and refuses to start if its device and inode are not those the launcher checked; the launcher keeps its descriptors open, so those numbers cannot be reused. pasta runs the command as uid 0 of a user namespace mapped to the host user, so the jail passes `--uid`/`--gid` to restore the real ids (passwd, D-Bus authentication and file ownership depend on them). IPv6 is forwarded by pasta when the host has a route.
- An allowlisting proxy for the LAN is not planned.

### Xwayland (`runtimejail.xwayland_command`)
`display = "xwayland"` is for X11-only apps. The host X11 socket is never bound (it would expose every other X client's keystrokes and screen). The app command is wrapped by a short `sh` script that starts a rootless `Xwayland` inside the jail as a client of the app's Wayland socket, with `-nolisten tcp` and `-displayfd`, then sets `DISPLAY` and execs the app.
- The X socket lives in the jail's private `/tmp` and abstract namespace, so no other app and no host X server is reachable. With `network_host` the abstract namespace is the host's: Landlock then refuses connections to sockets created outside the jail, including the host X server's, while the private Xwayland, started inside the jail, stays reachable. The environment has no `WAYLAND_DISPLAY` and selects X11 toolkits (`GDK_BACKEND=x11`, `QT_QPA_PLATFORM=xcb`, `SDL_VIDEODRIVER=x11`, ...). Xwayland dies with the jail.
- The script waits up to 20 s for Xwayland to report its display and gives up at once, with a message, if Xwayland exits. Needs `/usr/bin/Xwayland` (package `xwayland`); `run` stops with a clear message when it is missing. With no window manager, windows map as plain toplevels.
- `display = "xwayland-rootful"` runs Xwayland without `-rootless`, with `-geometry display_size -decorate`: it makes one `xdg_toplevel` of its own that holds the X screen, so the compositor needs no X window management. Rootless needs the compositor to be the X window manager, which mutter is only for the Xwayland it starts itself; there the rootless windows are mapped in the X server and never shown. Inside the jail `openbox` (`/usr/bin/openbox`, package `openbox`; `run` stops with a message when it is missing) is started on that display for stacking, focus, decorations and the cursor. Same isolation as the rootless mode; no root is involved. The mode is chosen with `--display`, never automatically. Its trade-off: the app's windows (dialogs, menus) live inside one host window.
- Xwayland's output is kept and shown only when it fails to start.

### D-Bus (`dbusproxy.py`)
`dbus_filter` lists the session-bus names the app may talk to, such as `org.freedesktop.Notifications` or `org.mpris.MediaPlayer2.*`. `add --dbus NAME` (repeatable), `perms --add-dbus / --rm-dbus`.
- Empty list: the jail has no bus at all (no `DBUS_SESSION_BUS_ADDRESS`, no socket).
- Otherwise `run` starts `xdg-dbus-proxy` on the host side inside a bwrap jail of its own: no network, read-only system, and only the real bus socket (read-only) and a private directory `$XDG_RUNTIME_DIR/appjail-XXXX` for the new socket. The proxy runs `--filter`; every name not listed is invisible and every call it does not allow is answered with an error by the proxy. Its `--talk=NAME` filters by destination name only, and one process answers on all its names: a call to a granted name would reach every object and interface of the connection that owns it, including those of refused names the same process owns (on GNOME Shell, Cinnamon and Plasma's shell, refused names share the connection of ordinary ones; DECISIONS.md, D-Bus names). So:
  - A name of a known service (`dbusproxy.CONFINED`: `org.freedesktop.Notifications`, `org.gtk.Notifications`, `org.freedesktop.secrets`, `org.kde.StatusNotifierWatcher`, `org.mpris.MediaPlayer2.*` and the names below it) gets `--call` rules for the interfaces its specification defines, plus `Properties`, `Introspectable` and `Peer`, on its object path only, and `--broadcast` rules for the signals of those interfaces from that path. Every other object of the owner is refused by the proxy, whether the app addresses the name or the owner's unique name.
  - Any other name gets `--talk=NAME`. Before starting the proxy, `run` lists the bus's names (`dbus-send`, `ListNames`, outside any jail) and asks the owner of each refused or granted one (`GetNameOwner`) and stops when a granted name, or a name a granted `.*` entry covers, is owned by a connection that also owns a name `dbus_filter` refuses. It fails closed when the owners cannot be read. The check sees the owners at launch; a name that is unowned then, or changes owner later, is not checked again. The app jail binds only the proxy socket as `$XDG_RUNTIME_DIR/bus`. The real bus is never visible.
- `run` waits 5 s for the proxy's ready byte, and stops the proxy and removes its directory when the app exits or `run` fails; the proxy also dies with appjail. The host address must be `unix:path=...` (from `DBUS_SESSION_BUS_ADDRESS`, else `$XDG_RUNTIME_DIR/bus`); abstract and TCP are refused. Needs `xdg-dbus-proxy`.
- Refused when the manifest is loaded and when typed: `org.freedesktop.DBus`, `org.freedesktop.systemd1`, `org.freedesktop.Flatpak`, `org.freedesktop.portal*`, `org.freedesktop.impl*`, `org.gnome.Shell`, `org.gnome.SessionManager`, `org.kde.KWin`, `org.kde.klauncher5*`, `org.kde.klauncher6*`, `ca.desrt.dconf*` (settings, including custom keybindings that run commands), `org.gtk.vfs*` (GVfs mounts and host locations), `org.gnome.Mutter*` (screen capture, remote input and input capture sessions that Mutter opens for any client of the bus), `org.cinnamon.Muffin*` (the monitor layout, backlight and gamma that Muffin changes for any client of the bus), `org.Cinnamon*` (the Cinnamon shell's `Eval`, which runs any script in the shell for any client of the bus), `org.kde.plasmashell*` (Plasma's `evaluateScript`, which runs a desktop script for any client of the bus), `org.kde.klipper*` (the clipboard and its history, for any client), `org.freedesktop.a11y*` (the keyboard monitor), `org.gnome.ScreenSaver`, `org.kde.kglobalaccel` and `org.kde.keyboard` (global shortcuts and keyboard state), any wildcard covering them, and wildcards with fewer than three name parts before `.*`. Names exposing stored secrets (`org.freedesktop.secrets`, keyring, kwallet) are allowed with a warning.
- Owning a name (MPRIS, single-instance) is `dbus_own`, passed as `--own=NAME` (`add --dbus-own`, `perms --add-dbus-own / --rm-dbus-own`; each owned name is warned about). Names in the desktop namespaces (`org.freedesktop.`, `org.gnome.`, `org.kde.`, `org.a11y.`, `com.canonical.`, `org.ayatana.`, `org.gtk.`, `ca.desrt.`) cannot be owned, so an app cannot impersonate the notification daemon, secret service or polkit; the exception is status-notifier item names. The proxy matches only a trailing `.*`, so a `-<pid>` suffix as in `org.kde.StatusNotifierItem-1234-1` is not expressible.

### Portals (`portal.py`, `dbusproxy.py`, `runner.py`, `cmd_portals.py`)
`portals = true` gives the app the desktop portals (file chooser, notifications, settings, ...) through the same filtering proxy; the app never sees the real bus.
- **Identity:** xdg-desktop-portal identifies the caller by reading `/proc/<pid>/root/.flatpak-info` of the D-Bus peer and `$XDG_RUNTIME_DIR/.flatpak/<instance>/bwrapinfo.json`. That is the only sandbox identity it understands besides Snap and Linyaps, so appjail writes it: a compatibility shim; nothing depends on or installs Flatpak.
  - The app id is `app.appjail.<name>`, one per name (`portal.app_id`): it is the portal's whole notion of who the app is, so two apps must never share it. Each dot-separated part of the name is escaped: `_` becomes `_u`, `-` becomes `_h`, an empty part becomes `_e`, and a part starting with a digit gets a leading `_` (`my-app` is `app.appjail.my_happ`, `7zip` is `app.appjail._7zip`; plain names keep their spelling).
  - The identity file is bound into the proxy's jail (the proxy connection is the peer the portal sees), never into the app's, so the app cannot read or forge it, and cannot pick its own id (the alternative, `org.freedesktop.host.portal.Registry`, lets an app claim any id that has a `.desktop` file).
  - `bwrapinfo.json` carries the app jail's init pid from bwrap's `--json-status-fd`; `--block-fd` holds the app back until the file exists.
- **Side effects:** the permission store and the Background portal treat the app as a Flatpak app (an autostart entry would say `flatpak run`, inert without Flatpak). Document-portal paths are `<XDG_RUNTIME_DIR>/doc/<id>/<name>`; the per-app view `doc/by-app/<app id>` is bound at `/run/user/<uid>/doc` (and at the host runtime path too if it differs).
- **Interfaces:** `portals = true` allows only the safe set (`grants.PORTAL_SAFE`: FileChooser, Notification, Settings, Trash, Print, Inhibit, NetworkMonitor, ProxyResolver, Secret, Realtime, MemoryMonitor, PowerProfileMonitor) plus the document portal. Privileged interfaces must be named in `portal_interfaces` (`grants.PORTAL_OPT_IN`: OpenURI, Email, Screenshot, ScreenCast, RemoteDesktop, GlobalShortcuts, InputCapture, Camera, Location, Account, Wallpaper, Background, Usb); `add` and `perms` warn for each (`--portal NAME`, `--add-portal`, `--rm-portal`). `Flatpak` (spawn on the host) and `DynamicLauncher` (installs launchers) are refused. Everything else on the portal's name is invisible (`--call` rules per interface; unknown calls get AccessDenied from the proxy).
- **Document portal:** D-Bus activated; if `doc/by-app/<id>` is missing, `run` asks the bus to start it (`dbus-send`, GetMountPoint) and otherwise stops with a clear message. It needs FUSE.
- **Revoking:** `portals APP [--revoke DOC_ID]... [--revoke-all] [--yes]` lists the documents granted to `app.appjail.<name>` (host permission store, read with `dbus-send`) and revokes them through `org.freedesktop.portal.Documents.RevokePermissions` on the host side. Revoking only in the store is not enough: the portal keeps serving the file until the call removes the per-app view. The app's own recent-files list is untouched. `remove` revokes the grants too, and also deletes the app id's entries from the portal's other permission-store tables (`portal.STORE_TABLES`: device access such as the camera, location, screenshot, background, screen-cast restore tokens, chosen URI handlers, ...), so a later app with the same name starts with no remembered decision. The store cannot list its tables, so the list follows xdg-desktop-portal 1.20; a table a system does not use is empty.

## Menu entry and opening files (`desktop.py`, `cmd_desktop.py`, `cmd_open.py`)
`desktop NAME [--mime TYPE]... [--mime-all] [--rw] [--yes]`, `--remove`, `--prune`, `--show` (read-only: `Registered`, `Offered` with the registered ones marked, `Not offered`; exclusive with the writing options); `add ... --desktop [--mime TYPE]... [--mime-all] [--rw]`; `open NAME [--rw] -- FILE...`. The AppImage's own `.desktop` is untrusted (its `Exec`, `Actions`, `TryExec` and `MimeType` would act outside the jail), so appjail generates the entry and never copies that file. It is written by the host-side CLI to `${XDG_DATA_HOME:-~/.local/share}/applications/appjail-<name>.desktop`; only files carrying the `X-Appjail-App=<name>` marker are ever replaced or deleted.
- **Fields:** from the top-level `*.desktop` of the tree (regular file, no symlink following, 64 KiB cap) only `Name`, `Comment`, `GenericName`, `Categories`, `Keywords` (unlocalised, through `textsafe.clean`, one line, length caps, charset check for `Categories`) are kept. `Name` gets the suffix ` (appjail)` so an app cannot pose as a host app. `Exec=<absolute appjail> run <name>` (quoted per the spec, `%` doubled, no field codes), `Terminal=false`.
- **Icon:** `Icon=` or `.DirIcon` resolved with `appimage.resolve_entry(..., executable=False)` (no escape from the tree). PNG: 1 MiB cap, then rewritten by `pngclean.sanitize` (stdlib, no pixel decoded): every chunk and CRC checked, square 16..1024 px, image data inflated with a hard size limit and checked against the header (right length, legal filter bytes), then written again with only IHDR, PLTE, tRNS, IDAT and IEND, so the desktop's image loaders never read the app's own bytes; a file that does not fit is refused, not repaired. Installed as `icons/hicolor/<WxH>/apps/appjail-<name>.png`. SVG: rendered to 256 px by `rsvg-convert` inside a no-network jail (the host never decodes an SVG), then validated like any PNG. No converter: no icon, a one-line note at install and update; `desktop --show` names the reason. After writing or removing an entry, `gtk-update-icon-cache -t` runs on the user's `icons/hicolor` (the directory has no `index.theme`), then `update-desktop-database`; a missing tool is a note.
- **File types** (`MimeType`) are opt-in and advertise-only: nothing is registered unless the user picks types (`--mime`, `--mime-all`, or the interactive list); only types the app declares and that pass the filter can be picked. The filter drops anything not `type/subtype` in lowercase, `x-scheme-handler/*`, `inode/*`, executables, shell and script-language types, AppImage and installer types, duplicates, and everything beyond 32. appjail never writes `mimeapps.list`. With types, the entry runs `appjail open <name> [--rw] -- %F`.
- **`open`:** each file is opened, checked and bound alone into the jail like `run --file`: read-only unless `--rw` (baked into the Exec by `desktop --rw`; the manifest is unchanged), sensitive-path policy applies, URLs and non-regular files are refused. The mode is always spelled out (`:ro`/`:rw`) so a file named `x:rw` cannot raise its own mode. No file after `--` is a plain start. Errors also go to `notify-send` when present. Choosing the file is the consent.
- **Lifecycle:** `remove` deletes the entry and icons and refreshes both caches as above; a default left in the user's `mimeapps.list` is only reported. `update` regenerates an existing entry, keeps the types the app still declares, drops the others and only lists newly declared types. Dangling entries (app directory removed by hand): `list` flags them, `desktop --prune` deletes them, and `open` of a removed app deletes its own entry.
- Out of scope: default applications, URL handlers, `%u`, per-type actions, drag and drop of unrelated types.

## Index and search (`catalog.py`, `indexstore.py`, `index.py`, `cmd_index.py`)
The index is a derived catalog, not a copy of the AM repository, and further sources can provide catalogs in the same format. The built-in catalog is built elsewhere (the sister project appjail-db, from the AM index and the AppImageHub feed, merged without duplicates); appjail reads neither itself. It only affects `search`; installed apps never depend on it.
- **Format** (`catalog.py`; user documentation in README "Searching"): one JSON document `{"format": "appjail-catalog", "version": 1, "origin"?, "revision"?, "apps": [{"name", "description"?, "source"?, "note"?}]}`. Strict: unknown keys, a wrong version, duplicate names, a bad `source`, names outside `[A-Za-z0-9][A-Za-z0-9._+-]{0,80}`, more than 50,000 apps or 16 MiB refuse the whole catalog. Texts are cleaned of terminal escapes and cut (description 300, note 200, origin and revision 300). What is stored is `catalog.dumps(catalog.parse(text))` (deterministic, apps sorted), never the downloaded bytes. A bare `owner/repo` source is refused.
- **Source grammar:** `source` is the manifest's `kind:target` string. Kinds: `github:owner/repo`, `gitlab:HOST/group[/sub...]/project` (host always explicit), `forgejo:HOST/owner/repo`, `codeberg:owner/repo` (normalized to `forgejo:codeberg.org/owner/repo`), `url:https://...`. `file:` is refused. Hosts are lowercased DNS names without port or credentials; syntax only, nothing is contacted. Only `github:` and `url:` can be installed; the others are information (`search` prints the matching `appjail add` command only for those). The update review compares `catalog.identity` (kind, host, owner, case-folded): another kind, host or owner is an owner change (loud warning), the same owner with another repository an ordinary source change. There is no forge alias table: a catalog cannot redefine what a host name means.
- **Sources** (`indexstore.py`): the built-in `appjail-db` plus any added with `index add NAME --url https://... | --file PATH`. Layout under `~/.local/share/appjail/index/`: `sources.json`, and per source `current.json`, `previous.json`, `state.json` (sha256, revision, update time of both). A `file` source stores the path and re-reads it at `index update`. Every file is replaced atomically and `current.json` is never moved, so a crash leaves a readable catalog; `index update` first removes the temp files an interrupted update left behind. Source names match `[a-z0-9][a-z0-9._-]{0,31}`; `appjail-db` is reserved and cannot be removed. The state of a snapshot may also hold `commit`, the appjail-db commit it was fetched at (40 lowercase hex digits, else the state is refused as malformed).
- **Built-in source (appjail-db):** the kind `repo`, `github:alberto743/appjail-db`.
  - `index update` asks the GitHub API for the commit the default branch points to (`github.Client.head_commit`; one request, a rate limit or API error fails the update without falling back to an unpinned URL), then downloads `https://raw.githubusercontent.com/alberto743/appjail-db/<commit>/catalog.json` exactly as a URL source is downloaded (network-only jail, 16 MiB cap) and runs it through `catalog.parse`. `--commit` takes only 40 lowercase hex digits and skips the API request; it applies to the built-in source only.
  - The commit is shown in the review and recorded in the snapshot's state (and in `index status`), so the catalog in use can be traced to an exact state of appjail-db and an older one fetched again.
  - The catalog itself is made by appjail-db, weekly, from the AM index and the AppImageHub feed (descriptions cut to 100 characters, size and shrink checks); appjail reads neither. An app whose name is the same in both but whose repositories differ has no `source` and a `note` naming both (`resolve manually: ...`). The catalog's own `revision` names the AM commit and the AppImageHub feed hash it was built from and is informational.
  - A commit is not a signature: the catalog is unsigned, and the controls are HTTPS, who can write to appjail-db, the strict parser and the diff review.
- **URL and file sources:** a URL is downloaded by `jail.download_url` (https start, 16 MiB cap, redirects as for `add --url`; a plain-http hop is warned about); a file must be a regular file within the cap. Both go through `catalog.parse`. There is no hash pin: the safeguards are the strict parser, the diff review at every update and the previous catalog kept for rollback.
- **Review** (`cmd_index.review_and_install`): app count, size, revision, the appjail-db commit (built-in source) and a sha256 prefix; for an update the apps added and removed and every app whose `source` changed, an owner change as a loud warning, and nothing replaces the current catalog before the user agrees (default no). An identical catalog is reported without a prompt. A new source is registered only after the user accepted its first catalog. `index update` without a name does every source; one failure does not stop the others and makes the status 1. `rollback` swaps current and previous (so it can be undone).
- **Search:** `search KEYWORD... [--limit N] [--all]` reads the current catalog of every source; with several sources each hit shows its source in brackets. Every keyword must occur (case-insensitive) in the name or description. Ranking: exact name, name prefix, all keywords in the name, any keyword in the name, description only; then alphabetical, then source name. A hit's `source`, its `appjail add` command and its `note` follow on lines of their own.

## Graphical front end (`gui/`)
`appjail-gui` (or `python -m appjail.gui`) opens a tkinter window; it needs the system package `python3-tk` and a display, and prints a one-line message without them. Tabs: Apps (the installed apps from their manifests, with the granted portal interfaces in the permissions column; the portals form lists the interfaces and the document grants, and the grants to revoke are selected from the list; run, run with extra access for one run, open file, update with its options, permissions, portals, history, menu entry, remove), Add (GitHub, URL or file, with every grant and menu-entry option of `add`; options the CLI refuses for the chosen source are greyed out), Search (a results list from the catalogs; "Add this app…" copies a hit with a `github:` or `url:` source into the Add form and switches to that tab, without installing; `index`), Tools (helpers, version, list, the history of all apps, prune). One output pane shows what the commands print. Options of a command that has many (`update`, `run`, `desktop`, `portals`) are set in a small form that only builds the argv.
- **One implementation:** every action builds an argv (`gui/argv.py`) and runs `cli.main` on a worker thread with `GuiConsole` (`gui/console.py`), a `Console` whose output goes through `textsafe` into a queue and whose prompts are answered by modal dialogs on the Tk thread. Closing a dialog cancels the command.
- **File types at add time:** the types an app declares are known only after the install. With "Create menu entry" on and no types (or "all") given, the window adds without `--desktop` and then runs `desktop NAME` for the new app, which lists the declared types and asks. The "Files writable" box adds `--rw` to the add or to that follow-up; the default stays read-only.
- **File types of an app:** the Apps tab shows `file types: N registered of M offered` in the detail line (read as data by `gui/apps.file_types`, which shares `cmd_desktop.file_type_state` with the command), a "File types" button runs `desktop NAME --show`, and "Menu entry…" offers the types as a multi-select list with the registered ones highlighted (the refused ones are named). Deselecting everything is refused for an entry that has types, because the command would keep the current ones.
- **Consent:** every prompt (confirmation, free text, list choice) shows the lines the command printed just before it (the review: before/after permissions, release details, the file types on offer); confirmations keep the command's default and take the keyboard focus on it: No everywhere except `desktop`'s "Write the menu entry?", which the user has just asked for. The GUI never adds `--yes`; the permissions editor only computes the `perms` options and the command asks.
- **Running apps:** `run` and `open` start `python -m appjail` in its own session, so closing the window does not end the app. A file chosen in the dialog is bound read-only, like the menu entry.
- **Text:** everything shown passed `textsafe.clean`; network text is never put into a widget directly.
- **Menu entry of appjail-gui:** `appjail-gui --desktop` writes `${XDG_DATA_HOME:-~/.local/share}/applications/appjail.desktop` (the name cannot collide with an app entry, which is `appjail-<name>.desktop`) and copies the SVG shipped in the package (`gui/appjail.svg`, trusted, so not converted) to `icons/hicolor/scalable/apps/appjail.svg`. The entry carries `X-Appjail-GUI=true`; only a regular file with that marker is replaced or deleted by `--desktop` and `--remove-desktop`, a symlink or foreign file never. `Exec` is the installed `appjail-gui`, or the running interpreter with `-m appjail.gui`. Neither flag needs a display or tkinter (a missing tkinter is a note).

## Verification
- The ordinary suite (`APPJAIL_INTEGRATION=1`, no downloads) runs in a dedicated qemu-kvm guest and in GitHub Actions on every push. Opt-in suites run on demand and in the manual/weekly `e2e.yml` workflow: `APPJAIL_E2E=1` (real downloads of user-approved repositories), `APPJAIL_LIVE=1` (live API metadata). All execution happens in the guest or on CI runners, never on the developer's host (see CLAUDE.md).
