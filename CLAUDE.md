# appjail: instructions for Claude

The documentation is the site built from `docs/` (<https://alberto743.github.io/appjail/>); `DESIGN.md` and `DECISIONS.md` only point into it. Read `docs/understand/principles.md` first, then the concept pages under `docs/understand/` for the area you work on: they specify the behaviour. `docs/reference/` holds the exact commands, keys, lists and files; `docs/decisions/` records each choice with its reasons, rejected alternatives, deferred features and the planned code work (`docs/decisions/deferred.md`). Do not deviate from the principles without asking.

## Project
A Python (stdlib only) AppImage manager: GitHub, URL and file installs with pinned and verified downloads, bwrap jails, quarantined updates, a derived catalog index (the built-in catalog is built by the sister project `../appjail-db`; `catalog.py` here defines the format and appjail-db keeps a copy). The version comes from the git tag (`[tool.hatch.version]`); pushing a `vX.Y.Z` tag runs `release.yml` and `pypi.yml` after the CI gate.

## Hard rules
- Never use the host for execution, except to edit files, run git in this directory and run qemu itself. Everything else runs in the qemu-kvm guest: unit and integration tests, the `appjail` command, network access (GitHub API probes included), downloads, extraction and bwrap. Never install test tools on the host.
- Never source, execute or `eval` any text from the network (catalogs included). Parse as text only and strip terminal escape sequences. appjail never reads the AM repository; the sister project `../appjail-db` (github.com/alberto743/appjail-db) converts it to the catalog the built-in `appjail-db` source downloads. The tool has no self-update and never fetches code to run.
- No sudo for Claude (sudo lines in the VM recipe are for the user on a new machine). Install nothing outside this directory and the tool's own data directories (`~/.local/share/appjail`, `~/.config/appjail`).
- Ask before downloading any AppImage or other binary. Network tests use small, well-known repositories the user names.
- Extraction: prefer `unsquashfs` on the SquashFS offset; fall back to `--appimage-extract` only inside the no-network jail. Never run the AppImage runtime outside a jail.
- Git: work in this repository and commit at each completed, tested milestone with a clear message, using the repository's own identity (`.git/config`: GitHub noreply address); never override `user.name`/`user.email`. Build a new feature on its own branch and merge it into `main` with an ordinary merge commit (`--no-ff`, never a fast-forward) whose message outlines the branch's purpose, so the history shows when each feature was included; the milestone commits on the branch stay as they are. This applies only when the work has more than one commit: a change that is a single commit goes straight onto `main`, with no branch and no merge commit. Commits stay local; push to `origin` (public: everything pushed, commit messages included, is world-readable) in batches, at the end of a piece of work or when the user asks (each push starts CI runs and uses GitHub limits). Never rewrite pushed history; never commit `vm/` or secrets.
- No personal data in tracked files or commit messages: no home paths, usernames, session or scratchpad paths, hostnames or emails. Use `~` and placeholders. No session links or IDs either: no `Claude-Session:` trailer, no `claude.ai/...` URL in commits, PR bodies or files (`.claude/settings.json` sets `attribution.sessionUrl: false`; if a tool adds one anyway, strip it before committing). Enable the check once per clone: `git config core.hooksPath .githooks` (`.githooks/commit-msg`, patterns in `.githooks/forbidden-patterns`); the `hygiene` job of `ci.yml` checks the whole history.
- Licensing: MPL-2.0, REUSE-compliant at every commit. Every code file starts with `SPDX-FileCopyrightText: 2026 Alberto P` and `SPDX-License-Identifier: MPL-2.0` (after a shebang if any); other files (Markdown, config, templates) are covered by `REUSE.toml`. New file types need a header or a `REUSE.toml` entry in the same commit.

## Docs
- The site (`docs/`, `zensical.toml`) is the documentation; how it is organised and written is in `docs/develop/writing-docs.md`. Build it in the guest with `tests/vm/docs.sh` (strict: a broken link or anchor fails). `docs.yml` builds it on every push and publishes it on `vX.Y.Z` tags.
- When code, decisions or the environment change, update in the same commit: the concept page under `docs/understand/`, the guide and the reference, a decision page under `docs/decisions/` when a choice was made, and the tests and scripts. A new grant, mechanism or external tool needs its concept page, or a section in one. Concept pages keep the headings What it is, Why it matters, How appjail uses it, Connections, Limits, References (`tests/test_docs.py` checks them and the navigation).
- `docs/reference/commands.md` names every command and option (checked by `tests/test_docs.py`). `docs/reference/policy.md` is generated from the source: after changing a policy list run `python3 tests/policy_tables.py --write` in the guest.
- References: primary sources only, each opened and checked before citing; re-check them, and `docs/decisions/project/related-projects.md` with its date, at each minor release.
- `README.md`: short entry point (what it is, why, requirements, install, quick start, limits summary, links into the site), absolute links (it is the PyPI description). Keep its requirements and limits in step with the site.
- `SECURITY.md`: the reporting policy and its scope. It follows the limits on the site and the supported systems and Python version; when those change, update it in the same commit.

## Code
The code layout, the rules the code relies on and walk-throughs of `add`, `run` and `update` are in `docs/develop/architecture.md` and `docs/develop/source-tour.md`. In short: `cli.py` is only the parser and the command table (new commands go in `cmd_<name>.py`); untrusted work runs in a jail built by `jail.py` or `runtimejail.py`; policy modules (`grants.py`, `valid.py`, `manifest.py`) do no I/O; every line printed goes through `console.Console`; every write uses `store.atomic_write` or `store.staging`. The GUI (`gui/`) runs the CLI and never reimplements a command or adds `--yes`.

## Testing environment
The guests, the scripts, the opt-in suites, the coverage and the known CI behaviour are in `docs/develop/testing.md`. The rules for Claude:
- Everything that runs software runs in the qemu-kvm guest (see Hard rules). Change guest requirements in `tests/vm/packages.txt`, never ad hoc in the guest. Keep images, disks and scripts under this directory or the scratchpad, never in the user's home.
- Ask before creating or downloading a guest image (a binary download).
- Approved test AppImages (guest only; anything else needs a new approval): `AppImage/appimagetool`, `AppImage/AppImageKit`, `skyjake/lagrange` (the GUI test app), `pkgforge-dev/htop-AppImage` and `pkgforge-dev/Galculator-AppImage` (DwarFS), `ImageMagick/ImageMagick` (X11-only), `mhx/dwarfs` universal-small and `cli/cli` gh tarball (pinned tools). `hluk/CopyQ` cannot run in the Debian 13 guest (glibc 2.43 needed). `cli/cli` is also the repository for API metadata checks. `alberto743/appjail-db` (`catalog.json`, ~1.5 MB text) is approved for the index e2e test. The docs tooling of `.github/requirements-docs.txt` is approved for the guest.
- GitHub limit: 60 unauthenticated requests per hour, shared by every run from the guest. Check `https://api.github.com/rate_limit` (free) before an e2e run and run one group at a time.
- Before a milestone commit, and before any push, run the full suite on both guests: `tests/vm/test.sh` and `GUEST=ubuntu tests/vm/test.sh`. A pass on one is not a pass. `tests/test_lint.py` (ruff) must stay clean.

## CI
The workflows, the release procedure and the automation pull requests are in `docs/develop/ci-release.md`. Rules: pin actions to the full commit SHA with a trailing `# vX.Y.Z` comment, keep `permissions: contents: read` unless a job needs more, keep the runner label `ubuntu-26.04` until the scheduled switch, add no workarounds for systems older than Debian 13 and Ubuntu 26.04. CI runs on GitHub's runners, not on the host; read results with `gh run list/view/watch` (read-only). A red CI on `main` is a bug to fix; a failure only on CI is often a fixture assumption (runner uid 1001, guest uid 1000): find the cause with a captured log before adding a workaround. A `bump-tools` pull request moves a pinned binary: close and reopen it to start CI, and review it before merging.
