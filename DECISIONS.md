# appjail: decisions

Why appjail is built the way it is: features deliberately deferred, alternatives that were evaluated and rejected, design decisions, and the facts those choices rest on. How the tool behaves is in [DESIGN.md](DESIGN.md). Each entry gives the decision, the reason, and the condition for revisiting it.

## Deferred features

| Feature | Why | Revisit when |
|---|---|---|
| GPG tier (tier 2) | A signature proves a key, not its owner, so `add` would still be trust on first use for the key fingerprint. It needs a per-app fingerprint pin, a jailed `gpgv`, update rules (a key change blocks, a lost signature is a downgrade) and a source for the signature file. The attestation tier plus the quarantine hash already cover attested and unattested apps. | A wanted app signs with GPG and has no GitHub attestation. |
| Resolvers for other forges (GitLab, Codeberg/Forgejo, SourceForge, vendor sites) | Only GitHub is supported. The appjail-db catalog (built from AM and AppImageHub) lists 13 apps on GitLab or Forgejo and about 180 more whose note points to a vendor site, which `search` shows and `add` cannot install. Other forges expose release assets with sizes but not GitHub's `digest` or attestations, so apps from them would be tier 4 at best. The catalog format already carries `gitlab:`, `forgejo:` and `codeberg:` sources. | A wanted app lives only on another forge. A resolver sits behind the interface of `github.py`. |
| Other architectures | x86-64 only; see "arm64" below. | The arm64 work is resumed. |
| Allowlisting proxy for the LAN | With `network`, other hosts on the LAN stay reachable (pasta has no filtering). Attacks from an app against LAN hosts are outside the threat model; the goal is to keep apps off the user's own host services. | Host filtering for the app jail's `network` permission is wanted. |

### arm64 (aarch64): evaluated, not implemented, paused

Feasible and moderate in code, expensive in verification. Scope if done: aarch64 only (armhf, riscv64 and i386 stay out; the ELF parsers accept 64-bit little-endian only).
- **Where x86-64 is hard-wired:**
  - `seccomp.py`: `AUDIT_ARCH_X86_64`, the `SYSCALLS` numbers, the x32 guard and the `platform.machine()` refusal. aarch64 uses the generic syscall table (different numbers; no `_sysctl`, `uselib`, `create_module`, `get_kernel_syms`, `query_module`, `nfsservctl`, `ioperm`, `iopl`), `AUDIT_ARCH_AARCH64 = 0xC00000B7`, no x32. The table becomes per architecture, skipping names the architecture lacks, still refusing unknown architectures. `clone` flags stay argument 0. A wrong number either leaves a hole or denies a needed call, so every name must be cross-checked against the kernel header table and probed natively.
  - `github.py` (`X86_64_TOKENS`, `OTHER_ARCH_RE`, `appimage_candidates`) and the error text in `cmd_add.py`: parametrize by host architecture; add an ELF `e_machine` check (0x3E, 0xB7) in `appimage.py`/`fetcher.py` as the backstop (also covers `add --file/--url`).
  - `tools.py`: `dwarfs` and `gh` are single x86-64 pins; `Tool` would carry per-architecture variants. Both projects publish aarch64 builds; the pins need real, user-approved downloads.
  - Catalog: AM has parallel aarch64 lists (to confirm), so appjail-db would publish one catalog per architecture and `indexstore.py` would select by host architecture, keeping a snapshot of one architecture from serving another.
  - `seccomp.py` also filters `socket`, `socketpair` and `personality`, which have other numbers on aarch64; the `io_uring` calls share theirs.
  - `landlock.py`: the Landlock system calls have the same numbers on aarch64; only its `platform.machine()` check is x86-64.
  - `runtimejail.py`/`jail.py` look architecture-neutral (to verify: the `/lib64` bind).
- **Verification cost:** an arm64 guest on an x86 host runs under TCG (5-20x slower: fine for unit tests and seccomp probes, painful for GUI e2e) and needs `qemu-system-arm` and `qemu-efi-aarch64` on the host and an arm64 Debian image. `tests/vm/*.sh` would take a `VM_ARCH`. Real arm64 AppImages need new approvals. `ubuntu-24.04-arm` is below the minimum supported system. GitHub's September 2026 announcement makes Ubuntu 26.04 generally available on x64 and arm64, so an `ubuntu-26.04-arm` runner should exist (label not checked); with it arm64 could be tested natively in CI, otherwise it would be "supported, tested in an emulated guest only", and the README must say so.
- **Staging if approved:** (1) architecture-aware core with no change on x86, unit-testable on the x86 guest; (2) arm64 guest scripts and suite under TCG; (3) arm64 helper pins and an aarch64 catalog from appjail-db; (4) one real arm64 AppImage smoke test and an arm CI job if a runner exists; (5) docs at each step.

## Rejected alternatives

Approaches that were evaluated and not taken, with the reason.

### Building on `sas` (Samueru-sama/simple-appimage-sandbox)

A POSIX shell wrapper around bwrap (952 lines when evaluated; the current release, 2.4, makes FUSE optional with `--allow-fuse` and otherwise extracts and runs, which was not re-evaluated). Rejected as a base: it is shell (the project is Python), its defaults are permissive (D-Bus, network, audio, X11 and Wayland sockets all on; `/tmp` and `/etc` shared; `/dev` fully bound; a host `xdg-open` daemon), it mounted with FUSE instead of extracting, and it is a moving external dependency. Taken as reference only: `--unshare-user/pid/uts/ipc/cgroup`, `--die-with-parent`, `--new-session`, GPU binds including nvidia nodes. AM also supports `aisap`, not evaluated.

### Flatpak

Mature sandbox, portals, signed OSTree remotes and permission overrides; covers the need when the app exists on Flathub. It does not cover AppImages released only on GitHub, user-pinned per-release hashes with a quarantine, or declarative manifests in the user's own git repo. appjail targets that gap and does not replace Flatpak: prefer Flatpak when the app is there. appjail writes a `.flatpak-info` identity file only because xdg-desktop-portal understands no other sandbox identity (see DESIGN.md, Portals).

### Firejail (netblue30/firejail)

A setuid-root C program under GPL-2.0 with 900+ maintainer-written profiles. Not a base and not a dependency: it needs setuid root (appjail runs unprivileged bubblewrap), its profiles are implicitly trusted text rather than pinned declarative manifests, and GPL-2.0 rules out copying code or profile text into this MPL-2.0 project. Only ideas were taken, written from scratch: its denylist categories were the checklist for the `dirs` sensitive-path policy; it strips token variables from the environment (appjail clears the whole environment and passes a whitelist); its `--x11` defaults to Xephyr and it dropped Xpra, which supports a separate X server inside the jail, never the host X11 socket.

### A private network namespace built without pasta

Would have needed a host-side CONNECT proxy with a host allowlist on a unix socket plus an in-jail TCP relay for `git` and `gh`, which speak no HTTP proxy over unix sockets: new code on the path of every download. Superseded: pasta (package `passt`) gives a private namespace with ordinary outbound sockets and is an optional dependency, required only for apps with `network`.

### Related projects compared in the README (November 2026)

The README's "Alternatives and related projects" section was written from each project's GitHub page and website, read in November 2026; commit dates are not shown on those pages, so activity claims are limited to what a release page or search listing showed. None of these was installed or run. Re-checked for the 0.4 release through the GitHub API (language, license, last push, archived, moved) and, for aisap, its README: Bread and appimage-cli-tool were last pushed in 2024 and 2023, Zap (checked in November 2026, after the release) on 2024-06-14, not archived, latest release v2.2.1 of December 2021, and aisap's largest language is now Zig although its README calls that implementation not yet usable. The claims about features were not re-read. Not evaluated as a base, only compared:
- **AppManager (kem-a/AppManager)**, Vala/GTK, GPL-3.0: per-app private home and bubblewrap sandbox with `xdg-dbus-proxy`; the closest in spirit. A GUI over files the user already has; no pinned releases, quarantine or declarative manifests found. Vala and GPL-3.0 rule out reuse here.
- **Soar (pkgforge/soar)**, Rust, MIT: package manager with signature and checksum checks and GitHub/GitLab/Forgejo release tracking; release notes mention Landlock sandboxing, but the configuration reference has no sandbox key and no update delay was found. Re-read its docs before claiming more.
- **Bubblejail (igo95862/bubblejail)**, Python, GPL-3.0-or-later: bubblewrap profiles and a GUI for any desktop app; not AppImage-specific and does not fetch or pin anything.
- **ubi** has `--min-age-days`, the only quarantine-like feature found among the release installers; **eget** verifies a published `.sha256`.
- **Flatpak**: the sandbox and portal claims in the README come from the entry above, not from flatpak.org, whose front page does not describe them.
- FreeBSD **AppJail** (DtxdF/AppJail, BSD-3-Clause) shares only the name.

## Design decisions

Choices that shape the design, with the reason and, where one exists, the condition for revisiting.

### Mounting AppImages

FUSE mounts do not work well in user namespaces. Images are extracted and `AppRun` is executed.

### Landlock: only the abstract-socket scope

An unprivileged kernel filesystem and network filter. appjail uses exactly one part of it: `LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET` (ABI 6, Linux 6.12) on every app jail not behind pasta, applied by a small exec wrapper in front of bwrap (`landlock.py`, raw system calls like the seccomp filter, since bwrap cannot apply Landlock; a wrapper rather than a `preexec_fn`, which is unsafe in a launcher with threads). Behind pasta it is not needed, since pasta's private namespace isolates abstract sockets, and not possible: pasta refuses to start its command under the `no_new_privs` Landlock requires of an unprivileged process. The reason is `network_host`: an app with it shares the host's network namespace, and abstract unix sockets belong to that namespace, not to the filesystem, so the mount namespace does not hide them. The X server's `@/tmp/.X11-unix/X0` is the dangerous one: desktops commonly let any process of the user connect, which means keystrokes and input injection into every X11 app. On a kernel without ABI 6 an app with `network_host` is refused; the other apps still run, since their private network namespace already isolates abstract sockets.
- Not used: filesystem rules (the mount namespace already does that) and network rules, which cover only TCP bind and connect by port (no UDP, DNS or host names), so they add nothing for the download jails and would break apps that need other ports. Signal scoping adds nothing either: the jail has its own pid namespace.
- **Revisit when:** a network jail starts running third-party code, a bwrap release gains Landlock support, or an allowlisting proxy is wanted.

### A graphical front end

`appjail-gui` is a tkinter window over the CLI, shipped in the same package. tkinter is in the standard library, so `dependencies` stays empty, but Debian and Ubuntu split it into `python3-tk`; the GUI is therefore optional and imported lazily, and the CLI never needs it. A toolkit from PyPI (Qt, GTK bindings) would break the stdlib-only rule. The GUI does not reimplement any command: it builds an argv, runs `cli.main` with a console that shows prompts as dialogs, and so keeps one parser, one set of checks and the same reviews. The one exception is read-only data for lists: the Apps tab reads the manifests and the Search tab reads the catalogs directly (`gui/apps.py`), so rows can be selected; installing still goes through `add`. It never passes `--yes` for the user; `perms`, `remove`, `update` and the rest ask through a dialog that defaults to No. Revisit when a command needs progress or cancellation that a worker thread cannot give (downloads run in a jail subprocess with no incremental output).

### Output layout and the error stream

- **Decided:** one small vocabulary in `Console` (`kv`, `table`, `item`, `note`, `warn`, `error`) instead of hand-padded strings in each command; errors on stderr, everything else on stdout; `list` is a table and the permissions move to `list -l`.
- **Why:** `list` put every field of an app on one line, and four label styles made the other commands hard to scan. stderr for errors lets a pipe or script see only results. The permissions moved out of the default view because they are what made the line long; `perms APP` and `list -l` show them.
- **Rejected:** a third-party formatting library (stdlib-only rule); `--json` on the commands that change something (their output is a conversation with prompts; a script has `--yes` where it is allowed); always-on colour (breaks pipes and log files).
- **Cost:** tests and any script that matched the old text (`WARNING:`, `Label : value`, `Summary:`) had to change; the GUI shows the same text in its output pane.

### Nothing is granted by default, display `none`

- **Decided:** `add` grants nothing beyond the window: `audio` and `gpu` are `--allow` like the rest (`--no-audio` and `--no-gpu` are gone), and `display = none` is a fourth display value for apps with no window. `wayland` stays the default, since most AppImages are graphical.
- **Why:** audio was the one grant appjail could not scope (the Pulse server cannot restrict a client by device, so it includes the microphone and the sound other apps play; the private graph of `audio_mode = pipewire` is what scopes it), and the GPU is a large driver attack surface plus hardware information in `/sys`. Most command-line tools, converters and editors need neither. An app that needs them fails visibly (no sound, slow rendering) and `perms APP --allow audio` fixes it, which is the cheaper mistake than a silent microphone grant. The docs said "everything is denied by default" while `Permissions()` denied and `add` granted; both now agree.
- **Cost:** installing a media app or an Electron app takes one more flag (the GUI Add form has the checkboxes unticked). Apps already installed keep their manifests, which record `audio` and `gpu` explicitly.
- **Rejected:** lowering the defaults from the AppImage's own `.desktop` (`Terminal=true`): possible later, since untrusted data may only reduce permissions, but not needed now; a headless `display` inferred automatically (the mode is always chosen by the user, like Xwayland).
- **Revisit when:** the audio defaults need to change (see "Audio: `mic`, `audio_mode` and the private PipeWire graph").

### Granted paths are bound by descriptor

- **Decided:** `runtimejail.Grants` opens each granted directory and file once (`O_PATH`), runs the type and policy checks on what was opened (`fstat`, `readlink` of `/proc/self/fd/N`, and a `stat` of that path, which must be the same file), and passes the descriptor to bwrap's `--bind-fd` or `--ro-bind-fd`.
- **Why:** bwrap resolved the path string again, so a same-user process or an app with a writable grant could swap a component for a symlink between the check and the bind. A test shows the app reading the forbidden file before the fix. Low severity, since the attacker already runs as the user or holds a writable grant, but it is the jail's own boundary. Checking after the open also makes a walk of the intermediate components (`dir_fd`, `openat2`) unnecessary: a swapped component only changes what is opened, and that is what gets judged.
- **Behind pasta:** pasta closes inherited descriptors, so `reopen.py`, between pasta and bwrap, opens each path again and compares device and inode with the launcher's record. The comparison follows the open, so no window is left; a swap there refuses the start instead of keeping the checked file.
- **Rejected:** binding `/proc/self/fd/N` (bwrap has an option made for this, added in 0.10 for the same race in Flatpak), and comparing the inode just before exec (a window remains). The `sh` of `net_wrap` could not do the reopening: it has no `fstat` and dash accepts only single-digit descriptors.
- **Cost:** bubblewrap 0.10 or later is required (its changelog: added to resolve CVE-2024-42472 in Flatpak); both minimum systems have it. A `dirs` entry naming a regular file is now refused, which `--dir` already did at parse time. Ubuntu 26.04 has 0.11.1 (Launchpad) and the Debian 13 guest 0.12.0.

### Audio: `mic`, `audio_mode` and the private PipeWire graph

- **Decided:** `audio` is playback only and `mic` is a separate permission (it needs `audio`; `--allow mic` implies it). `audio_mode` is `pipewire` (default, a private PipeWire graph per app) or `pulse` (the host's Pulse socket). Existing manifests with `audio = true` became playback only without any notice; that was accepted.
- **Why:** the Pulse server cannot restrict a client by device, so capture is part of the socket and a separate permission would be a promise it cannot keep. PipeWire cannot be shared either: it restricts only clients it identifies as Flatpak sandboxes (a `.flatpak-info` in the client's root, checked against PipeWire 1.4 and WirePlumber 0.5), and neither workaround held up against PipeWire 1.4.2 and WirePlumber 0.5.8 with a test video source: a `.flatpak-info` in the app jail (it would also make GLib and Electron believe they run under Flatpak), and a second socket marked `restricted` through `module-access` (WirePlumber's default rules give such clients `r,x` on every object, so they can still record, link to the camera and receive its frames). A private graph keeps the promise: with no source tunnel the app only finds the silent monitor of its own sink (measured).
- **How:** tunnels (`libpipewire-module-pulse-tunnel`) from a graph the app owns to the host's Pulse server. The daemons run in a jail with no `/dev/video*`, `/dev/snd` or `/sys` devices, so no hardware node can appear; the profile that disables the monitors and the check of the graph after start are further layers (unjailed, a WirePlumber with its monitors enabled put the host camera into the graph). The tunnel module is stock PipeWire (the options are the same in 1.4.2 and 1.6.11, read from the source), needs no D-Bus, and its stream shows on the host like any client.
- **Fallback:** when the graph cannot be used, an app with `mic` gets the Pulse socket with a warning that names the reason (it warns and does not refuse); an app without `mic` gets no audio, with a warning, because the host's Pulse socket would open a microphone it was not granted. Chosen by the user: a missing sound is visible and harmless, a silently open microphone is not. In `pulse` mode capture cannot be denied, and `add` and `perms` say so.
- **Start order:** PipeWire starts first and WirePlumber and `pipewire-pulse` only once `pw-dump` gets an answer from it.
  - **Why:** WirePlumber connects once; started in parallel with PipeWire, on a loaded machine it can try before the socket exists, log "Failed to connect to PipeWire" and stay up for good without a connection, so the graph never completes ("WirePlumber not connected", `pw-dump` timing out). Found by reproducing the intermittent failure of the Ubuntu 26.04 runner in the Ubuntu guest under CPU load (1 of 15 runs; the full daemon log showed the failed connect 0.4 ms before the socket appeared). With the start order fixed, 60 loaded runs of `tests/test_private_audio.py` in the Ubuntu guest gave no start-up failure (before: 1 in 15).
  - **Not the cause:** the daemons' `module-access` warning "flatpak check failed: No such file or directory" for clients from another PID namespace (it appears in runs that pass; those clients are treated as sandboxed but still get what the look at the graph needs).
  - **Two other causes of failures, in the tests only:** (1) on PipeWire 1.6 the test host has two equal microphones and WirePlumber's default changed after the tunnel had connected, which added a second link; the fixture now settles the defaults. (2) On a loaded machine the test host's own tone source (`audiotestsrc`) is now and then silent for a second or more (a plain recording from it shows it, no appjail involved; about 1 fresh host in 40 under six busy loops), so the whole-launch test and the Pulse-client recording test (which failed once on the runner this way) record the same window from the host source directly and skip, rather than fails, when that reference is silent too; a silent app recording with a sounding reference still fails.
- **Module loading and the filter:** a Pulse client may load modules, and the private graph's `pipewire-pulse` could reach the host's socket, so an app without `mic` could load `module-tunnel-source` and record the host microphone (reproduced in both guests before the fix). The configuration now sets `pulse.allow-module-loading = false` for that daemon, and the graph's jail gets the seccomp filter like the other helper jails (it had none, against this document). Rejected: giving only `pipewire` the host socket and running the other daemons in a second jail. It is the more direct fix, but `pw-dump` in the second jail connected to the manager socket and then waited until the timeout, since PipeWire treats a client from another PID namespace as sandboxed (the `flatpak check failed` line above); it was not pursued. One filter descriptor per jail: bwrap reads it to the end, and a descriptor shared between jails shares its offset, so the second jail failed with EINVAL. On the host's socket (`pulse` mode, the fallback) module loading cannot be turned off from here; tested on PipeWire 1.4.2 and 1.6.2: `module-ladspa-*` with an absolute path is not implemented, so no library is loaded, but null sinks, loopbacks, a TCP listener and FIFOs (mode 0666, any path the user can write) were. PulseAudio proper: see the next entry.
- **PulseAudio proper:** reproduced in the `debian-pulse` guest (PulseAudio 17.0, a sine source as the microphone): `pactl load-module module-ladspa-sink plugin=/abs/path.so` makes the `pulseaudio` process `dlopen` the library, so its constructor runs there, and an app in `audio_mode = pulse` did exactly that with a library from its own home (its host path is in `/proc/self/mountinfo`). Decided by the user: the host's Pulse socket is refused when PulseAudio is behind it, in `pulse` mode and in the fallback (no audio, with a message). Rejected: warning only (an escape, not a weaker promise), and refusing `pulse` mode everywhere (it works on PipeWire hosts, whose server implements no module that loads a path; its remaining module effects are named in DESIGN.md). The server is identified through the inode of the listening socket, because `SO_PEERCRED` of a socket-activated server names systemd; an unidentifiable server is treated as PipeWire's and keeps the warning, which is the weak point of this check. The private graph on that host works and refuses the same requests (`tests/test_pulseaudio.py`). Without `pipewire-pulse` (the `debian-pulse` guest installs it, units masked, for the graph), the graph is unavailable and the fallback gives no audio, with or without `mic`: tested against the real server with that one tool hidden from the availability check, and checked once with the package removed from the guest (the graph test skips, the rest passes).
- **Offered both modes** because `pulse` follows the host's device policy and `pipewire` does not. Measured limits of `pipewire` (PipeWire 1.4.2, WirePlumber 0.5.8; `tests/test_private_audio.py`): the tunnel connects to the devices that are the default at the start; a later default change adds links (playback on both, the microphone mixed) instead of moving them, and naming the devices does not prevent it; unplugging removes only the unplugged device's links and nothing re-attaches; a tunnel on a single unplugged device is silent for good; it does not reconnect when the host's `pipewire-pulse` restarts.
- **Rejected:** a filtering proxy in front of the Pulse socket. A denylist that blocked recording still let a client load modules into the host's audio server and mute its microphone, and a safe one needs an allowlist of the protocol plus per-source filtering, parsing untrusted data in Python. Also rebuilding the tunnel when devices change: a `pw-cli` session could unload the module, but `pw-cli` crashed doing so, and restarting the daemons drops the app's connection.
- **Not verified:** a real headset, microphone and desktop (the guest has test devices only); two apps at once (each has its own graph, so the memory doubles); latency. The versions in Ubuntu 26.04 run the full suite in the Ubuntu guest and on the CI runner.
- **Revisit when:** the limits above hurt (a supervisor that rebuilds the tunnel on host device changes), or xdg-desktop-portal gains an audio portal.

### The Wayland socket is checked by what it lists, not by the protocol

- **Decided (by the user), after measuring nine compositors on Debian 13 and Ubuntu 26.04 (docs/compositor-assessment):** `run` reads the registry of the socket the app will get and refuses a windowed app (`display` wayland, xwayland or xwayland-rootful) when it lists a privileged interface (`wayland.PRIVILEGED`), unless the manifest grants `full_wayland`; then it warns and runs. `display = none` never asks.
- **Why:** principle 4 says what cannot be enforced is refused. The first rule (refuse where `wp_security_context_v1` is missing) rested on a wrong claim that GNOME has the protocol; it does not, and GNOME's own socket lists nothing privileged (it guards ScreenCast, RemoteDesktop and InputCapture on D-Bus), so that rule refused every app on stock GNOME while protecting little. The protocol is also not sufficient: KWin offers it and its restricted socket still lists data-control, and a client read another client's clipboard through it; Hyprland 0.53's restricted socket lists virtual input and a client typed through it. What decides is what the socket lets a client do. A warning that scrolls past in a terminal, or never shows from a menu entry, is not consent.
- **KWin is refused**, like any compositor whose app socket lists a privileged interface. Accepting data-control on KWin alone would give the capability of `full_wayland` without asking and would go stale with KWin. Plasma users need `full_wayland` per app until KWin hides data-control. Ordinary copy and paste is not affected (measured on every compositor, with keyboard focus, in both directions): it uses the core clipboard, which needs focus. **Revisit when:** KWin hides data-control on restricted sockets, or a narrower grant for the clipboard alone is wanted.
- **Allowlist (decided by the user, 2026-11-12):** the denylist alone let an unknown dangerous interface through on a compositor that was not measured (niri, river, COSMIC, Muffin) or in a new version of one that was. `wayland.ALLOWED` now lists the globals checked to act only on the client's own surfaces, its input while focused or its buffers (every non-privileged global the measured compositors list); a global in neither list is `unknown` and refused like a privileged one, named in the message, unless `full_wayland`. The denylist stays, so known interfaces are still named by what they allow. `tests/test_wayland.py` fails when a saved registry (full or restricted socket) holds an unclassified name; adding it found six on full sockets only, all classed privileged (`ext_transient_seat_manager_v1`, Hyprland's focus grab, toplevel mapping, CTM and lock notifier, COSMIC's workspaces), so no verdict changed; a live run of `tests/compositors/rule_a.py` with the new lists in the `debian-compositors` guest (2026-11-12) gave the saved verdicts on all nine compositors and no unknown global. KWin's screen power, brightness, virtual desktops, screen edges and lock-key state became a `desktop` kind. **Allowed after a decision** (listed in the README): `ext_idle_notifier_v1` and `org_kde_kwin_idle` (a privacy signal, not control; refusing them would refuse sway and Hyprland), `wp_drm_lease_device_v1` (non-desktop outputs; GNOME lists it), pointer constraints and shortcut inhibition (while focused), the capture-source managers (capture needs the privileged copy manager). Rejected: a separate, weaker grant for unknown globals (`full_wayland` already means "more than appjail vouches for"); measuring the unmeasured compositors first (they may not be packaged for the supported systems; the allowlist protects without measuring them). **Cost:** a compositor update that adds a harmless global refuses apps until it is classified; the message names it and the README asks for a report. **Revisit when:** a commonly used compositor's new global is reported, or a protocol for idle notification gets a permission of its own.
- **Limits:** the classification is by name, not version (a new version of an allowed interface is assumed to keep its scope). The measurements are of headless compositors, not of real sessions. The names the D-Bus filter refuses are what guard GNOME (see D-Bus names below).
- **How:** a manifest permission, not a `run` option, so that menu entries and `open` (which run `appjail run NAME`) can work for an app the user decided about. The check comes first in `runner.launch`, after the restricted socket exists and before the audio graph, the filtered bus or the portal instance are started; a refusal through `open` is also a desktop notification. Existing manifests do not have the key. A restricted socket that refuses connections is retried for a few seconds (`wayland.CONNECT_ATTEMPTS`).
- **Tests:** the registries measured on real compositors are replayed against the rule (`tests/test_wayland.py`, from the saved results); the stand-ins are `NO_RESTRICTION` and `RESTRICTED` for the socket and `NO_PRIVILEGED` for its registry, and `COMPOSITOR` in `tests/helpers.py` bundles `RESTRICTED` and `NO_PRIVILEGED` for the tests of `runner.launch` that are not about the rule. The tables of the assessment are generated from the saved results and checked by `tests/test_assessment.py`. The opt-in end-to-end suite under headless weston (which lists privileged interfaces) adds `--allow full_wayland` at `add`.

### Icons: a canonical PNG, written by appjail, no jail

- **Decided:** the app's PNG icon (and the PNG rsvg-convert makes from an SVG) is rewritten by `pngclean.sanitize` before it is installed: chunks and CRCs checked, data inflated to the exact size the header promises, only IHDR, PLTE, tRNS, IDAT and IEND written. The audit had suggested re-encoding in a jail.
- **Why not a jail:** a jail needs an image tool (ImageMagick or similar) that is not a dependency, and that tool would itself decode the untrusted file. The sanitiser is stdlib code that never interprets a pixel; what it removes is the malformed structure, ancillary chunks (text, profiles, EXIF), trailing bytes and oversize data that crafted icons use against the loaders in the shell and the file manager.
- **Limit:** a bug in a loader that is triggered by pixel values of a well-formed image is not removed. **Revisit when:** a tool that decodes and re-encodes safely is already a dependency.

### Camera: the V4L2 capture nodes, nothing else

- **Decided:** `camera` binds the `/dev/video*` nodes whose driver reports video capture and, for each, its own sysfs directory (read-only, with the `/sys/dev/char` symlink recreated). Off by default, a risky grant (`add` and `perms` warn).
- **Why:** PipeWire cannot hide a camera from a jailed client (see "Audio: `mic`, `audio_mode` and the private PipeWire graph"), so a device bind is the only path that works for apps that open `/dev/video*` themselves. Tested in the guest against the `vivid` virtual camera: a frame captured through `v4l2src` and through raw mmap ioctls, one camera or two, none present, and the other nodes absent.
- **Narrow, not broad:** a first version bound all `/dev/video*` and the whole of `/sys/devices` and `/sys/dev/char`. Only the capture nodes and their own directory are needed: output, metadata and codec nodes are other devices, and the media controller is unnecessary for capture.
- **Portal route:** apps that reach the camera through PipeWire use the Camera portal (`portals`, `--portal Camera`), which needs no code. In the guest the portal's remote showed only the camera-role node, and a real frame arrived through it. Not verified: a real V4L2 camera node exposed by the portal. There the node was created by WirePlumber's V4L2 monitor and never reached WirePlumber's own object managers, so neither automatic linking nor the portal's grant worked in the guest. Explained on 2026-11-13 (PipeWire 1.4.2 with WirePlumber 0.5.8, and 1.6.2 with 0.5.13): `vivid` has a test control, `s32_2_element_array`, of type INTEGER with two elements; PipeWire's V4L2 plugin keeps it as a plain integer and reads it with `VIDIOC_G_CTRL`, which fails with EINVAL on an array control, so the whole `Props` parameter fails; WirePlumber then aborts the node's activation ("enum params id:2 (Spa:Enum:ParamId:Props) failed"), raises no `node-added` event and makes no session item, so nothing can link to the node ("target not found"). PipeWire fixed it upstream, unreleased as of 2026-11-13 (`6734d69c`, compound controls are no longer props; `919de4c5`, one unreadable control no longer fails the others). An ordinary webcam has no such control, so this is an artefact of the test camera; a real camera through the portal is still a manual check.
- **Not verified:** a real USB webcam (its sysfs path is deeper than `vivid`'s), hot-unplug while the app runs, and whether opening a real device for the capability query wakes it.
- **Cost:** no per-camera choice; a camera plugged in after the launch is not visible until the next start; the nodes are opened once at every launch with `camera`.
- **Revisit when:** a real webcam shows a missing sysfs attribute, or per-camera selection is wanted.

### Waiting for every process in the jail, by default

The jail ends with its main command; the `linger` permission (opt-in per app) waits for all processes instead. Waiting always was rejected: an app that leaves a crash handler, `dbus-daemon` or an agent behind would keep `appjail run` from ever returning, and "closing the app closes everything" would no longer hold. Found with VSCodium, whose launcher hook runs `cli.js`, which starts the editor detached and exits. **Revisit when:** most catalog apps need `linger`, or a reliable way to tell the app's own processes from helpers exists.

### D-Bus names refused beyond the shell and portals

- `ca.desrt.dconf`: the settings database; writing it can set GNOME custom keybindings, which run commands.
- `org.gtk.vfs*`: GVfs mounts and host locations outside the jail's file grants.
- `org.gtk.` and `ca.desrt.` are also unownable, like the other desktop namespaces.
- `org.gnome.Mutter*`, `org.freedesktop.a11y*`, `org.gnome.ScreenSaver`, `org.kde.kglobalaccel`, `org.kde.keyboard`: measured on headless Mutter 48.7 and 50.1, where `ScreenCast`, `RemoteDesktop` and `InputCapture` open a session for any client of the bus (the portal's consent dialog is what normally stands in front of them), and `kglobalaccel` answers any client. GNOME offers no privileged Wayland global, so these bus names are what keep an app from the screen and the keyboard there. A complete capture and typing into another client's window through them, as an ordinary bus client with no prompt, were shown on Mutter and GNOME Shell 48.7 and 50.1 (`tests/compositors/mutter_dbus.py`, 2026-11-13). See docs/compositor-assessment.
- `org.cinnamon.Muffin*`: measured on Muffin 6.4.1 (Debian 13 and Ubuntu 26.04, standalone and nested in Xvfb, 2026-11-13), where `DisplayConfig` answers any client of the bus (`GetCurrentState` worked) and offers `ApplyMonitorsConfig`, `ChangeBacklight` and `SetCrtcGamma`; refused as a family, like Mutter's, which it was forked from. Its Wayland socket has no privileged global, so it runs apps; four older or GTK-private versions of ordinary protocols it lists (`wl_shell`, `zxdg_shell_v6`, `gtk_primary_selection_device_manager`, `gtk_text_input_manager`) were added to `wayland.ALLOWED`. The shell on top of it is the next entry. Found on the way: Muffin crashes (a floating-point exception) serving `wl-copy` and `wl-paste`, so any client can end a Cinnamon Wayland session; appjail cannot prevent it, and the README says so.
- `org.Cinnamon*`: measured on Cinnamon 6.4.10 and 6.4.13 (the shell, `cinnamon --wayland --nested` in Xvfb, Debian 13 and Ubuntu 26.04, 2026-11-13), where `org.Cinnamon.Eval` runs any JavaScript in the shell for any client of the bus. As an ordinary client, with no prompt, it ran a command as the user and typed into another client's window; the shell also answers `org.gnome.Shell.Screenshot.Screenshot` for any client, which captured the whole screen (`tests/compositors/cinnamon_dbus.py`, three runs per distribution). Refused as a family; `org.gnome.Shell.Screenshot` already was. Names are case-sensitive, so `org.cinnamon.Muffin` did not cover it. Not measured: the daemons of a full session (`org.cinnamon.ScreenSaver`, the settings daemon).
- **One granted name reaches its whole connection** (found 2026-11-13, `tests/compositors/shared_connection.py`, both distributions). xdg-dbus-proxy with `--talk=NAME` filters by destination name; a call addressed to an allowed name reaches every object of the connection that owns it. A desktop shell owns ordinary names on the same connection as the refused ones: through the proxy as appjail starts it, `org.gtk.Notifications`, `org.gnome.keyring.SystemPrompter` and `org.gtk.MountOperationHandler` reached Mutter's `RemoteDesktop.CreateSession` on GNOME Shell, and `org.freedesktop.Notifications`, `org.gnome.Magnifier`, `org.gnome.Caribou.Keyboard`, `org.gnome.Panel`, `org.gnome.keyring.SystemPrompter` and `org.x.StatusIconMonitor.cinnamon_0` reached `org.Cinnamon.Eval` on Cinnamon. So the blocklist protects only where every name of the privileged connection is refused (Mutter, Muffin, KWin alone). The README states the limit until it is fixed. Options: (a) at `run`, before starting the proxy, refuse a granted name whose current owner also owns a refused name (simple, covers what was measured; misses a name whose owner appears or changes after the check); (b) replace `--talk` by `--call` rules that confine a name to its own objects and interfaces (exact, but each service's paths and interfaces must be known, and a name without rules would need them from the user); (c) (a) for every name, plus `--call` rules for the common ones (notifications).
  - **Decided (c), by the user, 2026-11-13.** (a) alone refuses grants that work when confined (notifications on Cinnamon) and is blind after launch; (b) alone breaks unknown services or needs rules in the manifest. Implemented: `dbusproxy.CONFINED` gives the known services `--call` and `--broadcast` rules (interfaces from their specifications: Desktop Notifications, `org.gtk.Notifications`, the Secret Service, MPRIS, StatusNotifierWatcher), and every other granted name passes `dbusproxy.check_owners` at `run`. A known service skips the check, since the proxy confines it whoever owns it. Measured: in a private bus with a fake shell (`tests/test_dbus.py`), xdg-dbus-proxy 0.1.6 applies the `--call` rules also when the app addresses the owner's unique name, a path ending in `/*` includes the path itself, and `--broadcast` lets the service's signals through; on both shells (`shared_connection.py`) every allowed name is either confined (the privileged call refused, the service's own call working) or refused at launch.
  - **Rejected for now:** rules written by the user in the manifest (a format change, and wrong rules fail silently); deriving a path from the name (`org.foo.Bar` → `/org/foo/Bar`; MPRIS and StatusNotifier already break the convention); re-checking owners while the app runs (the proxy cannot be told, and stopping the app on a name change is a new behaviour). The remaining limit, an owner that appears or changes after launch, is in the README. The portal rules' own `--talk=org.freedesktop.portal.Documents` was checked the same way (Debian 13, activated on a private bus): `xdg-document-portal` owns only that name, and the permission store runs as its own process (`xdg-permission-store`).
- Not refused: `org.freedesktop.FileManager1`, which is needed to browse files when portals are active. Terminal and other file-manager names vary by desktop and were not verified on a live desktop, so they are not listed.

### X11-only apps on GNOME: rootful Xwayland with openbox

A rootless Xwayland needs the compositor to be the X window manager. mutter does that only for the Xwayland it spawns, so on GNOME the windows of the private rootless Xwayland are mapped in the X server and never presented (found with `xeyes`, Java/AWT apps). `display = "xwayland-rootful"` drops `-rootless`: Xwayland makes one window of its own, and a small `openbox` in the jail provides stacking, focus and the cursor that plain rootful lacks. It is a separate `display` value, not an automatic fallback: the choice stays visible in the manifest, and the rootless mode stays for compositors where it shows several real windows. `openbox` over `matchbox` for the familiar behaviour with several windows. Rejected: binding the session's X socket as Flatpak does (every X client could then read the others' keystrokes and screen, and it needs a per-app cookie and a Landlock exemption); a nested kiosk compositor (`cage`; one more dependency with GPU and input quirks for the same result); Xpra (a client on the host, two moving parts). Native Wayland remains the better route for apps whose toolkit has it (Java: `-Dawt.toolkit.name=WLToolkit` where the JDK has it).

### Vulnerability reports through GitHub, latest release only

`SECURITY.md` points to GitHub private vulnerability reporting rather than an email address: tracked files carry no personal data, and it needs no infrastructure. It promises no response or disclosure times (one maintainer, best effort). Only the latest release is supported, with no backports, since the tool has no long-lived branches. Catalog contents are out of scope: a catalog is untrusted data and a bad entry is the case appjail contains; only a flaw in how it is parsed or shown counts.

### Catalog built by appjail-db, not on the user's machine

- **Decided:** the built-in `appjail-db` source downloads `catalog.json` from `alberto743/appjail-db` at a commit resolved through the GitHub API. The conversion (sparse git fetch of AM, parsing the install scripts (8,735 at the analysed commit), merging the AppImageHub `feed.json`) lives in appjail-db and runs weekly in CI.
- **Why:** the client no longer needs a network git jail, a 39 MB fetch or a parser of untrusted shell text; one build point carries the size and shrink checks (fewer than 5,000 apps or a drop of more than 10% is refused) and records owner changes in its history; the update is a 1.5 MB text download. The commit pin makes every catalog traceable and an older one re-fetchable (`--commit`).
- **Rejected:** converting AM on the client (the previous design), and an unpinned raw URL (no way to say which state was reviewed, and a failed API lookup would silently skip the pin).
- **Cost:** appjail-db becomes a dependency of `search` (not of installs); the catalog is unsigned, so its integrity rests on HTTPS and on who can write to appjail-db.
- **Revisit when:** appjail-db is unmaintained (any other catalog works with `index add`), or catalog signing becomes worthwhile (a signature by a key pinned in appjail).

## Facts the design rests on

### GitHub API

- Release assets have a `digest` field (`sha256:<64 hex>` or null). Older releases may lack it, hence tier 4 (trust on first use) as the fallback.
- Attestations: `GET /users/{u}/attestations/{digest}` and the `orgs/` variant need a token. The repo-scoped `GET /repos/{owner}/{repo}/attestations/{digest}` works unauthenticated and returns `attestations[]` with `bundle_url` (a short-lived signed blob URL). appjail uses the repo-scoped endpoint with the digest from the release asset. Existence alone is not proof; the bundle is verified (DESIGN.md, Attestation verification).
- The unauthenticated rate limit is 60 requests per hour per address; `GET /rate_limit` is free. One `add` costs 4 requests, 5 when the asset has a digest (the attestation is looked up before and after the download); one `update` about 4, one `index update` of the built-in source 1.

### AM index (ivan-hc/AM)

Analysis done for appjail-db, which now converts AM; appjail itself no longer reads AM. Not to be redone.
- `AppMan/appman` is a stub that downloads `APP-MANAGER` from `main`; AM self-updates and runs install and updater scripts from `main` outside any sandbox. Only 6 of 8,735 install scripts mention a checksum or signature (counts at the analysed commit; AM's own release notes later count about 3,600 unique apps, so recount before quoting). Its own sandbox wraps `sas` or `aisap`.
- `programs/x86_64-appimages` has lines `◆ name : description` (U+25C6); `programs/x86_64/<app>` holds the scripts. 8,247 scripts have `SITE="owner/repo"`, about 224 point elsewhere, a few use `SITE2=` for a repackager. `SITE=` may appear more than once in a script: the first assignment counts, matched by regex, never sourced.
- Commit signatures (last 200 commits at the analysed state): 139 carry a PGP signature (GitHub web-flow key), 2 SSH, 59 unsigned; the maintainer's own commits are unsigned. They cannot prove maintainer authenticity. Not to be redone.
- Reference clone for reading: a blobless no-checkout clone, read with `git show <commit>:<path>` as text. Existing sandbox flags are in `modules/install.am`.

## What the tests cover

- Verified against real software: `add` and `run` of real AppImages (SquashFS and DwarFS), tier 3 and tier 4 downloads and the quarantine hash, Sigstore verification with the real `gh`, the private Xwayland with an X11-only app, a GUI app with `network` behind pasta, the real xdg-desktop-portal frontend with a fake backend and with the GTK backend (non-interactive calls), the real `xdg-dbus-proxy`, the menu entry through `gio`, the real appjail-db catalog, a real PipeWire and pipewire-pulse (`tests/test_audio.py`: Pulse reachable, the camera not), the real permission store (an app's entries forgotten on `remove`), and Landlock ABI 6 on Linux 6.12 (an outside abstract socket refused, the private Xwayland still reachable).
- Tamper tests: modifying the pinned hash, the stored AppImage or the extracted tree makes `run` refuse; a changed digest on `update` is a new candidate under the quarantine; a granted file, directory or parent directory swapped for a symlink just before the jail starts does not reach its target, with and without pasta (`tests/test_grant_swap.py`).

**Not verified**
- Portals: the GNOME, KDE and wlr backends and interactive dialogs. Desktops differ in which interfaces they implement; each privileged interface depends on its backend asking the user.
- Xwayland: GPU acceleration (glamor). `xwayland-rootful` works on GNOME in a brief test only; clipboard and drag-and-drop through its window are unchecked. `openbox` with `-decorate` never gets going under headless weston and sway, so the test runs without it.
- D-Bus: real desktop services (notification daemon, MPRIS players) and tray icons with `-<pid>` bus names.
- Network: IPv6 on a real internet route (covered only by a fake network).

## Platform and CI

- Minimum supported systems: Debian 13 and Ubuntu 26.04. On Ubuntu 24.04 the real-portal tests fail (xdg-desktop-portal 1.18 does not export `FileChooser` with the tests' fake backend; cause not investigated) and its `reuse` cannot read `REUSE.toml`. No workarounds for older systems.
- The CI runner label is `ubuntu-26.04`, not `ubuntu-latest` (still Ubuntu 24.04 when tried). GitHub's changelog (2026-09-17) schedules the move of `ubuntu-latest` to 26.04 between 2026-10-19 and 2026-11-19; once it is complete (planned for December 2026), switch the workflows to `ubuntu-latest` and check CI is green.
- Pinned helper tools (`gh`, `dwarfs`): `bump-tools.yml` proposes a PR for each new stable release; it never merges. Dependabot cannot do this (the pins are URLs and hashes in Python source). The PR carries the measured size and sha256, and a checklist (release notes, the dated Debian-packaging comment, the opt-in tool and attestation tests in the guest). **Known limit:** PRs created with `GITHUB_TOKEN` do not trigger workflows; closing and reopening the PR starts CI. Using a PAT or GitHub App would remove that step but adds a stored secret, so it was not done. Only the latest release is proposed when several were missed. The workflow needs the repository setting that lets GitHub Actions create pull requests; with it off, the scheduled run of 2026-11-09 pushed its branch and then failed, and since a run skips a release whose branch exists, the bump would never have been proposed again. A refused PR now deletes its branch.
- Release notes: most work reaches `main` without a pull request (single commits, or local branches merged with `--no-ff`), so GitHub's generated notes (pull requests only) would be nearly empty, and `release_notes.py` lists the non-merge commits itself; a branch's merge commit is not listed, its milestone commits are. By the files touched, not the subject: many commits have no `Area:` prefix and the verbs vary, while paths always exist. Sections: Security (subject prefix `security`/`seccomp`/`landlock`/`audit`, or only the security modules touched), Interface (changes under `src/` confined to `gui/`, `cli.py`, `cmd_*.py`, `console.py`, `permargs.py`), Logic (any other `src/`), Documentation, Tests, Other (CI, packaging, mixed). A commit that touches `src/` is classified by its source files, whatever else it touches. Commits that came in through a pull request are skipped there because GitHub's notes list them: a squash merge ends in `(#N)`, and a `Merge pull request #N` merge brings in the commits of its second parent (a bump-tools PR merged that way would otherwise be listed twice), under the categories of `.github/release.yml` (labels `security`, `tools`, `dependencies`, `documentation`, else "Other changes"). **Rejected:** grouping by subject prefix (most of the history lands in Other), a hand-written changelog file (drifts from the tags).
- Release build tooling (`build`, `twine`, `hatchling`, `hatch-vcs` and their dependencies, 38 packages): pinned in `.github/requirements-build.txt` by exact version and by every file hash PyPI lists for it (the resolution came from `pip install --dry-run --report`, the hashes from PyPI's JSON metadata; nothing was built or run), installed with `--require-hashes --only-binary=:all:`, and the build runs with `--no-isolation` so the backend is not fetched unpinned either. A changed or replaced upload then fails the release job. The `package` job of `ci.yml` makes the same install on every push, so an out-of-date pin shows up before a tag. Dependabot's pip ecosystem proposes new versions. **Limit:** `pip` in the runner's venv is not pinned (`setuptools`, which `setuptools-scm` needs, is among the pins); the pins were resolved on Python 3.13, the runner's Python may add or drop a conditional dependency, which the CI step would show.
- Commit-message hygiene: commits made from web sessions carried a `Claude-Session:` trailer linking the session; it was removed from the history (messages only, trees unchanged, no tag affected) and force-pushed, the one exception to never rewriting pushed history. To keep it from coming back: `attribution.sessionUrl: false` in the tracked `.claude/settings.json` (read by cloud sessions, which do not see a machine's user settings), a `commit-msg` hook in `.githooks/` and the `hygiene` job of `ci.yml`, both reading `.githooks/forbidden-patterns` (session links, home and temporary paths, non-noreply e-mail). **Limit:** GitHub keeps old commits reachable by hash and through pull-request refs until its support purges them.
- Actions are pinned to the full commit SHA with a trailing `# vX.Y.Z` comment: a tag can be moved, a SHA cannot. Dependabot's github-actions ecosystem reads the comment and updates SHA and comment together. For an annotated tag, pin the commit it points to (`git ls-remote ... tag^{}`).
